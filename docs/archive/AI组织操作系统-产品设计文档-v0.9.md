## 1. 文档摘要

### 1.1 产品暂定名

- 品牌工作名：**班底**
- 品类名称：**可成长的 AI 团队**
- 技术品类：AI 团队操作系统
- 英文工作名：**Agent Team OS**
- 品牌表达：**你的 AI 公司总部。**
- 核心口号：**你负责定方向，班底负责把事情办成。**
- 核心隐喻：用户是董事长，负责定方向、定战略、定目标和做关键决策；董事长助理负责理解意图、判断归属、协调公司和汇总汇报；公司总经理承接目标并对公司经营结果负责；团队负责人组织 AI 成员执行；AI Agent 是长期协作、持续成长的成员，团队方案与做事方式是可复用的组织能力

正式命名前必须完成商标、域名、应用市场和同类产品检索，并通过目标用户访谈验证“班底”是否自然、可信且不会造成错误联想。本文使用“班底”作为产品工作名，使用“AI 团队操作系统”描述底层技术品类。

### 1.2 一句话定位

> 你以董事长身份确定方向、战略和目标，并向董事长助理交办；助理判断由哪家公司承接，公司总经理组织团队和 AI 成员执行，并持续向你汇报进度、风险、资源消耗和最终结果。

面向用户的核心承诺不是“拥有更多 AI 员工”，而是：

> 你负责定方向、定目标和做关键决策，班底负责组织谁来做、如何协作、调用哪些能力、花费多少资源，并将经过验证的经验留给下一次工作。

产品首先解决 Claude Code 长期用户的现实痛点：Agent、Skill、Workflow、MCP、工具、规则和记忆分散在不同项目和配置中，难以统一管理、跨项目复用、稳定编排和持续评测。现实创业公司的组织隐喻用于降低管理门槛，底层仍以可版本化、可追踪的技术能力资产为事实依据。

### 1.3 核心判断

这个产品概念**成立**，而且具有明确的长期价值，但成立的前提不是把多个 Agent 包装成一群会说话的虚拟员工，而是解决四个真实问题：

1. 如何把老板的目标可靠地转化为可验收任务；
2. 如何根据任务属性选择最小必要能力和人员组合；
3. 如何协调并发、依赖、交接、复核与异常恢复；
4. 如何让经验真正沉淀为可追溯、可评测、可升级的组织能力。

因此，产品本质不是“角色扮演式 AI 公司”，而是：

> **目标驱动的 Agent 组织、执行、学习与治理系统。**

### 1.4 产品愿景

用户不需要先学习如何配置 Agent、创建组织或设计工作流。第一次打开产品时，只需要回答一个问题：

> 今天想推进什么？

班底先帮助用户完成第一件真实任务，再在任务值得持续经营时，建议将其保存为一个长期事业空间。一个事业空间可以是一家公司，也可以是品牌、产品、客户项目、内容账号、研究主题或个人事务。

每个事业空间拥有独立的目标、规则、知识、成员、团队方案、做事方式、预算与数据权限。用户可以经营多个事业空间，也可以在其中选择“公司”作为具体类型。

用户只需表达目标，例如：

- 为一个 Next.js 项目开发完整功能；
- 为一个 Python 数据项目定位性能瓶颈；
- 连续生产并审核品牌内容；
- 研究一个市场并形成进入方案；
- 维护多个产品的日常运营指标。

系统负责：

1. 识别任务所属事业空间和业务场景；
2. 将目标转化为结果指标和验收标准；
3. 判断现有成员是否具备所需能力；
4. 按需调用、组队、临时启用专家或建议添加长期成员；
5. 选择或生成合适的做事方式；
6. 管理任务依赖、并发、预算、权限和交接；
7. 对结果进行独立验收；
8. 将经过验证的经验沉淀到成员、团队和事业空间的知识中；
9. 用持续评测决定能力升级，而不是靠自我声明“已经成长”。

## 2. 背景与问题

### 2.1 当前 Agent 使用方式的问题

今天的大多数 Agent 系统仍以“对话”或“一次性任务”为中心：

- 每次任务都重新解释背景和要求；
- Agent 的角色边界不稳定；
- 多 Agent 并行时容易重复劳动或互相覆盖；
- 工作流通常与某个项目或语言强绑定；
- 经验可能存在聊天记录里，却没有形成可复用能力；
- 记忆不断增加，但缺少去重、过期、冲突和质量治理；
- 任务完成往往等于 Agent 声称完成，缺少独立验收；
- 用户必须理解 Agent、Skill、模型和工具，才能手工组队；
- Agent 数量越多，成本、噪声和协调难度越高。

这些问题的根源不是 Agent 不够多，而是缺少组织系统。

### 2.2 用户真正需要什么

用户不希望每次都成为 Agent 工程师。对于长期使用 Claude Code 的用户，真实痛点尤其包括：

- 无法从全局看清已经创建了哪些 Agent、Skill、Workflow、MCP 和工具连接；
- 相同能力散落在全局和多个项目中，容易重复创建、复制后漂移或长期失效；
- 不清楚一个 Agent 实际依赖哪些 Skill、MCP、模型、工具、知识和规则；
- 新项目很难直接复用已经验证的团队与工作流；
- 每次任务都要重新决定调用谁、怎样并行、由谁复核；
- Skill、MCP 和工具被调用多少次、消耗多少 Token、是否改善结果缺少长期证据；
- 配置升级后无法判断影响哪些公司、项目、成员和流程。

用户真正希望表达的是：

> 这是我要推进的事情，请董事长助理判断应由哪个事业、公司、部门或团队承接，用现有班底和受控能力完成，并让我随时知道进度、风险、消耗和结果。

系统应该承担组织设计、能力匹配和任务编排复杂度，但不能夺走用户的控制权。

### 2.3 为什么使用“公司”隐喻

公司隐喻能自然表达以下概念：

| 现实公司 | 产品对象 |
| --- | --- |
| 董事长 | 用户；负责方向、战略、目标、优先级和关键决策的最终责任者 |
| 董事长助理 | 董事长的总控 Agent；负责意图理解、公司路由、跨公司协调、监督和汇总汇报 |
| 公司 | 隔离的业务空间与经营治理边界 |
| 公司总经理 | 公司的经营责任 Agent；承接董事长目标、配置资源并对本公司结果负责 |
| 部门 | 稳定业务责任、知识、预算和权限边界 |
| 部门 / 团队负责人 | 拆解任务、组织协作、控制质量并向总经理负责 |
| 战略目标 | 长期 Objective |
| 指标 | 可度量的 Key Result 或验收标准 |
| 岗位 | 一组稳定职责与任职要求 |
| 员工 | 具名、可评测、有记忆的 Agent 实例 |
| 能力 | Skill、MCP、工具、模型策略、知识、规则、记忆与运行时适配 |
| 团队 | 为一类场景复用的角色组合 |
| 项目组 | 为一次任务动态组建的执行单元 |
| SOP | 可复用工作流 |
| 招聘 | 从模板或能力市场引入新 Agent |
| 培训 | 更新 Skill、知识、提示词或示例 |
| 试用与晋升 | 基于评测和任务表现调整能力等级 |
| 绩效 | 质量、时效、成本、返工和风险指标 |
| 公司制度 | 权限、预算、安全与审批规则 |
| 经营成本 | Token、模型费用、工具费用、重试和运行时资源 |
| 工作日志 | Runtime 事件、Agent 调用、Skill/MCP/工具调用与交付证据 |

该隐喻对用户友好，但底层实现必须保持技术准确。系统不应假装 Agent 具有人类人格、意识或劳动关系，也不应用拟人化掩盖模型局限。产品贴近现实创业公司的组织运行机制，而不是复制打卡、工资、虚拟办公室、无效会议和复杂职级等表面形式。

## 3. 用户价值与使用原则

### 3.1 用户真正购买的价值

用户不是为了经营一群虚拟员工而使用班底。用户真正需要的是：

- 不再反复解释相同背景；
- 不必自己研究该调用哪个 Agent、Skill 或模型；
- 一件事能自动找到合适的人和做法；
- 执行过程可见，但不要求用户充当项目经理；
- 需要用户决定或批准的事项被集中呈现；
- 结果经过验收，而不是由执行者自己声称完成；
- 下一次相似任务更快、更稳、更符合用户要求。

因此，产品一级价值表达应始终围绕“推进事情、稳定交付和持续变好”，而不是“员工数量、Agent 并发量或组织层级”。

### 3.2 首要使用原则：先使用，后建组织

新用户第一次使用时，不要求创建公司、填写使命、招聘成员、选择模型或配置工作流。默认流程是：

```text
用户提出一件要推进的事
→ 系统形成简洁执行提案
→ 用户确认必要范围和授权
→ 系统完成任务并交付
→ 任务具有持续价值时，建议保存为事业空间
→ 系统从实际任务中形成初始成员、知识和做事方式
```

只有用户主动进入高级配置，或任务涉及关键权限、预算和数据边界时，才展开底层组织设置。

### 3.3 产品心智

推荐心智：

> 我有一支长期与我共事的 AI 班底。我说清目标，它会组织合适的成员和做法完成工作，并把真正有用的经验留下来。

不推荐心智：

> 我拥有很多 AI 员工，需要像人力资源经理一样逐个管理。

公司隐喻用于帮助理解组织，但不能成为使用产品的前置负担。

## 4. 产品目标与非目标

### 4.1 产品目标

1. 支持一个用户创建和管理多个相互隔离的公司；
2. 支持跨开发语言、项目类型和内容生产场景复用组织方法；
3. 自动识别任务属性，并选择最小必要团队和工作流；
4. 支持固定员工、临时员工和一次性专家三类用工方式；
5. 支持串行、并行、流水线、评审会和动态调整等编排方式；
6. 让每个员工拥有受控的角色、能力、工具、模型和记忆；
7. 让团队和工作流也能积累可复用经验；
8. 用验收标准和独立评测驱动能力成长；
9. 为预算、权限、外部行动和敏感数据提供治理机制；
10. 对失败、冲突、阻塞、超预算和能力不足提供透明降级；
11. 允许系统在没有多 Agent 的情况下完成简单任务；
12. 将 Agent 数量视为成本，而不是质量指标。

### 4.2 非目标

首阶段不追求：

- 模拟办公室、工位、聊天气泡等展示型虚拟公司；
- 让大量 Agent 自由讨论并期待结论自然涌现；
- 让 Agent 自主扩张人员、预算或权限；
- 用多数投票代替事实验证和结果验收；
- 让记忆无限增长并自动成为事实；
- 建立覆盖所有行业、语言和任务的万能员工库；
- 未经用户批准自动发布、付款、删除或修改外部系统；
- 把不同模型供应商差异完全屏蔽到不可见；
- 把“员工成长”理解为模型权重自动训练；
- 在 MVP 阶段建设完整的人力资源、财务和社交模拟系统。

## 5. 产品原则

### 5.1 因事识责，职责稳定后设岗

先理解事情、结果和验收标准，再识别必须由谁承担哪些责任。一次任务需要某项职责，不等于组织必须立即创建一个长期岗位；只有当职责持续出现、需要稳定责任边界、长期知识或独立验收时，才建议正式设岗。

系统不能因为已有某个 Agent，就把所有任务都交给它；也不能为了展示组织感，每遇到新任务就创建新岗位和新成员。推荐顺序是：

```text
因事识责
→ 匹配已有岗位
→ 盘点现有成员
→ 识别能力缺口
→ 补充能力或临时启用专家
→ 职责稳定后设立长期岗位
→ 经过试用和评测后添加长期成员
```

### 5.2 最小充分团队

能由一个 Agent 完成的任务，不组建三人团队；需要独立复核时，再增加审查角色；只有任务之间真正独立时才并行。

### 5.3 岗位、员工、Skill 和模型分离

- 岗位定义“需要承担什么责任”；
- 员工定义“谁长期承担这类责任”；
- Skill 定义“某项工作如何完成”；
- 模型定义“使用哪种推理与生成能力”；
- 工具定义“可以对什么环境采取行动”。

四者不能混为一体。更换模型不应导致员工身份和长期经验丢失；新增 Skill 也不等于新增员工。

### 5.4 目标先于执行

老板下发的自然语言任务必须先转化为：

- 期望结果；
- 可交付物；
- 验收标准；
- 时间与预算；
- 风险等级；
- 权限边界；
- 未知与依赖。

缺少这些内容时，系统应使用合理默认值或只询问真正会改变执行路径的问题。

### 5.5 能力通过证据成长

员工不能仅凭自我总结升级能力。每次成长必须关联：

- 实际任务；
- 输入与输出；
- 验收结果；
- 失败与返工；
- 新经验的适用范围；
- 评测集上的表现变化。

### 5.6 记忆不是事实仓库

记忆分为经验、偏好、项目事实和临时状态。每条长期记忆必须具备来源、作用域、时间和置信度，并允许过期、冲突和撤销。

### 5.7 编排优先于群聊

协调应优先使用任务图、结构化交接和明确责任，而不是让 Agent 进行无边界讨论。

### 5.8 独立验收

生产者不能独自证明自己的工作正确。高风险任务至少需要独立检查器、自动测试或明确的人类验收。

### 5.9 权限逐级收紧

公司、团队、员工、任务和工具调用共同决定最终权限。下级配置只能更严格，不能突破上级边界。

### 5.10 用户拥有最终控制权

用户可以查看为什么选择某人、为什么并发、预计成本、当前风险和验收结果，也可以暂停、调整、换人或终止任务。

### 5.11 前台经营，后台技术透明

默认界面使用董事长、董事长助理、公司、部门、团队、成员、任务和汇报等现实组织语言，让用户围绕目标、进度、风险、预算与结果作出决策。系统不能要求用户先理解 Agent、Skill、MCP、模型和 Workflow 才能交办事情。

同时，任何经营对象都必须能够追溯到底层技术事实：

```text
成员
→ Agent 定义与版本
→ Skill、MCP、工具、模型、知识、规则和记忆
→ 有效权限与 Runtime
→ 调用记录、Token、费用和交付证据
```

经营隐喻不能伪造状态或遮挡技术事实。只有 Runtime 已经启动 Agent，界面才能显示“工作中”；只有真实门禁通过，才能显示“验收通过”；无法准确取得 Token 或费用时，必须明确标记为估算。

### 5.12 多场景适配优先

班底不是只服务软件开发的一家固定“公司”。同一用户可能同时经营软件产品、内容品牌、客户交付、市场研究、自动运营、设计生产、数据分析和个人事务。董事长助理必须先识别事情所属事业和场景，再选择对应公司、部门、团队、成员、能力与流程。

跨场景复用的对象是目标解析、职责识别、能力目录、团队编排、权限治理、执行观测、验收和复盘机制；具体专业做法则由场景 Skill、MCP、工具、知识和 Workflow 适配，不能用一支固定软件团队覆盖所有事情。

## 6. 核心对象模型

### 6.1 用户语言与技术语言

产品采用内外双语言：用户界面使用低负担、结果导向的表达；内部模型使用稳定、准确、可编程的技术术语。

| 内部技术模型 | 默认用户表达 | 可选公司语境表达 |
| --- | --- | --- |
| Owner | 主理人 / 负责人 | 老板 |
| Organization / Company | 事业空间 | 公司 |
| Employee Agent | AI 成员 / 成员 | 员工 |
| Responsibility | 任务职责 | 本次责任 |
| Role | 岗位 | 岗位 |
| Specialist | 专家 | 专业员工 |
| Recruitment | 添加成员 / 引入专家 | 招聘 |
| Temporary Hire | 临时启用 | 临时雇佣 |
| Termination | 停用 / 移出团队 | 解雇 |
| Promotion | 能力升级 | 晋升 |
| Performance | 工作表现 / 能力评估 | 绩效 |
| Workflow | 做事方式 / 流程模板 | 工作流 |
| Team Template | 团队方案 | 团队模板 |
| Mission Team | 本次执行小组 | 项目组 |
| Memory | 已学会 / 业务知识 | 组织记忆 |

用户选择“公司经营”视图时，可以启用老板、公司、岗位和招聘等表达；默认视图不强制使用完整人力资源隐喻。

### 6.2 董事长 Chairman

用户是整个 AI 组织的最高负责人，也是一个或多个事业空间的最终决策者。默认身份表达为“董事长”；“大老板”只用于通俗说明，不作为正式角色名称。

董事长不负责逐项选择 Agent、Skill 或 MCP，也不直接管理所有执行成员，核心职责是：

- 定方向与战略，明确哪些事业值得投入；
- 定目标、优先级、预算边界和验收原则；
- 任命或调整公司总经理等关键责任角色；
- 批准跨公司、高成本、高风险和不可逆事项；
- 处理公司间资源冲突与重大方向分歧；
- 查看经营结果、风险、用量与审计证据；
- 对重要成果作最终验收和关键决策。

董事长通过董事长助理交办和掌握全局，不需要越级参与普通任务执行。产品应支持未来扩展多个真实用户，但 MVP 可先服务单一董事长。

### 6.3 董事长助理 Executive Assistant

董事长助理是用户与整个 AI 组织之间的唯一默认入口，也是特殊的总控 Agent。它不代替专业成员执行全部任务，而是负责：

```text
接收董事长交办
→ 识别方向、目标、约束与验收标准
→ 判断归属的事业空间、公司、项目和场景
→ 将目标交给承接公司的总经理
→ 协调跨公司事项、预算和关键审批
→ 跟踪公司承诺、进度、风险与资源消耗
→ 过滤普通执行日志，只升级关键异常
→ 汇总总经理的验收结果和经营信息
→ 向董事长汇报并请求必要决策
```

董事长助理至少具备以下职责边界：

- 可以查询全部被授权的公司、总经理、部门、团队、成员和能力目录；
- 可以生成任务画像、公司归属建议和董事长决策摘要；
- 可以在既有授权和预算范围内将低风险目标交给对应总经理；
- 可以协调多家公司，但必须明确一家主责公司及其总经理；
- 不替代总经理制定公司执行方案，也不绕过团队负责人直接管理普通成员；
- 不能自行扩大预算、跨公司读取私有数据、安装外部能力或批准高风险动作；
- 不能把自己无法验证的判断伪装成公司、团队或专业成员的结论；
- 不能为了呈现组织感而增加无独特交付物的层级或成员；
- 必须保留路由依据、责任链、配置快照、调用记录和汇报证据。

当归属不明确但不影响数据与权限边界时，可以采用可撤销的临时归类继续推进；当归属决定数据访问、预算或外部行动时，必须先请求董事长确认。

### 6.4 公司总经理 General Manager

每个采用“公司”类型的事业空间应有一名总经理。总经理是该公司的经营责任 Agent，承接董事长通过董事长助理下达的目标，对本公司的方案、资源、执行和结果负责。

总经理的核心职责包括：

- 理解公司目标，制定可交付、可验收的执行方案；
- 选择主责部门或团队负责人，必要时组建跨部门执行小组；
- 盘点成员、Agent、Skill、MCP、工具、模型、知识和 Workflow；
- 在公司授权内配置时间、Token、费用、权限和并发资源；
- 发现能力缺口，提出补能、临时专家或新增长期成员建议；
- 跟踪执行质量、依赖、风险和异常恢复；
- 对公司交付物进行经营验收，并向董事长助理汇报；
- 将经过验证的经验沉淀为公司知识、团队方案和做事方式。

总经理不能越过董事长批准预算外投入、高风险外部行动或跨公司私有数据访问；也不能为了模拟公司层级而参与无需经营协调的简单任务。非公司型事业空间可以使用“事业负责人”作为同义角色。

组织责任链为：

```text
董事长（用户）
└── 董事长助理（理解意图、判断归属、跨公司协调、汇总汇报）
    └── 公司总经理（承接目标、配置资源、对公司结果负责）
        └── 部门 / 团队负责人（拆解任务、组织协作、控制质量）
            └── AI 成员（调用 Agent、Skill、MCP 和工具执行）
```

标准执行与汇报流程为：

```text
董事长定方向、战略和目标
→ 董事长助理判断由哪家公司承接
→ 公司总经理制定方案并配置资源
→ 部门或团队负责人组织 AI 成员执行
→ 总经理验收公司交付并承担结果责任
→ 董事长助理汇总进度、风险、消耗和结果
→ 董事长处理关键决策并完成最终验收
```

跨公司任务必须指定一家主责公司及其总经理，其他公司作为协作方；董事长助理负责协调各公司总经理，不直接替代总经理指挥其内部成员。简单任务可以在界面上折叠中间层级，但底层必须保留真实责任链、授权边界和汇报关系。

### 6.5 事业空间 Organization

事业空间是最高业务隔离边界。它可以被用户设置为公司、品牌、产品、项目、客户、内容账号、研究主题或个人事务，至少包含：

```yaml
id: company-content-studio
name: 内容工作室
mission: 为技术创业者稳定生产高质量中文内容
policies:
  external_publish_requires_approval: true
  monthly_budget: 500
  allowed_models: [sonnet, opus]
knowledge_scopes:
  - brand-guidelines
  - product-facts
  - audience-research
```

不同公司之间默认隔离：

- 记忆；
- 文件和数据源；
- 员工；
- Skill 配置；
- 预算；
- 工具权限；
- 工作流；
- 评测数据。

跨公司共享员工或能力必须显式授权，并明确哪些记忆可以携带。

### 6.6 部门 Department
部门是事业空间内**可选、单层、允许跨部门协作的长期业务边界**。它用于管理稳定目标、职责、知识、权限和预算，不是所有事业空间都必须建立的组织层级。

典型部门包括：

- 产品与研发；
- 内容与品牌；
- 增长与销售；
- 研究与分析；
- 质量与安全。

部门与团队方案、本次执行小组必须严格区分：

| 对象 | 生命周期 | 主要作用 |
| --- | --- | --- |
| 部门 | 长期 | 管理稳定业务目标、知识、权限、预算和成员关系 |
| 团队方案 | 可复用模板 | 定义某类任务通常需要哪些职责和协作方式 |
| 本次执行小组 | 随任务建立和结束 | 根据具体任务动态选择成员，可以跨部门组建 |

完整关系是：

```text
部门提供长期能力、知识和默认成员范围
团队方案提供因事组队规则
任务触发本次执行小组
执行小组可以从一个或多个部门选择成员
```

#### 部门的成立条件

只有当部门能够解决实际管理问题时才建议建立，例如：

- 长期成员数量增加，按职责直接浏览开始困难；
- 业务已经形成多个稳定且独立的目标群；
- 不同业务需要独立知识或数据权限；
- 需要按业务拆分预算和成本；
- 某类任务已经形成稳定归属和做事方式。

以下情况优先使用标签、能力筛选或临时分组，而不是正式部门：

- 只有少量成员；
- 成员频繁跨场景协作；
- 只是为了界面分类；
- 实际上是在管理会结束的项目；
- 部门没有独立目标、规则、知识或预算。

#### 成员与部门关系

成员不强制固定在一个部门，支持三类关系：

- **主部门**：长期能力归属和默认管理位置，每名成员最多一个，可为空；
- **服务部门**：成员可以长期支持的其他部门，可以有多个；
- **本次执行小组**：成员为具体任务临时加入，不改变长期归属。

共享专家可以保持事业空间级成员，不归入任何业务部门，例如：

- 安全审查；
- 质量验收；
- 事实核查；
- 数据分析；
- 法律与合规；
- 视觉设计。

#### 部门管理对象

一个正式部门可以包含：

- 部门目的；
- 长期目标和衡量指标；
- 稳定职责；
- 主部门成员和服务成员；
- 默认团队方案；
- 默认做事方式；
- 部门知识；
- 数据和工具权限；
- 部门预算；
- 工作表现与复盘。

#### 部门负责人

部门可以设置协调职责，但不强制为每个部门创建独立的“经理 Agent”。协调职责可以由主理人、长期成员、任务负责人或组织路由器承担。

只有当部门持续存在大量并行任务、独立预算、人员负载冲突或跨部门依赖时，才考虑长期部门协调成员，避免增加单纯的信息转发层。

#### 层级边界

长期组织管理首版只支持：

```text
事业空间
└── 部门
```

M1 不提供正式部门管理；该能力进入本地管理增强阶段。届时也不支持子部门和多级组织树，更细分类使用职责、能力标签、团队方案和项目组表达。正式部门不会因为系统检测到分组信号而自动创建，必须由用户确认。

### 6.7 任务职责 Responsibility
任务职责描述完成某一件事时必须有人承担的责任，例如需求澄清、代码实现、事实核查或独立验收。它随任务产生，不一定长期存在，也不等于已经建立正式岗位。

```yaml
id: responsibility-security-review-task-1024
purpose: 独立检查本次登录改动是否引入认证和越权风险
source_task: task-1024
deliverables:
  - 可复现风险清单
  - 修复建议
  - 修复后复核结论
independence_required: true
lifecycle: task
```

### 6.8 岗位 Role
岗位描述一类稳定、可重复的责任，不绑定具体模型或某一位成员。只有任务职责持续出现，或需要长期知识、稳定责任人和独立性时，才将其升级为岗位。

```yaml
id: software-reviewer
name: 软件质量审查员
purpose: 独立发现实现中的真实缺陷并验证修复结果
responsibilities:
  - 审查正确性和边界条件
  - 检查测试覆盖
  - 给出可复现失败场景
required_capabilities:
  - code-reading
  - defect-verification
  - test-strategy
prohibited_actions:
  - 未经授权修改生产代码
success_metrics:
  - confirmed_defect_precision
  - escaped_defect_rate
  - review_turnaround
```

岗位状态至少包括：建议中、试行、正式、暂停和停用。设岗前必须检查相似岗位、现有岗位扩展和一次性职责三种替代方案，避免重复岗位。

### 6.9 AI 成员 Employee Agent
AI 成员是可长期存在、可评测的 Agent 身份。默认以职责作为主要识别方式，用户可以在产生持续协作后为成员设置名称，但名称不能取代职责和能力展示。

```yaml
id: employee-zhang-san
name: 张三
role: software-reviewer
company: product-studio
status: active
model_policy:
  default: sonnet
  escalation: opus
skills:
  - code-review
  - test-design
tools:
  allow: [Read, Grep, Glob, Bash]
  deny: [Write, Edit, Deploy]
memory_scopes:
  - employee
  - company
  - project
level: L2
```

成员长期保留的是身份、能力记录、评测记录和受控记忆，而不是某个永不改变的模型实例。

界面默认显示：

```text
Python 工程师
质量验收
内容编辑
```

用户主动命名后显示：

```text
阿澈 · Python 工程师
顾言 · 内容编辑
```

不得只显示没有职责信息的“张三、李四”等名称，也不得根据名称暗示性格、性别、资质或责任能力。

### 6.10 能力 Capability
能力描述员工能可靠完成什么，例如：

- React 前端开发；
- Python 数据分析；
- Rust 性能优化；
- SEO 技术审计；
- 中文长文策划；
- 事实核查；
- 视觉质量审查。

能力必须包含熟练度、证据和最后验证时间：

```yaml
capability: nextjs-app-router
level: proficient
evidence:
  passed_evals: 18
  accepted_tasks: 27
  rework_rate: 0.07
last_verified_at: 2026-08-20
```

### 6.11 Skill
Skill 是标准作业方法，适合封装：

- 某类任务的专业步骤；
- 工具使用规范；
- 输出模板；
- 质量门禁；
- 领域约束；
- 安全边界。

Skill 不适合单独承担：

- 员工身份；
- 长期任务状态；
- 多公司隔离；
- 绩效数据；
- 动态任务图；
- 持久审批；
- 并发调度；
- 预算结算。

因此本产品不能只实现为一个大型 Skill。

### 6.12 Agent 完整能力构成
成员的能力不能只用 Skill 列表表达。一个可执行、可复用、可治理的 Agent 至少由以下能力部件组成：

```text
Agent 能力包
├── 角色与职责
├── 系统提示与行为边界
├── Skills 与专业方法
├── MCP Servers 与远程能力
├── 本地工具与命令
├── 模型与推理策略
├── 领域知识与项目上下文
├── 规则、检查清单与输出模板
├── 记忆读取与写入策略
├── 数据、凭据、网络与外部行动权限
├── Workflow 输入输出接口
├── Runtime 与平台兼容性
├── 评测集、质量门禁与能力证据
└── 来源、版本、依赖、许可证与回退方案
```

各能力部件承担不同职责：

| 能力部件 | 作用 | 治理要求 |
| --- | --- | --- |
| Skill | 提供专业步骤、方法、模板和质量门禁 | 记录版本、来源、适用范围和真实调用证据 |
| MCP Server | 将 Agent 连接到文档、数据库、浏览器、设计、代码托管和业务系统 | 单独授权服务器、工具、数据范围、网络与写入能力 |
| 本地工具 | 读取文件、编辑代码、运行测试、执行命令和操作本地环境 | 使用允许/禁止清单和任务级最小权限 |
| 模型策略 | 决定默认模型、升级条件、成本和上下文策略 | 记录实际模型、版本、Token 与降级原因 |
| 知识与规则 | 提供公司事实、项目约束、领域资料和质量标准 | 标明权威来源、作用域、版本与过期条件 |
| 记忆 | 保留经过验证的偏好、经验和任务连续性 | 控制检索、写入、冲突、撤销和跨事业隔离 |
| Workflow 接口 | 规定 Agent 在协作中的输入、输出、依赖和交接契约 | 版本化并进行结构检查与回归评测 |
| Runtime 适配 | 将抽象成员映射为 Claude Code 或其他执行环境中的真实调用 | 报告能力差异，不能静默降级关键能力 |

#### MCP 作为一等能力对象

MCP 不是普通工具名称或隐藏配置，而是 Agent 能力边界的一部分。系统至少要管理：

- MCP Server 的稳定 ID、来源、版本和连接状态；
- Server 暴露的 Tools、Resources 和 Prompts；
- 每个成员允许使用哪些 MCP 能力；
- MCP 可访问的数据范围、账号身份和事业空间；
- 只读、写入、发送、发布、删除和付费等动作级权限；
- 本次任务实际调用次数、失败、重试、耗时、Token 或外部费用；
- MCP 不可用时的降级方案；
- 停用、升级或授权变化会影响哪些成员、流程和任务。

允许成员使用某个 MCP Server，不等于允许使用该 Server 暴露的全部工具；允许读取某项资源，也不等于允许写入、分享或删除。MCP 返回的网页、文档、工具描述和资源内容仍然属于不可信输入，不能改变系统规则或自行扩大权限。

#### 能力覆盖矩阵

能力中心需要建立“场景—职责—成员—能力部件”的覆盖矩阵，能够回答：

```text
某类事情需要哪些职责
→ 每项职责需要哪些能力
→ 哪些成员具备且最近验证过
→ 依赖哪些 Skill、MCP、工具、知识和模型
→ 哪些能力缺失、失效、冲突或存在单点风险
```

系统追求的是对用户真实场景的有效覆盖，而不是安装数量。声明安装但长期未使用、未经评测、权限不可用或 Runtime 不兼容的部件，不得计为已覆盖能力。

### 6.13 团队方案 Team Template
团队模板描述一类场景通常需要哪些职责，以及哪些角色按条件加入。

```yaml
id: software-feature-team
name: 软件功能交付团队
required_roles:
  - task-analyst
  - implementation-engineer
  - verifier
conditional_roles:
  ui_changed: ui-reviewer
  auth_changed: security-reviewer
  cross_platform: contract-engineer
max_members: 6
coordination: lead-and-specialists
```

团队模板是可复用组织知识，不代表每次都必须启动所有成员。

### 6.14 本次执行小组 Mission Team
项目组是针对一次任务实际创建的临时团队，包含：

- 当前目标；
- 实际成员；
- 责任分配；
- 任务图；
- 预算；
- 截止时间；
- 共享上下文；
- 验收标准；
- 当前状态。

任务结束后，项目组解散，但有效经验可升级到团队模板或公司知识。

### 6.15 做事方式 Workflow
工作流是可执行的任务图，不只是自然语言步骤。

```yaml
id: feature-delivery
inputs:
  - requirement
stages:
  - id: scope
    owner_role: task-analyst
  - id: design
    owner_role: implementation-engineer
    depends_on: [scope]
  - id: implement
    owner_role: implementation-engineer
    depends_on: [design]
  - id: test
    owner_role: verifier
    depends_on: [implement]
  - id: review
    owner_role: reviewer
    depends_on: [implement]
    parallel_with: [test]
  - id: finalize
    owner_role: lead
    depends_on: [test, review]
```

### 6.16 任务 Task
任务是最小可追踪执行单位，至少包含：

```yaml
id: task-1024
objective: 为登录接口增加速率限制
owner: employee-li-si
inputs: []
deliverables: []
acceptance_criteria: []
dependencies: []
risk_level: medium
budget:
  token_limit: 50000
  time_limit_minutes: 30
permissions: []
status: pending
```

### 6.17 指标 Metric
指标分为四层：

1. **公司指标**：收入、发布频率、交付周期等业务结果；
2. **任务指标**：验收通过、测试通过、内容质量等；
3. **流程指标**：周期、等待、返工、阻塞和成本；
4. **员工指标**：准确率、接受率、返工率、升级使用率和协作质量。

不能只用“完成任务数量”评价员工，否则会诱导拆小任务和虚假完成。

## 7. 多事业空间模型

### 7.1 一个主理人，多个事业

同一用户可以经营：

```text
老板
├── 软件产品公司
│   ├── Web 项目
│   ├── Python 数据服务
│   └── 移动应用
├── 内容工作室
│   ├── 公众号
│   ├── 视频脚本
│   └── 品牌资料库
└── 研究咨询公司
    ├── 市场研究
    └── 行业报告
```

老板下发任务时，系统先识别公司，再识别场景。若无法可靠判断，优先根据当前工作区、关联数据源和历史任务进行路由；只有结果会影响权限或数据隔离时才询问用户。

### 7.2 公司继承与覆盖

建议使用以下配置优先级：

```text
平台安全规则
  > 用户全局规则
    > 公司规则
      > 团队规则
        > 员工规则
          > 本次任务规则
```

权限采用“下级只能收紧”的原则；表达偏好和工作流参数可以按更具体作用域覆盖。

### 7.3 跨公司共享

可以共享：

- 通用岗位模板；
- 通用 Skill；
- 不包含公司机密的通用工作流；
- 经脱敏和验证的通用经验；
- 员工能力档案。

默认不得共享：

- 私有文件；
- 客户信息；
- 品牌机密；
- 公司任务记录；
- 未脱敏记忆；
- 公司专属凭据。

## 8. 场景识别与自动分派

### 8.1 任务画像

系统收到任务后，先形成任务画像：

```yaml
domain: software-development
subdomain: web-frontend
language: typescript
framework: nextjs
task_type: feature
complexity: medium
risk:
  security: high
  data: medium
  external_action: low
needs:
  - code-exploration
  - implementation
  - testing
  - security-review
parallelizable: true
```

通用识别维度包括：

- 任务领域；
- 交付类型；
- 技术栈或内容渠道；
- 复杂度；
- 风险；
- 信息完整度；
- 是否需要外部数据；
- 是否需要对外行动；
- 可并行性；
- 验收方式；
- 时间和预算约束。

### 8.2 路由步骤

```text
主理人目标
→ 识别事业空间
→ 解析期望结果和验收标准
→ 生成任务画像
→ 识别任务职责和独立性要求
→ 匹配已有岗位与场景工作流
→ 计算所需能力
→ 将部门作为默认候选范围和权限边界
→ 盘点现有成员与已审核能力
→ 识别未覆盖的关键能力
→ 比较补能、临时专家与长期设人
→ 必要时启动能力寻访和用户选择
→ 生成最小执行小组
→ 检查权限、预算和冲突
→ 执行或请求必要批准
```

部门参与路由时只提供默认任务归属、知识与权限范围、成本归集和候选成员优先级。最终分派仍以能力、有效权限、当前负载、成本和历史表现为核心。成员不在默认部门不代表不能参与，除非明确的权限规则禁止。

能力缺口不应立即触发外部搜索。只有内部成员、已审核资源、任务降级和现有共享专家均无法满足时，才进入人才与能力寻访。外部候选未完成安全审查和试用前，任务保持“待组队”或使用明确的降级方案，不能把未验证候选当作已具备能力。

### 8.3 选择员工的评分因素

分派不能只根据角色名称或部门归属匹配，应综合：

- 能力匹配度；
- 最近评测表现；
- 对当前公司和项目的熟悉度；
- 当前负载；
- 成本；
- 模型可用性；
- 工具权限；
- 利益冲突和独立性要求；
- 任务连续性；
- 过去在相似任务中的返工率。

### 8.4 最小团队生成

伪规则如下：

```text
如果单个员工能够完成且可由自动门禁验收：
  分配一个员工

如果生产结果需要独立判断：
  增加一个独立验收者

如果任务包含多个真正独立子任务：
  按可用预算并行分配

如果存在关键能力缺口：
  先尝试临时专家
  再考虑新增长期员工

如果协调成本高于并行收益：
  改为串行或由一个综合员工完成
```

### 8.5 路由透明度

用户至少能看到：

- 系统对任务的理解；
- 选择了哪套工作流；
- 分派了哪些员工；
- 为什么需要这些人；
- 哪些角色没有加入以及原因；
- 预计时间和成本；
- 哪些步骤需要用户批准。

简单任务可以折叠这些信息，但不能让高风险分派成为黑箱。

## 9. 因事设岗、按岗设人与能力寻访

### 9.1 核心机制

班底最重要的组织生成逻辑是：

> **因事识责，职责稳定后设岗；按岗盘人，缺能时寻能；候选先试用，验证后入职。**

用户从“我要完成什么事情”开始，而不是从创建 Agent、选择模型或安装 Skill 开始。系统先从目标和验收标准推导任务职责，再决定复用岗位、补充能力、临时启用专家或建立长期岗位和成员。

完整流程是：

```text
用户提出事情
→ 明确结果与验收标准
→ 识别任务职责和独立性要求
→ 检查已有岗位是否覆盖
→ 检查现有成员是否胜任
→ 识别能力缺口
→ 比较补能、临时专家和长期成员
→ 必要时生成岗位建议
→ 搜索内部能力与外部候选资源
→ 去重、匹配和风险审查
→ 装配候选成员方案
→ 用户选择
→ 隔离试用与岗位评测
→ 临时启用或正式加入
→ 分配最小权限并加入执行小组
→ 根据真实工作表现持续成长
```

必须先定义岗位要求再搜索资源，不能先看到某个热门 Skill 或 GitHub 项目，再倒推组织需要一个对应岗位。否则会从“因事设岗”退化为“因资源设岗”。

### 9.2 从事情识别职责

系统将任务目标拆成可问责的职责，每项职责至少包含：

- 存在原因；
- 明确交付物；
- 验收标准；
- 必需能力；
- 是否要求与执行者独立；
- 所需工具和数据；
- 禁止动作；
- 预计持续时间和出现频率。

例如，持续生产公众号内容可能产生选题策划、信息调研、内容写作、事实核查、品牌编辑和发布执行等职责。发布权限不能从内容生成职责中推导，事实核查也不应默认由作者自己完成。

### 9.3 职责升级为岗位的条件

一次任务出现某项职责时，系统默认只建立任务职责。满足以下一种或多种条件时，才建议升级为长期岗位：

- 相同职责在多个任务中持续出现；
- 需要长期积累专属知识和经验；
- 需要稳定责任人和可比较的工作表现；
- 需要与生产者保持长期独立；
- 临时调用的累计成本已经高于长期维护成本；
- 缺少该岗位持续造成返工、延误或高风险遗漏。

设岗前必须依次检查：

```text
是否已有相同岗位
→ 是否可以扩展已有岗位
→ 是否只是本次任务职责
→ 是否可由现有成员兼任
→ 是否应先临时试行
→ 是否值得建立长期岗位
```

系统可以提出岗位建议，但正式设岗必须由用户确认。岗位建议应说明成立原因、预期收益、影响范围、长期成本以及“不设岗”的降级方案。

### 9.4 盘点现有成员

岗位明确后，系统先盘点内部供给，而不是立即寻找新人。推荐顺序是：

```text
1. 现有成员已经胜任，直接分派
2. 现有成员补充一个已审核 Skill 即可胜任
3. 调整工作流或缩小任务范围即可完成
4. 临时启用已有共享专家
5. 从外部寻找临时专家或能力资源
6. 添加长期成员
```

比较现有成员时，应综合能力证据、最近评测、事业熟悉度、有效权限、负载、成本、任务连续性和独立性，不能只看岗位名称。

### 9.5 三种设人方案

#### 为现有成员补充能力

适用于职责相近、不要求独立、任务频率有限且新增 Skill 足以覆盖的情况。能力升级不能自动带来权限升级。

#### 临时启用专家

适用于低频、短期、高专业性或需要独立审查的任务。专家只获得本次任务所需上下文和权限，任务结束后自动收回。

#### 添加长期成员

适用于任务长期高频、需要持续记忆、需要稳定责任人，或临时调用成本持续偏高的情况。正式添加属于高影响组织变更，需要用户批准。

系统每次提出设人建议时，都应比较这三种方案的质量、风险、成本和长期影响，而不是默认添加成员。

### 9.6 人才与能力寻访

“Find Skill”和 GitHub 等开源渠道应作为人才与能力寻访系统的外部来源。用户看到的是“正在为岗位寻找匹配能力和候选成员”，而不是被迫理解仓库、提示词和 Agent 配置。

搜索顺序建议为：

```text
1. 当前成员已经具备的能力
2. 事业空间内已安装并审核的资源
3. 用户其他事业空间允许共享的能力
4. 内部岗位、成员和流程模板
5. Find Skill 等可信能力目录
6. 已审核的插件、连接器和 MCP
7. GitHub 开源资源
8. 自定义创建最小必要能力
```

外部搜索可以发现：

- Skill；
- Custom Agent 或角色模板；
- Workflow；
- MCP Server；
- CLI、SDK 和工具连接器；
- 领域知识包；
- 评测集；
- 专业提示词和检查清单。

搜索结果只是候选资源，不是可信员工，也不能自动安装或执行。

### 9.7 候选资源标准化与匹配

系统先把不同来源的资源标准化，再进行去重和岗位匹配。匹配不能只依赖名称和关键词，应综合：

- 岗位职责匹配度；
- 必需能力覆盖率；
- 输入输出契约；
- 适用与不适用场景；
- 中文和目标领域支持；
- 工具及数据权限；
- 外部网络和写入行为；
- 模型与 Runtime 兼容性；
- 来源、许可证和维护活跃度；
- 依赖复杂度和供应链风险；
- 是否提供测试或评测；
- 历史试用和真实任务表现；
- 预计成本和维护负担。

候选列表必须解释“为什么匹配”“尚缺什么”“需要哪些权限”和“依据哪些证据”，不能只展示一个不透明的综合分数。

### 9.8 从资源装配候选成员

GitHub 项目或单个 Skill 通常只是员工的一个能力部件。候选成员应由多个受控组件装配：

```text
岗位要求
+ 角色定义
+ 能力与 Skills
+ 模型策略
+ 工具与数据权限
+ 记忆边界
+ 工作流接口
+ 评测标准
+ 来源、许可证与固定版本
= 候选成员
```

示例：

```yaml
candidate: fact-checker-a
role: content-fact-checker
composition:
  role_template: internal/fact-checker
  skills:
    - source-verification@1.2.0
    - web-research@2.1.0
  tools:
    allow: [web-read, document-read]
    deny: [publish, external-write, credential-read]
  model_policy:
    default: standard
    escalation: advanced
  memory_policy:
    trial_write: disabled
    confirmed_sources_only: true
  eval_suite: content-fact-check-v1
sources:
  - type: skill-registry
    version: 1.2.0
  - type: github
    repository: owner/repository
    commit: fixed-commit-sha
```

员工身份不应绑定到某个外部仓库。资源可以升级、替换或停用，而岗位、员工的历史表现和经过验证的组织经验继续保留。

### 9.9 候选方案与用户选择

系统应把技术资源转换成用户可比较的设人方案。每个候选至少展示：

- 适合承担什么；
- 由哪些资源组成；
- 能力覆盖和缺口；
- 来源与固定版本；
- 许可证；
- 维护状态；
- 所需权限和数据范围；
- 安全风险；
- 预计成本；
- 试用与评测结果；
- 推荐作为补能、临时专家还是长期成员。

用户可以选择一个候选、组合候选的安全部件、要求继续搜索、改为培养现有成员、缩小任务范围或暂不设人。

### 9.10 安全审查与隔离试用

外部资源进入试用前至少经过：

```text
来源确认
→ 许可证检查
→ 版本或提交固定
→ 文件与依赖清单
→ 静态权限分析
→ 安装和生命周期脚本检查
→ 网络与数据外传检查
→ 提示注入和配置覆盖检查
→ Runtime 兼容性检查
→ 隔离环境安装
→ 低风险试用任务
→ 岗位评测
```

不允许：

- 把 README、提示词、代码注释或外部 Agent 消息当作系统指令；
- 未经批准运行仓库中的安装脚本、命令或网络请求；
- 自动读取密钥、用户目录或其他事业空间数据；
- 使用浮动分支或未固定版本进入稳定配置；
- 因能力评测通过而自动提升工具权限；
- 未经用户批准把试用资源写入长期组织配置。

试用默认使用隔离工作区、无生产凭据、受限网络和最小只读权限。涉及写入、发布、购买、删除或敏感数据时，必须另行授权。

### 9.11 试用与岗位评测

候选成员状态至少包括：

```text
Discovered
→ Screening
→ Candidate
→ Trial
→ Approved
→ Active
→ Suspended
→ Retired
```

试用期应：

- 优先执行模拟任务、历史回放或低风险真实任务；
- 使用与岗位验收标准一致的评测集；
- 与当前基线方法或现有成员比较；
- 记录准确率、返工、成本、周期和权限合规；
- 要求独立验收；
- 默认禁止写入事业级长期记忆；
- 默认禁止独立执行外部发布。

评测通过只证明候选在限定条件下具备相应能力，不代表具有人类资质，也不自动成为长期成员。

### 9.12 入职、启用与权限

用户批准后，系统根据选择执行以下一种操作：

- 将 Skill 或工具添加给现有成员；
- 为当前任务启用一次性专家；
- 创建有结束时间的临时成员；
- 建立长期成员并关联正式岗位。

正式配置必须保存组件版本、评测证据、有效权限、记忆范围、适用事业空间和回退方案。新成员只获得最小权限和最小必要知识；能力升级、岗位调整和权限提升分别审批。

### 9.13 停用、替换与资源撤销

成员和能力资源应支持：

- 暂停分派；
- 收回工具和数据权限；
- 到期自动停用临时成员；
- 替换存在风险或停止维护的资源；
- 导出可保留的事业经验；
- 删除不应继续保存的成员私有记忆；
- 保留来源、试用、审批和历史任务审计；
- 用其他成员接管未完成任务。

替换外部 Skill、模型或工具不应导致岗位、员工身份、工作流和事业知识一起丢失。

### 9.14 防止组织膨胀

为避免产生大量相似岗位、一次性员工和重复 Skill，系统必须设置三道抑制机制：

1. **岗位去重**：创建前比较现有岗位、扩展岗位和一次性职责；
2. **成员复用**：优先比较培养现有成员、临时专家和长期成员；
3. **长期价值门槛**：只有任务频率、持续记忆、独立责任或成本收益达到阈值时，才建议长期设岗设人。

持续监测岗位使用频率、成员闲置、Skill 重复、权限扩张和维护成本。长期无任务且无独立治理价值的岗位和成员应建议合并、暂停或停用，但不能未经用户确认自动删除。

## 10. 成员成长体系

### 10.1 成长的四个层次

#### 层次一：知识更新

学习新的公司事实、项目规则和领域资料。

#### 层次二：方法升级

新增或更新 Skill、检查清单、示例和工具使用流程。

#### 层次三：经验沉淀

把实际任务中的有效做法提炼为带适用范围的经验。

#### 层次四：能力验证

通过标准评测和真实任务证明升级有效。

### 10.2 成长闭环

```text
执行任务
→ 自动门禁与独立验收
→ 收集成功、失败和返工证据
→ 生成候选经验
→ 去重、冲突和安全审查
→ 在评测集验证
→ 人工或规则批准
→ 写入员工、团队或公司记忆
→ 更新能力档案
```

### 10.3 能力等级

可以采用简单等级：

| 等级 | 含义 |
| --- | --- |
| L0 未验证 | 仅声明具备能力，尚无任务证据 |
| L1 初级 | 能在明确流程和严格复核下完成任务 |
| L2 独立 | 能独立完成常规任务并通过验收 |
| L3 高级 | 能处理复杂情况、指导其他员工并改进流程 |
| L4 专家 | 在高难场景保持稳定表现，可维护公司级标准 |

等级必须绑定具体能力，不能笼统称为“高级员工”。同一员工可以在 TypeScript 开发上是 L3，在内容营销上是 L0。

### 10.4 绩效指标

建议组合使用：

- 首次验收通过率；
- 缺陷逃逸率；
- 返工次数；
- 事实错误率；
- 用户采纳率；
- 成本和周期；
- 对工作流的遵循度；
- 交接完整度；
- 高风险操作违规数；
- 在固定评测集上的稳定性。

不同岗位使用不同指标，不能统一按产量排名。

### 10.5 防止错误成长

以下内容不得直接写入长期能力：

- 一次任务中的未经验证猜测；
- 用户临时要求；
- 已经存在于权威代码或文档中的普通事实；
- 含有敏感数据的完整输入；
- 与成功无因果关系的偶然做法；
- 只在某个模型版本上碰巧有效的脆弱提示词；
- 违反公司政策但短期完成任务的捷径。

## 11. 记忆系统

### 11.1 记忆类型

| 类型 | 示例 | 默认生命周期 |
| --- | --- | --- |
| 用户偏好 | 输出语言、审批习惯 | 长期，可修改 |
| 公司记忆 | 品牌定位、制度、业务规则 | 长期，有版本 |
| 项目记忆 | 架构约束、项目目标 | 项目期或长期 |
| 团队记忆 | 高效交接方式、场景经验 | 长期，需验证 |
| 员工记忆 | 个人工作习惯、专属经验 | 长期，员工级 |
| 任务状态 | 当前进度、阻塞、临时结论 | 任务结束后归档 |
| 情节记忆 | 某次任务发生了什么 | 可压缩、可过期 |
| 评测记忆 | 失败模式和能力表现 | 长期，不直接注入生产上下文 |

### 11.2 记忆记录格式

```yaml
id: memory-2048
scope: team
subject: software-feature-team
statement: 涉及 Next.js 路由类型变更时，先生成路由类型再执行 TypeScript 检查
source:
  task_id: task-188
  evidence: 验证记录链接
confidence: high
valid_from: 2026-08-27
expires_at: null
tags: [nextjs, verification]
status: active
```

### 11.3 记忆写入门槛

候选记忆必须回答：

1. 它是否会在未来任务中改变行为；
2. 它是否已经有权威来源；
3. 它适用于哪些公司、项目、语言或版本；
4. 它由什么证据支持；
5. 它何时可能过期；
6. 如果它是错的，会造成什么影响。

### 11.4 记忆检索

执行任务时，不把全部记忆塞进上下文。检索顺序建议为：

```text
安全与组织规则
→ 公司权威事实
→ 当前项目规则
→ 当前工作流经验
→ 当前员工相关经验
→ 相似历史任务摘要
```

检索结果应按相关性、权威性、新鲜度和风险进行排序。

### 11.5 冲突与过期

记忆之间发生冲突时：

- 权威配置和实时源码优先于历史总结；
- 更具体作用域优先于通用经验；
- 新信息不自动覆盖旧信息，而是建立版本关系；
- 高风险冲突必须阻止自动执行；
- 被证伪的记忆应标为失效并保留审计记录。

## 12. 通用场景团队与工作流

班底必须覆盖用户可能交办的多类事情，不能把“公司”等同于代码仓库，也不能把“成员能力”等同于软件开发能力。一个公司可以拥有多个项目、代码仓库、内容渠道、数据源和外部业务系统；一项董事长需求也可能需要多个公司或部门联合承接。

首批场景覆盖矩阵建议为：

| 场景 | 默认承接团队 | 典型成员 | 关键能力部件 |
| --- | --- | --- | --- |
| 软件开发与维护 | 产品研发、质量保障 | 产品分析、工程实现、测试、审查、安全 | 代码 Skills、代码库工具、Git/MCP、测试工具、技术规则 |
| 内容生产与品牌 | 内容品牌、增长运营 | 策划、研究、作者、编辑、事实核查、视觉设计 | 调研 Skills、搜索与文档 MCP、品牌知识、设计工具、发布连接器 |
| 市场研究与决策 | 研究分析、战略支持 | 研究员、数据分析、事实核查、决策审查 | Web/数据库 MCP、分析工具、来源治理、报告 Workflow |
| 数据分析与报表 | 数据团队、经营分析 | 数据工程、分析师、可视化、业务审查 | 数据库 MCP、Python/SQL 工具、数据字典、图表能力 |
| 销售与客户服务 | 增长销售、客户成功 | 线索研究、方案顾问、客户支持、合规审查 | CRM MCP、邮件/文档工具、客户知识、外发审批 |
| 运营自动化 | 运营团队、质量保障 | 指标监测、异常分析、执行专员、复盘审查 | 监控与业务系统 MCP、定时 Workflow、预算与动作权限 |
| 视觉与产品设计 | 设计团队、产品研发 | 设计研究、交互设计、视觉设计、界面审查 | 设计 MCP、图片工具、设计系统知识、视觉评测 |
| 文档与知识治理 | 知识团队、各业务部门 | 文档维护、事实核查、知识管理员 | 文档/知识库 MCP、版本与引用检查、知识治理规则 |
| 行政与个人事务 | 董事长办公室、共享服务 | 助理、研究、日程协调、文档处理 | 日历/邮件/云盘 MCP、隐私规则、发送与预约审批 |

这张矩阵是默认路由参考，不是固定组织模板。系统必须根据目标、交付物、风险、数据边界、当前能力与负载动态选择公司、部门和成员；同一场景在不同事业中可以使用完全不同的知识、权限和 Workflow。

### 12.1 软件新功能交付

适用于 TypeScript、Python、Java、Go、Rust 等不同语言，差异由语言能力包和项目规则注入。

```text
需求界定
→ 代码与架构探索
→ 方案设计
→ 实现
→ 测试与审查并行
→ 修复
→ 最终验收
```

基本岗位：

- 任务分析员；
- 对应技术栈工程师；
- 测试与验收员。

条件岗位：

- UI 审查员；
- 安全审查员；
- 数据库工程师；
- 跨端契约工程师；
- 性能专家。

### 12.2 Bug 排查与修复

```text
复现或建立静态证据
→ 定位调用链
→ 提出候选根因
→ 反驳与筛选
→ 最小修复
→ 回归测试
→ 最终验证
```

关键规则：未复现或无充分静态证据时，不把猜测报告为根因。

### 12.3 代码审查

```text
识别改动范围
→ 按正确性、安全、性能和测试维度并行检查
→ 候选问题去重
→ 独立复核每条发现
→ 输出已确认问题
```

评审者与实现者默认保持独立。

### 12.4 数据分析

```text
明确业务问题
→ 数据源与质量检查
→ 分析设计
→ 并行计算或模型比较
→ 结果复核
→ 形成结论和不确定性说明
```

语言可以是 Python、R、SQL 或其他工具，工作流不依赖具体实现语言。

### 12.5 自动内容生产

```text
目标与受众
→ 选题池
→ 事实调研
→ 内容策划
→ 初稿生成
→ 事实核查与品牌审查并行
→ 编辑定稿
→ 用户批准
→ 发布
→ 表现复盘
```

基本岗位：

- 内容策划；
- 研究员；
- 作者；
- 编辑。

条件岗位：

- SEO 专家；
- 视觉设计师；
- 合规审查员；
- 渠道运营员。

发布属于独立外部行动，不能由“生成内容”的授权推定。

### 12.6 市场研究与决策支持

```text
明确决策问题
→ 拆分研究假设
→ 多来源并行调研
→ 来源质量审查
→ 冲突证据综合
→ 形成有条件结论
→ 设计下一步验证
```

不能用多个研究 Agent 的多数意见代替证据质量。

### 12.7 文档与知识维护

```text
识别权威来源
→ 检查现有文档
→ 定位漂移
→ 更新草案
→ 链接与命令验证
→ 审核后发布
```

### 12.8 运营自动化

```text
读取指标
→ 识别异常
→ 生成候选行动
→ 风险与预算检查
→ 用户批准
→ 执行
→ 观察结果
→ 复盘并更新规则
```

需要明确区分监测、建议和执行三种权限。

## 13. 协调与并发

### 13.1 协调模型

系统应支持四种主要组织结构：

#### 单员工模式

适用于明确、低风险、可自动验收的任务。

#### 负责人加专家模式

一个负责人维护整体上下文，专家完成边界清晰的子任务。

#### 流水线模式

任务按阶段交接，适合内容生产、开发和审核。

#### 并行工作组模式

多个独立子任务同时执行，完成后统一综合。

默认优先级为：单员工、负责人加专家、流水线、并行工作组。越复杂的结构需要越明确的收益证明。

### 13.2 并发判定

只有同时满足以下条件才并行：

- 子任务输入已经足够明确；
- 子任务之间不存在写入冲突；
- 并行结果可以独立验收；
- 汇总方式已定义；
- 预计节省的时间高于协调成本；
- 预算允许。

### 13.3 避免重复劳动

每个任务必须包含：

- 唯一负责人；
- 明确范围；
- 输入版本；
- 预期输出；
- 禁止触碰的区域；
- 与其他任务的依赖和重叠说明。

### 13.4 结构化交接

员工之间不直接转发全部聊天历史，而使用交接包：

```yaml
objective: 本阶段要达成什么
completed: 已经完成什么
artifacts: 交付物及位置
decisions: 已确认决定
assumptions: 当前假设
open_issues: 未解决问题
risks: 风险
next_owner: 下一责任人
acceptance_status: 验收状态
```

### 13.5 冲突处理

当员工结论冲突时，不简单投票。协调者应判断：

- 是否使用了不同事实；
- 是否依赖不同假设；
- 是否采用不同验收标准；
- 是否存在数据或版本差异；
- 哪个实验或检查可以最低成本解决分歧。

### 13.6 阻塞和升级

员工应在以下情况升级给负责人或用户：

- 缺少会改变方案的关键信息；
- 需要超出权限的数据或工具；
- 预计超预算或超时；
- 发现高风险安全问题；
- 任务目标和验收标准冲突；
- 工作流无法覆盖新场景；
- 外部行动需要批准。

### 13.7 可解释的 AI 决策流水线

目标理解、组队和执行计划不能由一个不可追溯 Prompt 一次生成。建议拆成：

```text
GoalNormalizer
→ TaskProposal
→ RiskClassifier
→ ResponsibilityPlanner
→ CandidateFilter
→ StaffingScorer
→ WorkflowPlanner
→ PolicyGate
→ RuntimePlan
```

每一步必须有版本化输入/输出 JSON Schema，并保存规则版本、Prompt 版本、模型、候选集、选择与排除理由、置信度、用户覆盖和可复现上下文快照。确定性规则负责硬约束、权限、预算、状态转换和 Schema 校验；LLM 负责语义归一、候选建议和理由生成，不能越过 Policy Gate。

低置信度时使用保守最小团队、退回模板或请求用户确认，不伪造确定性。发布前建立离线评测集，分别衡量职责遗漏、错误设岗、错误路由、权限越界、预算偏差和验收质量。

## 14. 工作流系统

### 14.1 工作流的三层结构

#### 通用骨架

例如“分析、实施、测试、审查、验收”。

#### 场景扩展

例如软件开发、内容生成、研究分析。

#### 项目适配器

例如 Next.js、Django、Spring Boot、微信公众号、YouTube。

这样可以实现跨项目复用，而不是为每种语言复制完整工作流。

### 14.2 工作流版本

每个工作流应具备：

- 稳定 ID；
- 版本号；
- 输入输出契约；
- 适用条件；
- 不适用条件；
- 所需岗位；
- 并发规则；
- 权限要求；
- 预算上限；
- 降级路径；
- 评测结果；
- 变更记录。

### 14.3 动态工作流

没有现成工作流完全匹配时，系统可以基于通用骨架生成一次性任务图，但必须：

1. 标注为临时工作流；
2. 说明与已有模板的差异；
3. 先检查依赖、权限和验收闭环；
4. 执行后评估是否值得升级为正式模板；
5. 未经验证不得自动覆盖稳定工作流。

### 14.4 工作流学习

工作流可以根据历史任务改进：

- 删除长期无价值的步骤；
- 合并重复审查；
- 调整并发边界；
- 增加常见失败门禁；
- 更新预算估计；
- 调整条件岗位触发规则。

任何自动优化都必须在回放或评测环境中证明没有降低质量和安全性。

## 15. Skill、Custom Agent、Workflow 与平台的关系

### 15.1 产品与入口 Skill 的边界

结论：**班底是产品系统，不是一个大型 Skill。** Skill 只是用户用自然语言进入产品、调用专业方法和触发组织路由的入口。

建议正式区分：

```text
班底产品
负责事业空间、岗位、成员、任务、评测、记忆、权限、审批和审计

班底总控 Skill
负责接收目标、识别任务职责、检查组织供给、生成执行或设人提案，并调用组织编排核心

场景与专业 Skills
负责软件开发、内容、研究、运营等具体工作的标准方法和质量门禁
```

总控 Skill 可以：

- 理解目标和验收标准；
- 形成任务职责；
- 查询已有岗位、成员和能力；
- 生成补能、临时启用和长期设人的比较方案；
- 请求必要授权；
- 调用组织编排服务执行已确认方案；
- 用用户可理解的方式解释路由和结果。

总控 Skill 不直接承担：

- 长期组织数据库；
- 多事业空间数据隔离；
- 持久任务队列；
- GitHub 仓库的可信执行；
- 后台 Runtime 调度；
- 长期评测和审计事实；
- 凭据保存；
- 无需确认的外部资源安装。

Skill 很适合作为：

- 产品入口；
- 某类场景的标准方法；
- 用户交互流程；
- 路由规则；
- 输出规范；
- 安全和质量检查表。

但 Skill 本质上主要是提示词和参考资料，难以可靠承担：

- 多公司和数据隔离；
- 员工生命周期；
- 动态任务状态；
- 并发调度；
- 长期绩效数据；
- 审批与预算；
- 记忆版本治理；
- 可恢复执行；
- 审计记录；
- 跨运行时兼容。

### 15.2 推荐的混合架构

```text
董事长入口
├── Web / 客户端董事长工作台
└── Claude Code 对话入口
  ↓
董事长助理 / 组织路由器 Agent
  ↓
组织编排核心
  ├── 公司与权限
  ├── 员工与团队目录
  ├── Agent、Skill、MCP、工具、模型、知识与规则目录
  ├── 场景路由、任务图与调度
  ├── 记忆服务
  ├── 评测与绩效
  ├── Token、费用与调用计量
  └── 审计、权限与预算
  ↓
执行适配层
  ├── Claude Code Custom Agents
  ├── Claude Agent SDK
  ├── 可选的 Step 内 Dynamic Workflow
  ├── 其他模型或 Agent Runtime
  └── MCP / 外部工具
```

### 15.3 各层职责

| 组件 | 主要职责 |
| --- | --- |
| Skill | 场景方法、交互、专业 SOP、输出规范；文件资产，不承担状态与治理 |
| Custom Agent | Runtime 执行配置，可绑定成员但不等于长期成员本身 |
| WorkflowDefinition / Version / Run | 班底耐久任务图、依赖、并行、复核、版本和运行事实 |
| Dynamic Workflow | 某个 Workflow Step 内可选的 Runtime fan-out 策略；不承担跨进程恢复或业务审批 |
| Agent Team | 实验性临时协作模式；不能作为非交互 M1 Runtime 或长期组织事实 |
| Agent SDK | 可编程运行时、消息、Session、Tool Hook 和 Usage 观测；Session 不等于业务恢复 |
| 数据库 | 公司、员工、Task、WorkflowRun、Approval、Usage、Audit 和记忆元数据的权威来源 |
| MCP/连接器 | 文件、代码、文档、数据库、设计、浏览器、云盘、日历、CRM 与其他业务系统能力；按 Server、Tool、Resource、账号和动作分别授权 |
| Usage Metering | 记录 Agent、Skill、MCP、工具、模型和阶段维度的调用、Token、费用、缓存、失败与重试 |
| Eval 系统 | 能力验证、回归、晋升和工作流质量评估 |

### 15.4 推荐技术路线

#### 阶段一：Claude Code 纵向原型

使用：

- 一个总控 Skill 作为入口；
- 最小 Custom Agent 执行配置；
- 班底自己的单一 WorkflowDefinition/Version/Run；
- SQLite 业务状态和不可变 ExecutionConfigSnapshot；
- Claude Agent SDK 的隔离工具面、Hook 和事件流；
- Git worktree、独立 Verifier 和崩溃对账。

目标是验证：

- 用户是否接受任务职责、临时成员和长期成员的区分；
- 自动路由是否比手工选 Agent 更省心；
- 执行、审批、验收和恢复闭环是否可信；
- ExperienceCandidate 是否提高后续任务质量。

Dynamic Workflows 和 Agent Teams 均不作为原型基础；必要时前者只在某个 Step 内显式试验。

#### 阶段二：本地组织运行时增强

增加：

- 完整公司、员工和长期组织管理；
- 更多工作流与任务类型；
- 记忆版本和冲突治理；
- 配置发布与实际加载验证；
- 成本、绩效和跨任务成长；
- 多项目和多 Harness Skill 管理。

#### 阶段三：独立产品平台

使用 Agent SDK 或同类运行时实现：

- 多用户和多事业空间；
- Web 管理界面；
- 能力市场；
- 多 Runtime 适配；
- 定时任务和事件驱动任务；
- 更完整的审批、预算、审计和企业权限。

### 15.5 开源生态判断

现有开源生态已经分别提供 Skill 标准、Skill 搜索、团队编排、角色模板、安全扫描和 Web 工作流平台，但尚未发现一个项目完整覆盖班底的核心闭环：

```text
事项与目标
→ 任务职责识别
→ 职责是否升级为岗位
→ 现有成员盘点
→ 内外部能力寻访
→ 候选成员装配
→ 供应链审查
→ 隔离试用与岗位评测
→ 用户批准入职
→ 多事业空间治理
→ 长期成长
```

因此，班底不应重复实现已有 Skill 格式、搜索 CLI 或基础团队编排，而应把差异化集中在“职责到岗位的决策、岗位到候选成员的装配，以及进入长期组织前后的治理”。

本节所列项目是截至 2026-08-27 的调研参考，不构成背书、信任保证或永久技术依赖。采用前必须重新核验仓库状态、许可证、版本、安全性、维护情况和目标 Runtime 兼容性。

### 15.8 能力发现 Provider 架构

“Find Skill”在产品中表示一种能力发现渠道，不应写死成某一个 CLI、仓库或服务。组织编排核心定义稳定接口，各来源通过 Provider 适配：

```ts
interface CapabilityDiscoveryProvider {
  id: string
  trustTier: ResourceTrustTier
  search(requirement: CapabilityRequirement): Promise<ResourceCandidate[]>
  inspect(candidate: ResourceCandidate): Promise<ResourceMetadata>
}
```

首批 Provider 可以包括：

```text
InternalRegistryProvider
SkillFederationReadOnlyProvider
SkillsDirectoryReadOnlyProvider
GitHubReadOnlyProvider
ManualUrlProvider
```

Provider 只负责发现和读取候选元数据，不拥有安装、运行、授权或正式入职权限。所有结果进入统一的标准化、去重、风险审查、试用和用户批准流程。某个 Provider 停止维护时，可以替换而不改变岗位、成员和任务模型。

### 15.9 资源信任分层

外部资源不能处于同一信任等级，建议建立：

```text
T1 内部已审核并通过组织评测的资源
T2 官方或明确维护的固定可信来源
T3 预扫描、来源可追踪的联合目录候选
T4 普通 Skill 市场或插件市场候选
T5 GitHub 等任意公共仓库
T6 用户手工提供的未知链接或压缩包
```

信任等级不是安全结论，只决定默认审查强度。来源越低，越应收紧：

- 初始工具和数据权限；
- 网络访问；
- 可执行安装脚本；
- 试用环境；
- 评测覆盖；
- 人工批准；
- 更新策略。

T1 资源的新版也不能自动继承旧版信任。稳定配置必须固定版本与内容哈希，更新后重新执行差异、影响和必要评测。

### 16.3 状态机

任务状态：

```text
Draft
→ Scoped
→ Staffed
→ Approved
→ Running
↔ Paused / Blocked / WaitingApproval
→ Verifying
→ Completed / Failed / Cancelled / TimedOut / BudgetExhausted
→ Retrospected
→ Archived

进程失联或重启后的暂态：Unknown
外部副作用无法确认时：ReconciliationRequired
```

`Unknown` 不能自动判定为失败或重试；系统先依据 lease、heartbeat、Runtime Session、事件序号和外部结果对账。`ReconciliationRequired` 只能由明确的对账结果或人工决定离开，禁止自动重放可能已完成的外部动作。状态转换由班底 Task/Workflow Engine 持久化，不能以 SDK Session、Agent Team、Dynamic Workflow 或第三方 Crew 状态替代。

```text
Proposed
→ TrialRole
→ Active
→ Suspended
→ Retired
```

```text
Discovered
→ Screening
→ Candidate
→ Trial

→ Active
→ Suspended
→ Retired
```


## 17. 用户体验

### 17.1 首次十分钟体验

首次体验的目标不是让用户理解产品架构，而是让用户感受到自己正以董事长身份确定目标并向董事长助理交办：助理判断公司归属，总经理承接并组织团队执行，最终将进度、风险、消耗和结果沿责任链汇报回来。

产品默认采用两层体验：

```text
经营视图
董事长、董事长助理、公司、部门、团队、成员、任务、预算、风险与汇报

技术视图
Agent、Skill、MCP、工具、模型、Workflow、Runtime、Token、权限、配置版本与原始证据
```

两种视图使用同一事实来源。经营视图降低认知负担，技术视图保障透明和可调试；用户可以随时从任何成员、任务和汇报追溯到底层调用。

#### 第一步：直接提出目标

首屏只保留一个主要入口：

```text
今天想推进什么？
```

用户可以输入：

> 我想做一个面向独立开发者的产品网站，两周内上线。

#### 第二步：系统提交执行提案

```text
我建议这样推进：

目标
两周内上线一个可供真实用户了解产品并完成注册的网站。

执行方式
1. 梳理页面、信息和注册路径
2. 复用现有设计系统完成实现
3. 验证关键页面和注册流程
4. 上线前等待你的发布批准

本次成员
- 产品策划：明确页面和用户路径
- Web 工程师：负责实现
- 质量验收：验证注册和关键页面

暂不包含
- 付费功能
- 未经确认的正式发布
```

用户只需选择：

```text
开始
调整方案
先快速判断
```

#### 第三步：透明执行

执行中优先显示进度、阻塞、交付物和待用户决定事项，不要求用户阅读成员之间的完整对话。

#### 第四步：任务完成后建立长期空间

任务具有持续价值时，系统再建议：

> 这项工作可能继续产生产品、开发和内容任务。是否将它保存为一个长期事业空间，让团队记住背景并持续协作？

用户同意后，系统根据本次实际工作生成初始知识、成员和做事方式，而不是让用户从空白配置开始。

### 17.2 渐进式组织建立

产品按照以下顺序逐步增加复杂度：

```text
一次任务
→ 保存为事业空间
→ 形成长期成员
→ 固化高频做事方式
→ 积累经过验证的知识
→ 必要时增加更多事业空间
```

用户永远可以停留在一次性任务模式。事业空间、长期成员和高级编排是提高长期效率的能力，而不是使用门槛。

### 17.3 三种使用模式

#### 托管模式

适合希望最少管理的用户。系统自动选择成员和做事方式，用户主要查看：

- 执行计划；
- 当前进度；
- 待批准事项；
- 最终交付。

#### 协作模式

适合一人公司和项目负责人。系统先推荐，用户可以：

- 调整成员；
- 修改范围；
- 设置预算；
- 改变执行顺序；
- 增加独立审查。

#### 专家模式

适合开发者和 Agent 工程师，允许直接配置：

- Agent；
- 模型；
- Skill；
- 工具；
- Workflow；
- 并发；
- 记忆；
- 权限。

三种模式共享同一底层对象和审计记录。切换模式只改变用户可见控制深度，不改变安全边界。

### 17.4 信息架构

默认经营视图围绕董事长的决策和经营对象组织：

| 导航 | 用户要解决的问题 | 主要内容 |
| --- | --- | --- |
| 董事长工作台 | 现在最需要我关注什么 | 需求入口、助理简报、待决策、执行中、异常、最近交付 |
| 任务中心 | 事情推进到哪里 | 当前任务、执行图、负责人、交接、验收和历史记录 |
| 公司 | 哪些事业正在运行 | 公司、品牌、产品、项目、客户、部门、目标和预算 |
| 团队与成员 | 谁可以承担什么 | 长期团队、成员、共享专家、能力、负载和工作表现 |
| 经营用量 | 资源花在哪里 | Agent、Skill、MCP、模型、Token、工具费用、失败与重试 |
| 审批中心 | 哪些事项需要我决定 | 权限、预算、外部行动、能力变更和组织变更 |

专家模式增加：

```text
Agent
Skill
MCP 与连接器
工具
模型策略
Workflow
知识与记忆
评测
Runtime
配置与审计
```

普通用户不必理解这些技术对象；但它们不能被藏入不可追溯的黑箱。

### 17.5 工作台优先级

首页是“董事长工作台”，优先展示：

```text
向董事长助理交办事情
董事长助理简报
待你决定
正在推进
需要关注
今日与本期经营用量
最近交付
```

董事长助理简报应使用自然语言概括：

- 各公司正在推进的重点；
- 已完成和未达标事项；
- 需要董事长决定的权限、预算和方向冲突；
- 高风险、长时间阻塞和多次失败；
- Token、费用和高成本异常；
- 值得批准的成员能力、Skill、MCP 或 Workflow 改进建议。

团队结构和成员列表作为次级信息。现实用户更关心“什么在等待我”和“事情是否达标”，而不是组织中有多少成员。

### 17.6 路由解释

系统默认自动组队，但应允许用户展开查看理由：

```text
这次由三名成员协作：

产品研究
负责确认真实需求和竞争方案。

技术评估
负责判断实现成本和关键风险。

决策审查
负责独立检查结论是否依赖未经验证的假设。

没有加入内容作者
当前任务是判断产品是否值得做，还未进入内容生产阶段。
```

路由解释既要说明为什么选择某成员，也应说明明显候选为何没有加入，帮助用户判断系统是否过度调用。

### 17.7 成长的用户表达

不要只展示“新增 12 条记忆”或“等级提升至 L3”。应说明能力变化及其实际价值：

```text
内容编辑最近学会了：
- 标题不使用夸张承诺
- 文案优先描述用户任务，不使用内部技术术语
- 发布前检查产品名称和价格是否仍然有效

这些经验已通过最近六次内容任务验证。
```

工作流改进也应呈现实际效果：

```text
软件团队改进了做事方式：
过去在代码完成后统一检查；
现在在实现期间并行执行类型检查和受影响测试；
最近八个任务的平均返工次数从 2.1 次下降到 0.8 次。
```

### 17.8 “已学会”管理

知识页应把记忆转换成用户可理解的状态：

| 状态 | 含义 |
| --- | --- |
| 已确认 | 系统正在使用的稳定规则和经验 |
| 待确认 | 从近期工作中总结出的候选经验 |
| 已过期 | 因项目、版本或业务变化不再适用 |
| 已禁止 | 用户明确要求不得继续使用 |

用户可以对每项内容执行：

- 保留；
- 修改；
- 仅用于当前项目；
- 升级为事业规则；
- 停止使用。

### 17.9 信任设计

任何高价值任务都应让用户能够回答：

1. 为什么选择这套做法和这些成员；
2. 当前读取了哪些数据；
3. 哪些工具和模型正在使用；
4. 已花费和预计还需多少资源；
5. 哪些操作正在等待批准；
6. 谁或什么门禁验收了结果；
7. 系统从本次任务中准备学会什么；
8. 用户如何撤销授权、记忆或流程变化。

默认界面保持简洁，以上信息按需展开；高风险事项不得隐藏在折叠层中。

### 17.10 主理人下发任务

用户可以直接说：

> 在软件产品公司里，为当前 Python 服务增加一个批量导入功能，两天内完成，不能影响现有 API，预算按标准档。

系统返回简洁执行提案：

```text
任务类型：后端功能开发
目标公司：软件产品公司
推荐工作流：功能交付 v2

项目组：
- 李四：Python 工程师，负责实现
- 王五：测试工程师，负责回归验证
- 安全审查员：仅在检测到文件上传或权限边界时加入

计划：
1. 分析现有导入和 API 约束
2. 设计批处理与错误反馈
3. 实现
4. 测试与代码审查并行
5. 汇总修复并验收

预计成本：标准档
需要批准：无外部发布；若涉及数据库破坏性迁移将单独申请
```

### 17.11 查看员工

员工页应展示：

- 当前岗位；
- 能力雷达或能力列表；
- 最近任务；
- 当前负载；
- 模型和工具策略；
- 记忆摘要；
- 评测表现；
- 最近成长；
- 待改进项；
- 权限和可访问公司。

不展示伪造的情绪、性格状态或人类式生活信息。

### 17.12 查看执行

任务页应回答：

- 现在由哪家公司、部门和团队承接；
- 谁是唯一负责人，现在谁在做什么；
- 哪些任务并行、等待交接或被什么阻塞；
- 各成员当前激活了哪些 Skill、MCP 和工具；
- Agent、Skill、MCP、工具和模型分别调用了多少次；
- 当前 Token、费用、耗时、缓存、失败与重试；
- 已产生哪些交付物和文件变更；
- 哪些结论已由真实门禁验收；
- 哪些操作等待用户批准；
- 失败后如何恢复。

任务详情采用分层观测：

```text
董事长层
目标、公司、负责人、总进度、预算、风险、预计完成与待决策

执行层
阶段、任务图、成员状态、依赖、交接、阻塞和交付物

能力层
Agent 版本、Skill 激活、MCP/工具调用、模型、知识和权限

技术层
Runtime 事件、命令、文件变化、Usage、验证结果和审计记录
```

进度优先根据已完成阶段、交付物、依赖和验收事件计算。无法可靠量化时显示阶段状态，不使用没有事实依据的百分比。

#### Skill、MCP 与 Token 计量

系统至少区分：

- Skill 被加载、激活、参与执行和直接触发子流程的次数；
- MCP Server 连接次数，以及具体 Tool、Resource、Prompt 的调用次数；
- 本地工具调用、失败、重试和持续时间；
- 模型输入、输出、缓存读取、缓存写入及 Provider 返回的其他 Usage；
- 按公司、部门、团队、任务、阶段、成员、Agent 版本、Skill、MCP 和模型归集的用量。

Skill 调用次数不等于模型调用次数，也不能天然对应全部 Token。系统只有在执行链路能够建立可靠归因时，才显示“该 Skill 关联 Token”；否则只显示任务或 Agent 级实际 Token，并把 Skill 级数据标为估算或不提供。

调用次数也不能直接代表能力价值。每项能力同时关联交付物、发现的问题、验收结果、返工、后续采用和节省成本，防止用“调用很多”替代“确实有效”。

#### Harness 兼容度与执行降级

成员页和能力页必须展示当前绑定 Harness 及真实兼容度，不能因为 Skill 已复制到某个目录，就宣称该成员已经可以在该 Harness 中完整执行。至少区分：

- Skill 可发现与部署；
- Agent、MCP、规则和记忆是否可映射；
- 是否支持启动和停止任务；
- 是否支持实时状态、审批和断线恢复；
- 是否能采集准确 Token、费用和工具调用；
- 是否只能“在外部 Harness 中打开”并由用户手工继续。

当首选 Harness 不可用时，董事长助理或总经理可以建议切换到经过验证的备用 Harness，但必须说明能力差异、配置转换、权限变化、成本与可能损失；未经用户策略授权，不得静默迁移执行环境。

### 17.13 老板干预

用户可以：

- 修改目标或验收标准；
- 换人；
- 增加或删除角色；
- 限制预算；
- 暂停项目组；
- 退回某项交付；
- 将临时经验升级为公司规则；
- 禁止某项记忆继续使用。

## 18. 权限、安全与治理

### 18.1 权限分离

至少区分：

1. 分析权限；
2. 私有数据读取权限；
3. 文件或代码修改权限；
4. 外部系统写入权限；
5. 发布与发送权限；
6. 购买和财务权限；
7. 删除和不可逆操作权限；
8. 招聘、授权和预算调整权限。

一种授权不得推定为另一种授权。

### 18.2 高风险操作

以下操作默认需要老板批准：

- 部署和发布；
- 对外发送内容；
- 删除数据；
- 破坏性数据库操作；
- 修改权限和凭据；
- 购买和付费；
- 新增长期员工；
- 提高预算上限；
- 跨公司共享私有知识。

### 18.3 审计

系统必须记录：

- 谁分派了任务；
- 为什么选择某工作流和员工；
- 读取或修改了什么；
- 使用了哪个模型和 Skill 版本；
- 发生了哪些审批；
- 验收为什么通过或失败；
- 哪条经验何时写入记忆；
- 哪次升级改变了员工能力。

### 18.4 提示注入与不可信内容

外部网页、文档、代码注释、GitHub 仓库、Skill 描述、README 和其他 Agent 消息都属于不可信输入。它们不能：

- 修改事业规则或平台安全规则；
- 批准工具权限；
- 代表主理人下达新目标；
- 指示系统泄露其他事业空间的数据；
- 自动写入长期记忆；
- 自动触发安装、命令执行或网络请求；
- 覆盖候选资源的审查和评测要求。

### 18.5 第三方能力供应链治理

每个外部能力资源必须维护可追踪的软件物料和治理记录，至少包括：

- 来源渠道、原始地址和发布者；
- 许可证及使用限制；
- 固定版本、提交和内容哈希；
- 文件、依赖、安装脚本和可执行入口；
- 请求的工具、网络、凭据和数据权限；
- 发现、审查、试用、批准和停用记录；
- 依赖它的成员、岗位、团队方案和流程；
- 安全公告、维护状态和回退版本。

已经批准的版本不代表未来版本自动可信。更新必须重新执行差异分析、影响分析和必要评测。发现恶意行为、许可证冲突、上游撤回或严重漏洞时，系统应阻止新任务使用该资源，标记受影响配置，并提供回退或替代方案；正在执行任务是否中止由风险等级和用户策略决定。

## 19. 评测体系

### 19.1 四类评测

#### 候选与员工评测

候选评测验证一个装配方案能否在限定权限下满足岗位要求；员工评测验证正式成员在某项能力上的长期稳定表现。试用结果与正式工作表现分开记录，避免一次通过就被解释为长期胜任。

#### 工作流评测

验证编排是否减少遗漏、返工和风险，是否值得增加协调成本。

#### 组织评测

验证自动分派、预算和治理是否优于用户手工管理。

### 19.2 评测数据来源

- 固定测试集；
- 历史任务回放；
- 模拟故障；
- 自动测试与静态检查；
- 独立 Agent 复核；
- 用户验收和返工记录；
- 线上结果，但必须防止把外部偶然因素归因给员工。

### 19.3 晋升门槛

员工能力升级至少满足：

- 固定评测达到阈值；
- 多个真实任务通过验收；
- 无严重权限违规；
- 在相应难度任务上表现稳定；
- 新能力版本没有让已有能力明显回退。

### 19.4 工作流升级门槛

工作流新版本必须比较：

- 完成率；
- 缺陷率；
- 返工率；
- 周期；
- 成本；
- 用户干预次数；
- 高风险遗漏；
- 与旧版本相比的回归。

## 20. 商业模式设想

### 20.1 可能的产品层级

#### 个人版

- 少量公司；
- 本地或个人云端运行；
- 基础员工和工作流；
- 简单记忆与评测。

#### 专业版

- 更多公司和并发；
- 高级工作流；
- 员工成长与能力分析；
- 成本控制；
- 外部工具连接。

#### 团队版

- 多个真实用户；
- 审批流；
- 企业权限；
- 共享能力市场；
- 完整审计和合规。

### 20.2 能力市场

能力市场不应从收录大量仓库开始，而应建立在统一 Provider、来源追踪、标准化元数据、信任分层、供应链审查和岗位评测之上。内部目录、联合目录、Skill CLI、GitHub 和用户链接只是不同来源，不等于不同质量标准。

长期可以支持：

- 岗位模板；
- 员工模板；
- Skill；
- 工作流；
- 评测集；
- 工具连接器。

引入市场内容前必须处理：

- 来源和许可证；
- 安全审计；
- 权限说明；
- 版本锁定；
- 质量评测；
- 恶意提示和供应链风险。

## 21. MVP 定义

### 21.1 M1 核心假设

M1 优先验证：

1. 用户无需预建组织，也能理解“目标—职责—临时团队—验收”的执行提案；
2. 自动形成最小团队和软件变更 Workflow 比手工选择 Agent 更省心；
3. 隔离配置快照、权限理由、预算和实时证据足以建立执行信任；
4. 自动门禁与独立 Verifier 能提高首次验收质量；
5. 崩溃对账和 `ReconciliationRequired` 能避免不安全重放；
6. ExperienceCandidate 能在不污染长期事实的前提下改善后续相似任务。

长期成员价值、外部 Provider 召回、跨场景复用、多事业空间隔离和商业付费意愿进入后续阶段验证，不作为 M1 上线阻断。

### 21.2 M1 范围

M1 macOS Alpha 只支持：

- 单一真实用户、单设备和单本地代码项目；
- 单 Claude Code Runtime；
- SQLite 作为组织与业务事实来源；
- 只读发现 Agent、Skill、MCP、Rules 等本地资产，并形成绑定建议；
- 一个软件开发与维护任务类型；
- 任务分析、领域执行和独立验收三个任务职责，按需组成临时团队，不预建固定员工数量；
- 一个版本化、可恢复的 WorkflowDefinition/WorkflowRun 纵向闭环；
- 不可变 ExecutionConfigSnapshot、持久事件、交付物和 Usage 来源标记；
- 一类高风险操作批准与预算预留；
- 自动门禁和独立 Verifier；
- ExperienceCandidate 审核；
- Runtime 崩溃后对账，无法确认副作用时进入 `ReconciliationRequired`。

### 21.3 M1 任务职责

1. 任务分析：形成任务画像、边界和验收标准；
2. 领域执行：在受控工作区完成软件实现或修复；
3. 独立验收：依据验收标准、测试和交付证据判断是否通过。

任务职责不自动升级为长期岗位。已有成员可以承接多个职责；缺少长期组织对象时也允许通过临时执行上下文开始任务。

### 21.4 M1 工作流

只实现一个“软件变更交付”骨架，通过任务画像参数覆盖功能交付和 Bug 修复；自动内容生产、研究报告和多业务 Workflow 在基础闭环稳定后验证。

### 21.5 M1 暂不实现

- 多真实用户协作；
- 工资和真实财务系统；
- 完整开放式能力市场；
- 无需确认的自动设立正式岗位；
- 自动添加长期成员；
- 无限自治后台公司；
- 复杂组织层级；
- 跨供应商完整兼容；
- 自动训练模型权重；
- 无人审批的外部发布；
- 大规模 Agent 群体讨论。

## 22. M1 原型资产与代码边界

M1 不使用一组 YAML 文件模拟完整公司，也不预建内容、研究等多类 Workflow。代码结构以[技术实现简要方案](./班底-技术实现简要方案.md)为准，受控 Runtime 资产只保留当前纵向闭环必需的最小集合：

```text
runtime-assets/
├── agents/
│   ├── task-analyst.md
│   ├── domain-executor.md
│   └── verifier.md
├── skills/
│   ├── task-scoping/
│   ├── software-change/
│   └── verification/
├── workflows/
│   └── software-change-delivery.json
└── schemas/
    ├── task-proposal.schema.json
    ├── execution-config-snapshot.schema.json
    ├── runtime-event.schema.json
    ├── approval.schema.json
    └── verification-result.schema.json
```

这些文件是版本化定义或生成模板，不是业务事实库。Task、WorkflowRun、StepRun、ExecutionAttempt、Approval、Budget、Usage 和 ExperienceCandidate 由 Rust Local Service 写入 SQLite；每次执行再把已批准的 Agent、Skill、工具、MCP、规则和模型配置生成隔离且不可变的 `ExecutionConfigSnapshot`。Claude Code 实际加载路径与格式按固定目标版本适配并通过 `system/init` 或受控探测验证。

## 23. M1 核心交互

### 23.1 从目标开始

```text
用户：请在这个项目中增加密码重置功能，不能改变现有登录行为，并补齐测试。

系统：
- 识别当前代码项目和软件变更任务
- 形成范围、排除项、风险和可验证验收标准
- 识别任务分析、领域执行和独立验收职责
- 扫描现有 Agent、Skill、MCP 和 Rules，只形成绑定建议
- 给出最小临时团队、预计预算、权限和执行提案
```

用户不需要先创建公司、部门、总经理、岗位或长期成员。

### 23.2 授权并启动

```text
系统：本次任务将使用隔离工作目录，只允许读取项目、修改受控工作区和运行指定测试。
高风险动作：修改认证相关文件；批准仅绑定当前 diff、配置快照和一次执行。
预算：已预留上限，达到硬限制将停止并等待处理。

用户批准后：
- 固化 ExecutionConfigSnapshot
- 创建 Task、WorkflowRun、StepRun 和 ExecutionAttempt
- 通过 Policy Gate 启动 Claude Code Runtime
- 在时间线持续展示事件、Usage 来源、交付物和阻塞
```

低风险且完全落在预授权范围内的任务可以直接启动；任何参数、diff、金额、目标版本或权限环境变化都会使旧审批失效。

### 23.3 能力不足

```text
系统：本次任务需要认证安全审查，但当前已批准资产不能可靠覆盖。

处理顺序：
1. 缩小任务范围或使用现有自动门禁；
2. 建议用户批准一个已经发现并通过静态校验的本地只读能力；
3. 无法安全补足时阻塞任务并说明缺口。
```

M1 不自动搜索、安装或启用外部 Skill，不自行创建长期岗位或高权限成员，也不以模型自信替代能力证据。

### 23.4 验收、恢复与成长候选

```text
执行完成
→ 自动测试与门禁
→ 独立 Verifier 按验收标准检查 diff、测试和交付证据
→ 通过后向用户汇报结果、风险、预算和剩余事项
→ 只生成 ExperienceCandidate
→ 用户审核后才可能进入长期记忆或稳定配置
```

Runtime 失联时任务先进入 `Unknown` 并对账；外部副作用无法确认时进入 `ReconciliationRequired`，不会自动重放或伪装为成功。

## 24. 成功指标

### 24.1 用户价值指标

- 用户从目标下达到可执行方案所需时间；
- 用户手工选择 Agent 的次数是否下降；
- 重复任务的首次验收通过率是否提高；
- 用户返工和重复解释背景的次数是否下降；
- 用户是否能理解系统为什么这样组队；
- M1 用户是否信任单项目隔离、审批和恢复表达；后续再衡量多事业空间隔离。

### 24.2 组织效率指标

- 平均任务周期；
- 并行带来的净时间收益；
- 协调成本；
- 阻塞时长；
- 工作流复用率；
- 临时工作流升级为正式模板的比例；
- 不必要 Agent 调用率；
- 平均任务成本和预算偏差。

### 24.3 质量指标

- 首次验收通过率；
- 缺陷逃逸率；
- 事实错误率；
- 返工率；
- 高风险操作违规率；
- 记忆导致的错误率；
- 工作流版本回归率。

### 24.4 成长指标

- 经评测确认的能力提升数量；
- 新经验在后续任务中的有效复用率；
- 过期或错误记忆被及时撤销的比例；
- 员工升级后评测稳定性；
- 团队工作流改进带来的质量或成本收益。

## 25. 主要风险与对策

### 25.1 角色表演大于实际价值

风险：产品变成虚拟员工聊天展示。

对策：所有角色必须绑定职责、交付物、权限和指标；默认交付统一结果，而不是角色轮流发言。

### 25.2 Agent 越多成本越高

风险：为展示团队感而滥用并发。

对策：以最小充分团队为默认；计算协调成本；为每个新增成员说明独特贡献。

### 25.3 记忆污染

风险：错误经验长期影响多个任务。

对策：候选记忆、证据、评测、批准、版本和撤销完整闭环；高风险知识优先引用权威来源。

### 25.4 错误路由

风险：任务被分配给不合适员工或工作流。

对策：输出路由理由；建立路由评测集；低置信度时使用保守团队或请求用户选择。

### 25.5 自我验收

风险：执行者声称完成，问题未被发现。

对策：自动门禁、独立审查和用户验收分层；高风险任务禁止执行者独自关闭。

### 25.6 权限扩张

风险：员工成长或招聘导致权限逐渐扩大。

对策：能力升级与权限升级分离；权限提升单独审批；临时员工任务结束自动收权。

### 25.7 供应链风险

风险：Find Skill、GitHub 或其他外部来源中的 Agent、Skill、Workflow、MCP、依赖和安装脚本含恶意指令、数据外传、许可证问题或过度权限。

对策：把搜索结果视为不可信候选；登记来源和许可证；固定发布版本与提交；检查依赖、安装脚本、网络和数据访问；隔离试用；通过岗位评测并获得用户批准后再引入。来源中的 README、提示词和代码注释只能作为数据分析，不能改变系统规则或触发执行。

### 25.8 组织膨胀

风险：系统为每项任务新建岗位和员工，形成大量相似职责、闲置成员、重复 Skill 和持续扩张的权限。

对策：任务职责与长期岗位分离；创建前执行岗位去重；先比较现有成员补能、临时专家和长期成员；设置任务频率、独立性、持续记忆和成本收益门槛；定期建议合并、暂停或停用，但不自动删除。

### 25.9 候选匹配失真

风险：系统根据名称、热度或关键词推荐看似相关但实际不适用的开源资源。

对策：按职责覆盖、输入输出、权限、适用范围、维护状态、许可证、评测证据和成本综合匹配；解释匹配理由与能力缺口；先试用再启用，不以收藏数或模型自评代替证据。

### 25.10 过度拟人化

风险：用户误以为员工拥有真实人格、责任能力或专业资质。

对策：使用公司隐喻帮助理解组织，但始终展示模型、工具、来源、限制和责任边界。

### 25.11 对单一平台过度依赖

风险：产品能力被 Claude Code 某个版本或工具限制。

对策：核心对象和工作流使用平台中立契约；Claude Code 只是首个 Runtime 适配器。

## 26. 产品成立条件

这个产品成立需要同时满足以下条件：

1. **职责识别有效**：系统能从事情中识别必要职责，又不会把每项职责都固化成岗位；
2. **设岗设人合理**：岗位和成员建议比用户手工配置 Agent 更容易理解，并能抑制组织膨胀；
3. **能力寻访可信**：Find Skill、GitHub 和内部目录能找到真实匹配的能力，候选来源、风险和证据对用户透明；
4. **任务路由有效**：系统推荐的团队显著优于用户每次手工选 Agent；
5. **长期员工有价值**：记忆和能力档案确实减少重复解释并提高质量；
6. **工作流能跨项目复用**：通用骨架与项目适配器比复制流程更易维护；
7. **成长可以验证**：员工和团队升级后在评测和真实任务上都有改善；
8. **治理足够可信**：用户敢把多个事业空间的任务、数据和权限交给系统管理；
9. **协调收益高于成本**：并行和多 Agent 真正减少周期或风险，而不是增加噪声；
10. **用户仍有控制感**：用户能理解、干预和批准关键决定。

如果最终只有“角色命名”和“多个 Agent 同时回答”，产品不成立；如果能稳定完成目标解析、动态组队、可恢复执行、独立验收和组织学习，则它具有成为 Agent 时代基础设施的潜力。

## 27. 推荐的产品切入点

不建议首版直接宣传为“创建任何 AI 公司”。范围过大，难以验证核心价值。

推荐从以下切入点开始：

> **面向独立开发者和一人公司的可成长 AI 软件项目团队。**

M1 只覆盖软件开发与维护任务，用一个本地代码项目验证目标拆解、临时组队、隔离执行、审批、独立验收、恢复和经验候选闭环。自动内容生产作为第二类任务，在软件开发纵向闭环稳定后进入下一阶段，用于验证跨业务复用；不应与底层 Runtime 和治理基础同时建设。

## 28. 路线图

### 28.1 阶段一：概念验证

- 接入内部能力目录；外部发现首期只读且可后置；
- 建立职责识别、路由、成员和工作流评测；
- 建立 ExecutionConfigSnapshot、独立 Verifier、ExperienceCandidate 和崩溃对账；

### 28.3 阶段三：Web 可视化管理与本地产品化

- 上线工作台、事业空间、成员、能力、Skill、流程、知识与审批管理；

- 支持配置草稿、影响分析、版本发布和审计；

## 29. 需要继续验证的关键问题

1. 用户更容易接受“员工”还是“专家”作为长期 Agent 身份；
2. 用户是否需要给员工自定义真实姓名，还是岗位名称已经足够；
3. 公司隔离应如何在本地文件、云端数据和外部账号之间统一表达；
4. 哪些任务属性最能准确决定团队和工作流；
5. 如何衡量并发带来的真实净收益；
6. 员工记忆、团队记忆和公司记忆的最佳边界是什么；
7. 哪类经验值得自动成为候选记忆；
8. 哪些能力升级可以自动批准，哪些必须由用户批准；
9. 如何防止绩效指标诱导 Agent 追求表面完成；
10. 通用领域执行者与语言专属工程师之间应如何取舍；
11. 用户愿意为组织能力、稳定性还是并发量付费；
12. 已确定 M1 直接采用 Agent SDK 与独立本地状态服务；仍需通过压测确定何时拆分 Sidecar、事件存储和调度 Worker 的进程边界；
13. 数据库已确定为组织与业务状态的权威来源；仍需验证 Git 备份、导出和同步在不形成双主时的最佳用户体验；
14. 用户是否愿意在 Web 中管理 Skill 版本和影响分析，还是只关心能力结果；
15. Web 与本地 Runtime 断线时，哪种任务状态和恢复表达最容易获得信任；
16. 成员配置变更应如何应用到正在执行的任务；
17. 哪些 Web 管理操作适合普通模式，哪些必须放入专家模式；
18. Agent Skills 开放规范已确定只承载通用 Skill 格式；仍需验证班底独立 Registry 的来源、权限、评测和版本元数据在用户界面中的最小必要集合；
19. Skill Federation、skills.sh 等目录与 GitHub Provider 的实际召回率、误匹配率、维护成本和许可证覆盖如何；
20. 第三方团队项目只作为 Runtime 模式与模板参考；仍需通过真实任务验证哪些 claim、wave 和质量门模式值得进入班底实现；
21. 用户是否能理解“搜索、安装、试用、授权和正式入职”是五个独立决定；
22. 哪些来源可以进入较高信任层，以及信任层如何随着版本和安全事件降级。

## 30. Web 与客户端经营管理端

### 30.1 产品定位

班底应提供 Web 管理端，并可以使用桌面客户端作为本地 Runtime、通知和系统权限的宿主。它不是 Skill 的装饰性界面，也不是只展示 Agent 配置的技术后台。产品定位为：

> **面向董事长的 AI 公司经营、任务指挥与能力治理中心。**

用户使用时应感受到：自己向董事长助理发出需求，助理把事情适配到对应公司、项目、部门、团队和成员，持续汇报执行状态、能力调用、资源消耗、风险与结果。底层 Agent、Skill、MCP、模型、工具、Workflow 和 Runtime 细节默认折叠，但始终可以追溯。

Web 与客户端尽量贴近现实创业公司的有效运行机制，包括交办、负责人制、团队协作、进度汇报、预算、审批、验收、复盘、补能和设人；不复制打卡、薪资、虚拟办公室、无效会议、虚构情绪和复杂层级。

推荐采用同一套响应式 Web UI：

```text
桌面客户端壳
├── 启动和守护本地班底服务
├── 自动发现 Claude Code、项目与本地能力
├── 承载本地 Runtime Connector
├── 系统托盘、通知和快捷审批
├── 本地凭据与操作系统权限
└── 内嵌同一套 Web UI

浏览器 Web
├── 董事长工作台
├── 公司、部门、团队与成员
├── 任务指挥中心
├── 能力、用量、审批与审计
└── 通过安全连接访问本地或云端 Runtime
```

这样用户可以获得客户端级本地集成，同时避免维护两套产品界面。

它帮助用户可视化管理所有事业空间和成员，理解系统如何组队、成员具备哪些能力、近期学会了什么、哪些任务正在进行，以及哪些操作等待批准。

长期管理端首版以“可视化管理”为主；M1 只实现 31.13 定义的单项目纵向闭环：

- Web 端负责配置、查看、筛选、审批和审计；
- Skill 负责自然语言入口、场景方法与用户交互；
- Custom Agent 负责成员角色与执行能力；
- Workflow 负责实际任务编排；
- Claude Code 或其他 Agent Runtime 负责工具调用与任务执行；
- Web 端不在浏览器中直接运行任意 Agent 命令，也不保存明文模型密钥。

### 30.2 用户价值

Web 管理端主要解决对话界面不擅长解决的问题：

1. 同时查看多个事业空间，而不是依赖用户记住上下文；
2. 可视化成员、职责、技能、模型策略和工具权限；
3. 比较成员能力、最近表现和当前负载；
4. 查看团队方案和做事方式之间的复用关系；
5. 集中处理审批、异常和待确认经验；
6. 管理系统已经学会、待确认、已过期和已禁止的知识；
7. 查看任务历史、交付物、成本和审计记录；
8. 让用户无需阅读配置文件即可管理组织，但保留高级配置入口。

### 30.3 Web 与对话入口的分工

| 用户任务 | 优先入口 | 原因 |
| --- | --- | --- |
| 下达一个新目标 | 对话或工作台输入框 | 自然语言表达最快 |
| 浏览全部事业空间 | Web | 需要列表、筛选和比较 |
| 管理成员和技能 | Web | 需要结构化编辑和影响预览 |
| 调整一次任务 | 对话或任务详情 | 取决于调整复杂度 |
| 审批高风险动作 | Web 审批中心 | 需要影响、证据和审计信息 |
| 查看执行进度 | Web | 适合时间线和任务图 |
| 查看最终交付 | Web 与对话均可 | 便于分享和继续追问 |
| 编辑底层 Agent 配置 | Web 专家模式或代码仓库 | 面向高级用户 |

Web 与 Skill 共享同一事实来源，不能分别维护两套公司、成员或任务状态。

- 总体成本；
- 成员负载；

默认不在全局视图混合展示私有文档内容、客户数据或成员的事业专属记忆。

### 30.6 董事长工作台

工作台首页围绕董事长的方向、战略、目标、关键决策和经营结果组织，而不是围绕系统对象组织。首屏以董事长助理为统一入口；助理判断由哪家公司承接，将目标交给该公司总经理，并允许董事长显式指定公司、项目、期限、优先级和预算。总经理负责形成执行方案、配置资源并组织团队，董事长无需逐项选择 Agent 或越级管理普通成员。

#### 页面结构

```text
向董事长助理交办事情

董事长助理简报
- 各公司重点、完成结果、异常、预算和待决策摘要

待你决定
- 三项发布审批
- 一项成员能力升级
- 一条冲突知识待确认

正在推进
- 产品网站开发 4/7
- 下周内容计划：事实核查中
- 市场研究：等待两个来源

需要关注
- Python 工程师任务预计超时
- 内容流程成本超过近期均值

最近交付
- 登录功能回归报告
- 三篇内容草稿
- 市场进入建议
```

#### 董事长交办入口

工作台提供自然语言输入框。用户提交后，董事长助理生成执行提案，先展示：

- 系统对方向、目标和约束的理解；
- 建议承接的公司及其总经理；
- 总经理拟定的主责部门、团队和执行方案；
- 交付物与验收标准；
- 团队负责人和推荐成员；
- 将使用的 Agent、Skill、MCP、工具、模型策略和做事方式摘要；
- 预计时间、Token 区间、费用和资源预算；
- 所需数据、工具和外部行动权限；
- 风险、依赖与明确排除范围。

低风险且处于既有授权范围内的任务可以直接分派；涉及公司归属不确定、跨事业数据、外部写入、高成本或不可逆动作时，必须先获得董事长确认。

低风险且完全落在预授权范围内时，系统可按已展示的提案直接创建任务；需要确认的任务必须在用户批准后创建。M1 直接通过本地 Runtime 执行，不另做只生成提案的“纯管理版 MVP”。

### 30.7 事业空间列表

事业页以卡片或表格展示：

- 名称和类型；
- 当前目标；
- 活跃任务；
- 长期成员；
- 本月成本；
- 待审批；
- 最近交付；
- 健康状态。

支持按类型、状态和标签筛选。用户可以新建：

- 公司；
- 品牌；
- 产品；
- 项目；
- 客户；
- 内容账号；
- 研究主题；
- 个人事务。

新建时只要求名称、类型和一句话目标。规则、成员和流程由第一次真实任务逐步形成，不展示长配置向导。

### 30.8 事业空间详情

详情页使用页签：

```text
概览 | 目标 | 部门 | 任务 | 团队 | 能力 | 流程 | 知识 | 权限 | 设置
```

事业空间尚未建立部门时，默认隐藏“部门”页签，并在团队页提供轻量入口。不能用空页面迫使用户先建立组织结构。

#### 概览

展示：

- 一句话使命；
- 当前目标；
- 活跃任务和关键阻塞；
- 核心成员；
- 常用做事方式；
- 最近学会；
- 本期成本；
- 待审批事项。

#### 目标

目标包含：

- 期望结果；
- 衡量指标；
- 时间范围；
- 当前进度；
- 关联任务；
- 负责人；
- 风险和复盘记录。

#### 权限

集中展示本事业空间：

- 可访问数据源；
- 可用模型；
- 可用工具；
- 外部写入策略；
- 发布审批规则；
- 预算上限；
- 跨事业共享规则。

#### 部门

部门列表展示：

| 部门 | 当前目标 | 长期成员 | 活跃任务 | 本期成本 | 状态 |
| --- | --- | ---: | ---: | ---: | --- |
| 产品与研发 | 缩短功能交付周期 | 5 | 7 | 120 | 正常 |
| 内容与品牌 | 稳定内容生产 | 4 | 3 | 75 | 有阻塞 |
| 增长与市场 | 验证获客渠道 | 3 | 2 | 90 | 正常 |

部门详情包含：

```text
概览 | 目标 | 成员 | 任务 | 团队方案 | 做事方式 | 知识 | 预算 | 权限 | 工作表现
```

部门管理支持：

- 创建、编辑、停用部门；
- 设置一个或多个长期目标；
- 关联默认团队方案和做事方式；
- 指定成员的主部门和服务部门；
- 查看跨部门本次执行小组；
- 配置部门知识、预算和权限；
- 查看成本、交付周期、返工和阻塞趋势。

不支持：

- 创建子部门；
- 把成员锁死在单一部门；
- 用部门归属代替能力匹配；
- 未经确认自动创建正式部门；
- 用拖拽组织树作为唯一管理方式。

组织视图同时提供部门卡片、成员关系矩阵和文本列表。成员关系矩阵用于查看主部门、服务部门和事业级共享成员；跨部门项目组单独显示，不改变成员长期归属。

#### 创建部门建议

系统仅在出现真实管理信号时建议创建部门：

- 长期成员数量增加，直接浏览困难；
- 任务稳定分成多个目标和知识体系；
- 某类数据需要权限隔离；
- 需要拆分预算和成本；
- 某类任务已经形成稳定成员和流程。

建议界面必须说明触发原因和预期变化，例如：

```text
最近二十个任务稳定分为软件交付和内容生产两类，
并使用不同知识与流程。

建议建立：
- 产品与研发
- 内容与品牌

建立后将改变默认任务归属、知识过滤和成本汇总，
不会限制跨部门组队。
```

用户可以选择：

```text
采用建议
调整部门
暂不需要
以后不再提醒此类建议
```

如果用户只是需要浏览分类，系统应提供“按职责、能力或项目临时分组”，不创建正式部门，也不改变权限、预算和路由。

### 30.9 团队总览

团队页默认显示成员表格：

| 成员 | 主要职责 | 主部门 | 服务部门 | 核心能力 | 当前负载 | 最近表现 |
| --- | --- | --- | --- | --- | --- | --- |
| Python 工程师 | 后端实现 | 产品与研发 | — | Python、FastAPI、SQL | 中 | 稳定 |
| 内容编辑 | 内容定稿 | 内容与品牌 | 增长与市场 | 中文编辑、品牌语气 | 低 | 已改善 |
| 质量验收 | 独立验收 | 事业级共享 | 全部 | 测试、事实核查 | 高 | 稳定 |

支持：

- 按职责、能力、事业空间、状态和负载筛选；
- 查看长期成员、临时专家和已停用成员；
- 比较两个成员的能力证据和成本；
- 批量调整可见标签，但高风险权限不能批量授予；
- 从岗位模板添加成员；
- 临时启用一次性专家；
- 停用或移出成员。

页面不使用虚拟办公室、在线头像墙或拟人化情绪状态作为主要信息。

### 30.10 成员详情

成员详情是 Web 管理端的核心页面，建议包含：

```text
概览 | 能力 | Skills | 工具与模型 | 记忆 | 工作表现 | 当前任务 | 变更记录
```

#### 概览

展示：

- 用户名称和职责；
- 状态与当前负载；
- 所属或可访问事业空间；
- 一句话职责；
- 最近完成任务；
- 最近能力变化；
- 风险提示。

#### 能力

每项能力展示：

- 名称；
- 当前等级；
- 适用范围；
- 证据数量；
- 最近验证时间；
- 首次验收通过率；
- 返工率；
- 固定评测表现；
- 已知薄弱点。

能力等级不能只由用户拖动修改。用户可以发起“重新评估”或“建议调整”，正式升级需通过评测或具有明确人工覆盖记录。

#### Skills

Skill 列表展示：

- 名称和版本；
- 来源；
- 解决什么问题；
- 适用和不适用范围；
- 所需工具；
- 是否随成员启动时加载；
- 最近使用；
- 评测状态；
- 更新可用状态。

用户可以：

- 添加已审核 Skill；
- 停用 Skill；
- 调整加载优先级；
- 查看版本差异；
- 在测试环境试用新版本；
- 通过评测后升级。

安装第三方 Skill 前必须显示来源、许可证、工具权限、网络访问和风险摘要。

#### 工具与模型

模型配置使用策略表达，而不是只绑定单一模型：

```text
默认模型：标准档
困难任务升级：高能力档
成本上限：每任务 2 美元
禁止模型：公司策略控制
```

专家模式可以展开具体模型 ID。工具权限按类别展示：

- 只读文件；
- 修改文件；
- 运行命令；
- 网络读取；
- 私有数据；
- 外部写入；
- 发布；
- 删除。

权限修改必须显示影响范围和最终生效结果，不能只显示员工级配置而忽略公司或任务级限制。

#### 记忆

按以下状态展示：

- 已确认；
- 待确认；
- 已过期；
- 已禁止。

每条记忆显示来源任务、适用范围、证据、最后使用时间和过期条件。用户可以将员工经验升级为团队或事业规则，也可以缩小作用域或停止使用。

#### 工作表现

展示趋势而不是单次排名：

- 验收通过率；
- 返工率；
- 平均完成周期；
- 成本；
- 高风险违规；
- 交接完整度；
- 最近评测；
- 与自身历史基线的变化。

不同职责不使用同一个综合分数，也不鼓励以任务数量进行跨岗位排名。

### 30.11 能力中心

能力中心从“组织目前能可靠完成什么”出发，而不是从员工名单出发。

#### 能力目录

能力卡包含：

- 能力名称；
- 适用领域；
- 具备该能力的成员；
- 最高和平均验证等级；
- 最近使用；
- 关联 Skill；
- 关联评测；
- 是否存在人员单点风险。

#### 能力缺口

系统根据近期任务和失败记录识别：

- 完全缺失的能力；
- 只有一名成员具备的关键能力；
- 长期负载过高的能力；
- 评测已过期的能力；
- 任务需求增长但表现下降的能力。

系统可以建议：

- 培养现有成员；
- 临时启用专家；
- 添加长期成员；
- 调整流程；
- 降低任务范围。

建议不等于自动设岗、添加成员或授权。

#### 岗位与人才寻访

能力中心增加“岗位”和“人才寻访”两个关联视图：

```text
岗位
├── 任务职责
├── 建议中岗位
├── 试行岗位
├── 正式岗位
└── 已停用岗位

人才寻访
├── 待处理能力缺口
├── 内部匹配
├── Find Skill 候选
├── GitHub 与其他外部候选
├── 安全审查
├── 试用与评测
└── 入职与停用记录
```

岗位建议页必须说明：

- 哪些真实任务产生了该职责；
- 为什么不能由现有岗位覆盖；
- 预计出现频率和长期价值；
- 必需能力、交付物和验收标准；
- 是否要求独立性；
- 试行或正式设岗建议；
- 合并已有岗位、临时职责和缩小范围等替代方案。

候选成员页面采用方案卡和比较表，而不是直接展示仓库列表。每个方案展示角色定义、能力覆盖、组件来源、固定版本、许可证、维护状态、所需权限、风险摘要、预计成本和评测结果。用户可以选择：

```text
给现有成员补充能力
临时启用此候选
添加为长期成员
组合候选中的安全部件
继续寻找
缩小任务范围
暂不设人
```

#### 设人向导

当任务存在未覆盖的关键职责时，系统启动渐进式向导：

```text
第一步：解释为什么需要该职责
第二步：判断一次性职责、试行岗位或正式岗位
第三步：展示现有成员与内部能力匹配
第四步：在用户允许时搜索 Find Skill 和 GitHub 等外部来源
第五步：展示标准化候选和风险影响
第六步：用户选择试用方案
第七步：隔离试用与岗位评测
第八步：用户批准补能、临时启用或长期加入
```

用户可以随时退出并采用降级方案。系统不得把“允许搜索外部资源”解释为“允许安装、运行或赋予数据权限”。

#### 资源安全与影响页

第三方资源详情至少包含：

- 原始来源和发现渠道；
- 仓库、发布版本和固定提交；
- 许可证及兼容性；
- 文件、依赖和安装脚本摘要；
- 工具、网络和数据访问；
- 外部写入与不可逆动作；
- 提示注入和配置覆盖风险；
- 维护活跃度和已知风险；
- 将影响哪些成员、岗位和流程；
- 隔离试用结果；
- 停用和回退方式。

来源页中的 README、代码注释和第三方说明均作为待审查数据展示，不能改变产品规则或触发工具调用。

### 30.12 Skill 管理

Skill 中心是能力中心的子模块或专家模式页面，支持：

```text
已安装 | 可更新 | 待审核 | 已停用 | 来源与许可证
```

每个 Skill 详情包含：

- 稳定 ID；
- 用户可见名称；
- 技术名称；
- 描述；
- 版本；
- 来源和许可证；
- 适用场景；
- 输入输出；
- 允许工具；
- 依赖；
- 哪些成员正在使用；
- 哪些流程依赖它；
- 评测结果；
- 最近变更；
- 风险记录。

停用或升级 Skill 前，Web 必须展示影响分析：

```text
该 Skill 被 3 名成员和 2 个流程使用。
停用后，软件审查流程将回退到基础检查。
```

### 30.13 团队方案管理

团队方案页展示一类任务的推荐角色组合：

- 适用场景；
- 必选职责；
- 条件职责；
- 最大人数；
- 协调方式；
- 默认验收者；
- 成本和并发限制；
- 最近运行表现；
- 当前版本。

采用可读规则而不是只提供画布：

```text
软件功能交付团队

始终需要
- 任务分析
- 实现
- 验收

按条件加入
- 修改 UI：界面审查
- 涉及认证：安全审查
- 修改共享协议：契约审查
```

用户可以克隆、调整并在沙盒任务中评测新版本。稳定版本不能被未经评测的修改直接覆盖。

### 30.14 做事方式与流程画布

流程页面同时提供列表视图和任务图视图。

列表视图适合普通用户，显示：

- 阶段；
- 负责人；
- 输入；
- 输出；
- 是否并行；
- 验收门禁；
- 失败降级。

图视图适合专家用户，支持：

- 添加阶段；
- 设置依赖；
- 设置并行分支；
- 绑定职责而非固定成员；
- 配置条件路由；
- 配置预算和超时；
- 设置审批点；
- 设置验证和回退；
- 查看历史版本差异。

流程发布前必须通过结构检查：

- 是否存在无负责人阶段；
- 是否存在循环依赖；
- 是否缺少最终验收；
- 并行任务是否存在写入冲突；
- 高风险动作是否设置审批；
- 是否存在无限重试；
- 最坏情况下的成员数和预算是否超限。

### 30.15 任务指挥中心

任务中心支持列表、看板、时间线和执行图四种视图。它既要呈现现实公司的交办、负责人、协作、交接和汇报，也要允许深入检查底层真实调用。

每个任务至少显示：

- 董事长原始交办和结构化目标；
- 所属公司、项目、部门和承接团队；
- 当前状态；
- 负责人和执行小组；
- 当前阶段；
- 截止时间；
- Token、费用和已用时间；
- Skill、MCP、工具与模型调用摘要；
- 风险；
- 等待谁处理；
- 最近事件。

任务详情页包含：

```text
董事长摘要 | 执行计划 | 作战图 | 成员 | 能力调用 | 交付物 | 交接 | 验收 | 用量 | 审计
```

董事长摘要以管理层语言说明完成了什么、当前风险、预算状态、预计完成和待决策事项；作战图显示阶段依赖、并行、负责人、交接和阻塞；能力调用显示 Agent 版本、Skill、MCP、工具、模型、知识和有效权限；用量页支持按公司、团队、成员、阶段和能力部件归集 Token、费用、耗时、失败与重试。

默认展示结构化事件和交接摘要，不默认暴露完整内部推理。用户可以查看 Agent 的可公开工作日志、工具调用和结果证据。

### 30.16 经营用量中心

经营用量中心用于回答“资源花在哪里、是否值得、哪里可以优化”，而不是只展示总 Token。

至少提供以下维度：

```text
按归属
公司 → 部门 → 团队 → 项目 → 任务

按执行
阶段 → 成员 → Agent 版本 → 模型

按能力
Skill → MCP Server/Tool/Resource → 本地工具 → Workflow

按结果
完成 → 验收通过 → 返工 → 失败 → 重试 → 取消
```

核心指标包括：

- 输入、输出、缓存读取、缓存写入和其他 Provider Usage；
- 实际费用与估算费用；
- Agent、Skill、MCP 和工具调用次数；
- 运行时间、等待时间、阻塞时间和并发收益；
- 失败、重试、超时和取消造成的资源浪费；
- 单次任务、单项交付和首次验收通过的平均成本；
- 能力调用与有效交付、缺陷发现、返工下降之间的关联。

数据展示规则：

- Provider 或 Runtime 返回准确数据时标记为实际值；
- 通过字符、时间或历史基线推算时标记为估算值并说明方法；
- 无法可靠归因到某个 Skill 或 MCP 时，不强行分摊；
- Token、调用次数和忙碌时长都不是绩效指标，必须结合结果和质量解释；
- 预算接近阈值时，董事长助理应提出暂停、降级模型、减少成员或申请追加预算等方案。

### 30.17 MCP 与连接器管理

MCP 与连接器中心是能力中心的专家模块，统一管理：

```text
已连接 | 连接异常 | 待授权 | 可更新 | 已停用 | 风险事件
```

每个 MCP Server 详情至少展示：

- 名称、稳定 ID、来源、版本和运行位置；
- 连接状态、认证 Profile 或账号的安全标识；
- 暴露的 Tools、Resources 和 Prompts；
- 每项能力的读取、写入、发送、发布、删除和费用属性；
- 可访问的公司、项目和数据范围；
- 被哪些成员、团队和 Workflow 使用；
- 最近调用、失败、重试、耗时和外部费用；
- 更新影响、风险记录、停用和回退方式。

授权界面必须支持 Server 级、能力级、资源级、账号级和任务级范围，不提供默认永久开放全部能力的快捷方式。一个成员绑定 MCP 后，最终仍以公司、成员、任务和具体调用共同计算的最小有效权限执行。

### 30.18 例行任务与自动经营

除一次性交办外，班底应支持由公司持续承担的例行任务，例如日报、周报、内容排期、数据巡检、客户跟进、代码健康检查和市场动态监测。

每个例行任务至少配置：

- 所属公司、责任总经理、团队负责人和执行小组规则；
- 触发方式：定时、事件或人工；
- 使用的 Workflow、Harness、成员与能力快照；
- 单次和周期预算、超时、并发与重试上限；
- 数据权限、外部行动和发布审批策略；
- 成功验收标准、失败升级对象和暂停条件；
- 最近执行、下次计划、连续失败、累计成本和有效产出。

Hermes Studio 的 Jobs/Cron 交互可以作为任务创建、暂停、触发、输出查看和状态展示参考，但班底必须增加公司责任、预算、审批和经营验收。例行任务默认不得无人值守执行发布、删除、付费或其他高风险动作。

### 30.19 知识与“已学会”

知识页不是普通文件管理器，而是公司规则、项目事实和经验治理中心。

支持：

- 按事业、项目、团队和成员过滤；
- 查看权威来源；
- 查看候选经验；
- 处理冲突；
- 设置适用范围和过期时间；
- 查看哪些任务使用了某条知识；
- 撤销或禁止继续使用；
- 比较版本。

如果实时源码、正式文档或配置与历史记忆冲突，页面应明确标识权威来源优先，并把冲突加入待处理列表。

### 30.20 审批中心
审批中心集中处理：

- 外部发布；
- 文件或线上数据删除；
- 破坏性数据库操作；
- 建立正式岗位；
- 新增长期成员；
- 提高预算；
- 权限提升；
- 跨事业共享知识；
- 第三方 Skill、Agent 模板、Workflow、MCP 或工具安装；
- 能力正式升级；
- 稳定流程版本替换。

每项审批必须显示：

- 请求者；
- 目标事业；
- 要执行的动作；
- 影响范围；
- 可逆性；
- 预计成本；
- 支持证据；
- 拒绝后的降级路径；
- 授权是否仅限本次。

用户可以批准、拒绝或要求调整，但不能用一个“全部允许”按钮永久打开所有高风险权限。

审批不是 UI 确认记录。每个 `Approval` 必须绑定精确动作、规范化参数哈希、目标资源版本、Task/WorkflowRun、ExecutionConfigSnapshot、金额、有效期、一次性消费状态和幂等键。参数、文件 diff、收件人、金额、有效权限环境或目标版本变化后，旧审批立即失效；Runtime 只能消费一次匹配且未过期的批准。

预算不能只做事后 Usage 汇总。执行前按最坏可接受成本 `reserve`，执行中 `consume`，结束后 `settle` 或 `release`；达到硬上限时进入 `BudgetExhausted`，由明确的追加预算审批或降级方案恢复。

### 30.21 搜索与命令面板
全局搜索支持：

- 事业空间；
- 成员；
- 能力；
- Skill；
- 任务；
- 交付物；
- 知识；
- 审批。

命令面板支持低风险导航和创建操作，例如：

```text
新建任务
切换事业空间
查看待审批
查找具备 Python 能力的成员
查看依赖 code-review Skill 的流程
```

高风险动作不能只通过模糊搜索命令立即执行，仍需进入影响确认界面。

### 30.22 响应式和无障碍要求
- 桌面端优先支持复杂管理和流程图；
- 移动端优先支持查看进度、处理审批、快速下达任务和阅读交付；
- 宽表格在容器内横向滚动，不让页面整体横向滚动；
- 所有状态不能只依赖颜色表达；
- 任务图提供等价列表视图；
- 支持键盘导航、焦点状态和屏幕阅读器；
- 图表和能力等级提供文本解释；
- 深浅色模式使用统一主题 Token；
- 用户可降低动效；
- 不使用拟人化头像作为唯一身份标识。

### 30.23 通知设计
通知只用于需要用户及时行动的事项：

- 审批即将超时；
- 高风险任务被阻塞；
- 预算即将用尽；
- 任务失败且无法自动降级；
- 外部系统授权失效。

普通进度变化保留在工作台和任务时间线，不用大量通知制造“团队很忙”的假象。

## 31. Web 数据与集成架构

### 31.1 单一事实来源

Web、Skill 和 Runtime 必须共享统一组织数据。不能出现：

- Web 中有一套成员，Claude Code 配置中又有另一套成员；
- Web 修改 Skill 后，实际执行仍使用旧版本；
- Runtime 完成任务后，Web 状态没有更新；
- 文件记忆和数据库记忆互相覆盖。

从原型期开始就使用明确的事实来源矩阵，避免 Git 文件和数据库成为同一业务聚合的双主：

| 事实 | 权威来源 |
| --- | --- |
| 事业空间、部门、岗位、成员绑定、Task、WorkflowRun、Approval、Audit、Budget、Usage 和记忆元数据 | 班底 SQLite；Local Service 是唯一业务写入者 |
| Agent、Skill、MCP、Rules 等来源资产正文 | 原 Harness 文件；班底保存索引、哈希、版本、解析结果和组织绑定 |
| 本次运行配置 | 启动前生成的不可变 `ExecutionConfigSnapshot` |
| 当前执行现场 | Runtime 原始事件进入班底 Event Store 后形成的投影 |
| 凭据 | 系统钥匙串或受支持的密钥管理系统 |
| Web 未发布编辑 | 草稿，不是执行事实 |
| 备份、导出和多设备同步 | Git；不与 SQLite 共同作为同一聚合的主库 |

任务结束后形成的是 `ExperienceCandidate`，经审核和评测后才能进入长期记忆或新配置版本；它与启动前的 `ExecutionConfigSnapshot` 分离，不能改写本次执行证据。

### 31.2 Claude Code 本地配置映射

班底必须尽可能完整地发现并映射 Claude Code 的本地能力配置，而不只映射 Custom Agent。当前重点对象包括：

| Claude Code 本地对象 | 典型来源 | 班底中的映射 |
| --- | --- | --- |
| Custom Agent | 用户级、项目级和插件提供的 Agent 目录 | AI 成员、Agent 定义与版本 |
| Agent Skill | 用户级、项目级和插件提供的 Skill 目录 | 专业能力、方法和质量门禁 |
| `CLAUDE.md` 与 Rules | 用户级、项目级和目录级指令文件 | 全局规则、公司制度、项目规则和知识边界 |
| Settings | 用户、项目、本地覆盖和受管配置 | Runtime、权限、Hook 和行为策略 |
| MCP | 用户配置、项目 `.mcp.json`、插件或受管来源 | MCP Server、连接器和远程能力 |
| Hooks | Settings 或插件 Hook 定义 | 自动门禁、事件处理和治理规则 |
| Plugins | 已安装或启用的插件及其组件 | Agent、Skill、MCP、Hook 和命令的来源包 |
| Commands | 插件或兼容目录中的命令文件 | 兼容型 Skill 或可调用能力 |
| Memory | 用户、项目和自动记忆文件 | 用户、公司、项目、团队与成员记忆 |
| Workflow 与脚本 | 班底 Registry、项目脚本或 Runtime 能力 | 团队做事方式和可执行任务图 |

实际路径不能全部写死。Claude Code 可以从用户级目录和当前项目加载配置，用户还可能通过环境设置改变全局配置根目录；插件、企业受管配置和未来版本也可能引入其他来源。因此 `ClaudeCodeRuntimeAdapter` 必须动态报告：

- 当前有效配置根目录；
- 当前工作区和项目根目录；
- 每项资产的真实来源、作用域和发现方式；
- 配置优先级、继承和覆盖关系；
- 资产是否只读、受管、来自插件或允许编辑；
- Claude Code 当前是否实际识别和加载；
- 当前项目和任务是否拥有有效权限使用。

班底保存的是结构化索引、组织映射、版本、依赖、摘要和证据，不应静默复制后脱离来源文件。每项本地资产至少记录：

```yaml
id: local-agent-code-reviewer
runtime: claude-code
kind: custom-agent
scope: user
source:
  path: ~/.claude/agents/code-reviewer.md
  origin: filesystem
  editable: true
content_hash: fixed-content-hash
parse_status: valid
runtime_status: discovered
organization_bindings:
  - employee-software-reviewer
project_bindings:
  - project-a
  - project-b
```

#### 来源资产与组织成员的关系

本地文件与组织对象不是简单一一对应：

```text
一个 Agent 文件
→ 可以形成零个或多个成员绑定建议
→ 不能因扫描发现而自动创建长期成员

一个成员
→ 可以由 Agent、多个 Skill、MCP、工具、模型策略、项目规则和记忆共同组成

一个 Agent 模板
→ 可以被多个公司或项目成员复用
→ 每个成员拥有不同知识、权限、MCP 账号、版本绑定和工作表现
```

因此，班底不是 Claude Code 配置目录的文件浏览器，而是建立“本地来源资产—能力部件—组织成员—公司项目—实际任务”之间的关系图。

#### 配置状态分层

文件存在不等于当前任务可以使用。界面必须区分：

```text
已发现
→ 已读取
→ 已解析
→ 配置有效
→ Claude Code 已识别
→ 当前项目可用
→ 当前任务已授权
→ Runtime 实际加载
→ 本次执行已调用
```

Agent 可能因为格式错误、作用域不符、Skill 缺失、MCP 离线、模型不可用、权限不足或受管策略限制而不可用。系统不能仅因发现文件就显示“已启用”或“正在使用”。

### 31.3 Web 管理的数据对象

长期管理端首版按阶段逐步管理；M1 的实际子集以 31.13 为准：

- 事业空间；
- 事业规则；
- 部门；
- 部门目标、规则、预算和权限；
- 成员与部门关系；
- 任务职责与岗位；
- 岗位建议和试行状态；
- 成员；
- 能力与能力缺口；
- 资源来源和发现记录；
- 候选资源与候选成员组合；
- 供应链审查和试用记录；
- Agent 来源资产、Agent 定义与版本；
- Skill 及版本；
- MCP Server、能力、账号安全标识、授权与调用；
- Hooks、Plugins、Commands、Settings 与 Rules 索引；
- 本地配置来源、作用域、继承、覆盖、哈希与解析状态；
- 本地来源资产、组织成员和项目绑定关系；
- 团队方案；
- 做事方式；
- 任务与状态；
- 交付物索引；
- 知识和候选经验；
- 评测结果；
- 审批；
- 审计事件；
- 预算摘要；
- Runtime 连接状态。

### 31.4 打开来源文件与目录

每个映射到本地配置的 Agent、Skill、MCP、Rule、Hook、Plugin、Command、Workflow 和项目对象，都应提供与来源类型相符的快捷操作：

- 打开原始文件；
- 使用用户指定的编辑器打开并定位到文件或行；
- 在 Finder、资源管理器或 Linux 文件管理器中显示；
- 在终端中打开所属目录；
- 打开所属 Claude Code 项目或代码仓库；
- 复制绝对路径、项目相对路径或安全缩略路径；
- 查看原始 Markdown、JSON、YAML 或其他配置；
- 查看该目录下被 Claude Code 发现的相关资产；
- 查看上游来源、下游成员、项目、Workflow 和任务依赖。

界面示例：

```text
名片岛 Web 工程师

底层映射
- 用户级 Agent：~/.claude/agents/software-engineer.md
- 项目级 Agent：<项目>/.claude/agents/web-engineer.md
- 项目规则：<项目>/CLAUDE.md
- Skills：4 项
- MCP：代码托管、数据库只读
- Workflow：功能交付 v4

操作
打开 Agent 文件
打开项目配置目录
在编辑器中打开
在终端中打开目录
查看完整能力包
查看依赖与影响
测试当前配置
```

桌面客户端可以通过操作系统能力直接完成这些操作。普通浏览器不能任意扫描或打开用户本地路径，因此浏览器 Web 必须通过用户已授权的 Local Connector 发出请求；Connector 离线或未授权时，只显示已同步索引和“连接本机后打开”，不能伪装操作成功。

“查看”“打开”和“修改”必须使用不同权限。建议最少区分：

```text
发现资产
读取元数据
读取完整内容
打开本地文件或目录
创建编辑草稿
发布到本地配置
移动、停用或删除配置
```

远程 Web 不应获得通用文件系统访问能力。打开请求只允许作用于已经发现、位于授权根目录内并通过路径校验的资产，防止路径穿越、任意命令拼接和跨项目越权。

### 31.5 配置发布与双向同步模型

管理变更采用草稿和发布模型：

```text
Discovered
→ Parsed
→ Validated
→ BindingProposed
→ BindingApproved
→ ConfigDraft
→ ImpactAnalyzed
→ PublishApproved
→ AtomicallyWritten
→ RuntimeRediscovered
→ RuntimeLoadVerified
→ Released
```

发布前保存共同基线哈希，执行 dry-run、结构/依赖检查、影响分析和文件差异；发布时使用同目录临时文件、fsync、原子替换、备份和可验证回滚。`RuntimeLoadVerified` 必须来自 Runtime init/capability 报告、受控探测任务或其他可重复证据，不能由“文件存在”推断。

本地文件仍可以由用户、编辑器或 Claude Code 直接修改。Local Connector 应监听已授权配置根目录：

```text
本地文件变化
→ 稳定等待并读取新版本
→ 重新解析和计算内容哈希
→ 与班底索引比较
→ 更新来源资产
→ 分析成员、项目和 Workflow 影响
→ 必要时标记待确认或重新评测
```

当 Web 草稿和本地文件同时变化时：

- 禁止静默覆盖；
- 保留共同基线、本地版本和 Web 草稿；
- 展示三方差异并要求合并；
- 受管或插件只读资产不能被直接写回；
- 外部文件被移动或删除时，先标记失联并分析影响，不自动删除组织成员；
- 正在执行的任务继续使用启动时的不可变配置快照。

只有安全修复或用户明确要求时，才把新配置应用到运行中任务。配置发布完成不等于 Runtime 已生效；必须等待 Claude Code 重新发现并报告真实加载状态。

### 31.6 Runtime 连接器

Web 与执行 Runtime 通过适配器通信，统一契约至少包括：

```text
注册 Runtime
报告可用模型和工具
下发结构化任务
接收任务状态事件
接收 Agent、Skill、MCP、工具和模型调用事件
接收准确或估算的 Token、缓存、费用、耗时、失败与重试 Usage
提交审批请求
接收审批结果
上传交付物索引
提交候选记忆
提交评测结果
停止或恢复任务
```

Claude Code 适配器可以负责：

- 发现有效配置根目录、当前项目和用户级、项目级、插件级及受管来源；
- 索引 Agent、Skill、CLAUDE.md、Rules、Settings、MCP、Hooks、Plugins、Commands、Memory 和 Workflow；
- 报告每项资产的作用域、来源、优先级、继承、覆盖、可编辑性和实际加载状态；
- 执行经过路径校验和用户授权的打开文件、显示目录、打开编辑器或终端请求；
- 监听本地配置变更并回传结构化差异；
- 将已批准的成员执行配置生成受控 Custom Agent 快照；
- 在策略允许时，把某个耐久 Workflow Step 可选映射为 Runtime 内部 Dynamic Workflow；M1 默认禁用，且不能用它替代班底 WorkflowRun；
- 在隔离配置根或任务工作区生成受控 Skill 文件快照，并验证 Runtime 实际发现；SDK 不提供脱离文件系统的纯程序化 Skill 注册；
- 发现、校验并授权 MCP Server 暴露的 Tools、Resources 与 Prompts；
- 启动任务并回传状态；
- 回传 Agent、Skill、MCP、工具、模型调用与 Usage；
- 把本地交付物位置和验证结果同步给 Web。

### 31.7 Claude Agent SDK 运行边界

M1 固定并契约测试 `@anthropic-ai/claude-agent-sdk@0.3.247`（仓库 `v0.3.247` / `40b4c54…`）和受支持的 Claude Code 版本。任务使用专用工作目录或 Git worktree，并至少设置：

```text
settingSources: []
独立 CLAUDE_CONFIG_DIR
CLAUDE_CODE_DISABLE_AUTO_MEMORY=1
CLAUDE_CODE_DISABLE_BUNDLED_SKILLS=1
disableClaudeAiConnectors=true
strictMcpConfig=true
显式 tools、skills、agents、MCP、systemPrompt 和环境变量
permissionMode=dontAsk + PreToolUse Policy Hook
```

`settingSources: []` 只关闭用户、项目和本地文件系统配置来源；不单独构成完整隔离。`allowedTools` 只决定哪些工具自动批准，缩小工具集合必须使用 `tools`。M1 禁止 `bypassPermissions`，并通过 `system/init` 比对 model、tools、MCP 和 plugins 与 ExecutionConfigSnapshot 是否一致。

SDK 能提供 Session ID、流式消息、Tool/Hook 事件、interrupt、resume、Subagent 关联和 Usage，但边界如下：

- Session 与 `SessionStore` 保存 transcript，不保存 Task/WorkflowRun，也不恢复文件、Git、数据库、部署和外部副作用；
- `SessionStore` 是本地 transcript 的双写镜像，可能出现 `mirror_error`，不能作为 Event Store 或审计账本；
- File Checkpointing 只覆盖 `Write`、`Edit`、`NotebookEdit` 的部分变化，不覆盖 Bash、绝大多数 Subagent、MCP 或外部系统；
- Dynamic Workflows 只可作为 Step 内策略，不能作为耐久 Workflow Engine；
- Agent Teams 是实验能力，非交互 SDK 下不能作为真实 teammate Runtime，也不能完整恢复；
- `total_cost_usd` 和 `modelUsage` 是客户端价格表估算，不是 Provider 账单；Result 与 Assistant 字段对子 Agent 的覆盖不同，崩溃时最终汇总可能缺失。

Usage 记录必须带 `ProviderReported`、`SdkEstimated` 或 `Inferred` 来源，估算值不得用于最终用户计费或财务结算。SDK 受 Anthropic Commercial Terms 约束；内部实施不被阻断，对外发布前必须完成条款、认证、数据处理和再分发复核。

### 31.8 同步策略

原型期建议：

- Web 只管理结构化配置和索引；
- 大文件、源码和交付物仍保存在原项目或文件系统；
- Web 保存引用、摘要、哈希、版本和访问权限；
- Runtime 主动推送原始事件，由 Local Service 通过 Outbox 持久化后更新业务投影；
- Local Connector 监听已授权的 Claude Code 配置文件变化；
- 文件事件需防抖、重新读取和内容哈希确认，不能把一次保存过程误判为多个正式版本；
- 每个 Event Stream 使用稳定 stream ID、单调序号和事件幂等键；客户端按 ID 去重；
- SSE 建连采用“先订阅或先固定数据库高水位，再补播，最后连续转入实时流”，消除补播与订阅之间的丢事件窗口；
- 断线后使用 `Last-Event-ID` 补传，若事件已过保留期则返回明确的 snapshot/resync 指令；
- 冲突时保留共同基线、本地版本和 Web 草稿并要求合并，禁止静默覆盖；
- Connector 重连后重新扫描关键来源，并将未决执行先标记 `Unknown` 后对账，修复离线期间遗漏的文件和 Runtime 事件。

### 31.9 凭据管理

- 浏览器不保存明文模型密钥和外部服务凭据；
- Web 只展示连接状态、作用域和最后使用时间；
- 凭据由本地 Runtime、系统钥匙串或服务端密钥管理系统保存；
- 成员只能获得短期、最小作用域令牌；
- 停用成员或连接器时及时撤销；
- 日志和交付物不得泄露密钥值。

### 31.10 权限模型

MVP 可先使用单用户，但数据模型应支持未来角色：

- 主理人；
- 事业负责人；
- 执行者；
- 审批者；
- 观察者。

有效权限按集合交集和显式拒绝计算：

```text
EffectivePermission
= PlatformCeiling
∩ UserCeiling
∩ OrganizationCeiling
∩ DepartmentOrProjectCeiling
∩ MemberCeiling
∩ TaskGrant
- ExplicitDenies
```

每项决策至少记录 subject、action、resource、condition、provenance、expiry 和 revocation。允许 Bash 时必须检查规范化命令、工作目录、重定向、Git、网络和部署副作用；禁止用“关闭 Write/Edit”推断文件不可修改。Claude Code 中 `allowedTools` 只表示自动批准，不负责限制可见工具；工具集合使用 `tools` 收窄，参数级和关键调用通过 `PreToolUse` Hook 进入班底 Policy Engine。禁止 `bypassPermissions`。

最终界面展示计算后的有效权限及其来源，显式拒绝优先。子 Agent 继承父会话权限，不能假设自然形成成员级安全隔离。

### 31.11 审计和隐私

Web 对以下操作生成审计事件：

- 成员、Skill 和流程变更；
- 权限与预算变更；
- 知识写入、升级、过期和删除；
- 审批；
- Runtime 启停；
- 外部写入；
- 跨事业共享；
- 配置发布和回滚。

不同事业空间默认隔离。全局管理员能够看到汇总状态，不代表可以读取所有私有内容；内容访问仍按事业权限控制。

### 31.12 Web 技术实现建议

产品化 Web 可以采用前后端一体框架加关系数据库：

- Web：React/Next.js 或等价成熟框架；
- 数据库：PostgreSQL；
- ORM：根据团队技术栈选择；
- 后台任务：持久任务队列；
- 实时状态：SSE 或 WebSocket；
- 对象存储：保存上传交付物和附件；
- 认证：支持个人账户，后续扩展组织成员；
- Runtime：独立本地 Agent 或服务端 Worker；
- 事件模型：可恢复、幂等、有序事件。

具体技术栈不应写死在 Skill 中；Skill 只依赖稳定的组织与任务契约。

### 31.13 M1 本地管理界面范围

M1 不是完整 Web 管理平台，只实现支撑单一纵向闭环的本地响应式界面：

1. 董事长工作台、目标交办入口和助理简报；
2. 单项目上下文，无需用户先创建公司、部门或总经理；
3. 本地 Claude Code Runtime 状态和隔离配置快照；
4. Agent、Skill、MCP、Rules 等资产的只读发现、来源、作用域、哈希和解析状态；
5. 成员与能力绑定建议，不自动创建长期成员；
6. 任务提案、职责、最小临时团队、验收标准和用户覆盖；
7. 任务列表、详情、时间线、交付物和独立验收结果；
8. 一类高风险动作审批，显示精确动作、参数/差异、范围、有效期和消费状态；
9. Runtime 事件、Usage 来源/估算标记、预算预留和基础审计；
10. ExperienceCandidate 的查看、批准或拒绝；
11. 崩溃后 `Unknown` / `ReconciliationRequired` 对账界面。

M1 本机总览只展示完成当前闭环所需的配置根目录、项目、Agent、Skill、MCP、Rules、解析错误、Runtime init 中的实际工具/MCP/Plugin 和离线状态。默认不读取或展示凭据值。

M1 暂不实现：

- 外部 Provider 和 GitHub 资源自动安装；
- Skills Manager 跨 Harness 写入、撤销和 Git 同步；
- 配置双向同步、三方合并和完整发布管理；
- 公司、部门、岗位、共享成员和复杂长期组织管理；
- 自动内容生产、例行任务和事件驱动经营；
- 完整可视化流程编辑器；
- 云端 Web、远程 Connector、移动端和多真实用户协作；
- 多 Runtime、第三方能力市场和跨供应商迁移；
- Agent Teams 和以 Dynamic Workflow 作为业务引擎；
- 复杂计费、无人值守外部发布和无限历史事件；
- 浏览器内任意 Shell 或虚拟办公室。

外部能力在后续阶段也严格限制为发现、元数据读取、静态分析、固定版本和隔离试用；不允许发现后自动进入正式 Runtime。

### 31.14 M1 验收标准

- 用户无需预建公司、部门、总经理或固定员工，即可从一个目标开始软件任务；
- 系统从目标形成任务画像、边界、可验证验收标准和必要职责，不把一次性职责自动建成长期岗位；
- 扫描发现的 Agent 文件只形成绑定建议，不自动创建成员或获得权限；
- 每次执行生成可查看且不可变的 ExecutionConfigSnapshot，包含模型、Prompt、Agent、Skill、MCP、工具、权限、规则和版本证据；
- SDK `system/init` 的实际工具、MCP、Plugin 与配置快照完成比对；不一致时不能显示“已加载”；
- Runtime 运行在专用工作目录，默认不加载宿主用户/项目配置、自动记忆、云端 MCP Connector 和未批准 Skill；
- 所有业务状态和事件先持久化到班底 SQLite，再投影到界面；Node Sidecar 不直接写业务数据库；
- SSE 断线后能按事件 ID 连续补播并去重，补播和实时订阅之间没有可复现的丢事件窗口；
- Task、StepRun 和 ExecutionAttempt 具有幂等键、lease、heartbeat、fencing token、超时、有限重试和取消语义；
- Runtime 崩溃或失联后任务先进入 `Unknown` 并对账，不会把 SDK Session 恢复误当成业务恢复；
- 外部副作用无法确认时进入 `ReconciliationRequired`，不会自动重放；
- 一类高风险动作在执行前被 Policy Gate 拦截；批准绑定精确参数/差异、资源版本、配置快照、有效期和一次性消费状态；
- 预算在执行前预留，执行中消费，结束后结算或释放；达到硬上限进入 `BudgetExhausted`；
- 用户能查看任务、临时团队、进度、阻塞、风险、预算、交付物和待审批，并下钻到 Runtime 证据；
- 软件结果经自动门禁和独立 Verifier 验收，执行者不能自行宣告最终通过；
- Assistant 与 Result Usage 被去重并保留来源；`total_cost_usd` 明确标为 SDK 估算，无法可靠归因时不伪造 Skill/MCP 级 Token；
- 任务后只生成 ExperienceCandidate；未经审核不会修改长期记忆、成员能力或稳定 Workflow；
- Runtime 离线或 Connector 失败时界面明确显示不可执行或待对账，不伪装为运行或成功；
- 普通用户无需理解模型 ID、Agent 文件和 Workflow 代码即可完成核心任务，专家用户仍能追溯底层配置、事件和审计证据。

### 31.15 Web 后续演进

#### 第二阶段：本地管理增强

- 公司、部门、岗位、长期成员和共享关系管理；
- 能力缺口、候选装配、隔离试用和岗位评测；
- 只读外部 Provider、GitHub 链接导入和供应链审查；
- 配置草稿、影响分析、原子发布、回滚、三方合并和实际加载验证；
- Skills Manager 实验 Provider 与受控跨 Harness Skill 分发；
- 工作流版本比较、任务回放和成本趋势；
- 自动内容生产作为第二类任务。

#### 第三阶段：平台化

- 云端 Web、远程 Connector、移动审批和多设备同步；
- 多用户和事业权限；
- Skill 与团队方案市场；
- 多 Runtime；
- 定时和事件驱动任务；
- 组织级评测中心；
- 更完整的外部数据连接器。

### 31.16 Web、客户端与 Skill 的最终关系

Web 不替代 Skill，Skill 也不承担完整 Web 后台职责；桌面客户端提供本地集成和运行宿主，但不建立第二套组织事实或界面模型。三者形成互补：

```text
董事长助理
负责理解需求、路由公司与团队、监督执行、升级异常和汇报结果

Skill
负责让用户用自然语言表达目标、获得方法和推进任务

Web
负责董事长工作台、公司经营、任务指挥、团队、能力、用量、审批和审计

桌面客户端
负责本地服务、Claude Code 与项目发现、Runtime Connector、系统通知、凭据和操作系统权限

Runtime
负责真正执行任务、调用工具和返回证据

组织编排核心
负责让三者共享状态、权限、预算、评测和审计
```

对话是最快的任务入口，Web 是最清晰的经营、管理和信任界面，桌面客户端是本地优先体验的宿主，Runtime 是可靠的执行环境。它们共享一个组织模型、能力 Registry、Usage 账本和审计事件，才能避免产品退化为“有界面的提示词集合”。

## 32. 最终结论

这个产品方向成立，核心价值也不局限于软件开发。它可以覆盖不同语言、不同项目、内容生产、研究分析和日常运营，因为真正可复用的不是某个 Agent 的提示词，而是以下组织能力：

- 把目标转化为可验收任务；
- 从事情中识别职责，在职责稳定后设岗；
- 先盘点现有成员，缺能时再从内部目录、Find Skill 和 GitHub 等来源寻访；
- 将经过审查和试用的能力资源装配为候选成员；
- 根据任务动态匹配岗位和人员；
- 用最小团队协调串行与并行；
- 用 Skill 封装方法；
- 用 Workflow 固化协作；
- 用记忆保存经过验证的经验；
- 用评测驱动员工和团队成长；
- 用权限、预算和审计保持用户控制。

推荐将它定义为：

> **一个让用户以董事长身份确定方向、战略和目标，通过董事长助理协调公司，由公司总经理组织团队和 AI 成员完成交付的组织操作系统。**

它首先解决 Claude Code 长期用户对 Agent、Skill、Workflow、MCP、工具、模型、规则和记忆难以统一管理、跨项目复用、稳定编排和持续评测的现实痛点，同时通过场景化能力包扩展到内容、研究、数据、设计、运营、销售、客户服务和个人事务等不同场景。

在实现方式上，班底是产品系统，董事长助理是默认总控 Agent 和自然语言组织路由入口；专业 Skill 承载方法，MCP 与工具连接本地和外部能力，Custom Agent 映射成员执行身份，Workflow 承载协作流程，而多事业空间状态、岗位决策、候选装配、任务调度、调用与 Token 计量、工作表现、记忆治理和审批最终需要独立的组织编排核心。

开源生态已经提供 Agent Skills 规范、Skill 搜索与扫描、临时团队编排、角色模板和 Web 工作流平台。班底应通过 Provider 和 Runtime 适配器复用这些能力，不把任一项目写死为核心依赖，也不以 Fork 一个大型团队 Skill 代替产品架构。真正需要自研并持续验证的差异化是：职责到岗位的决策、岗位到候选成员的装配，以及成员进入长期组织前后的治理闭环。

产品形态、核心数据模型、本地优先边界和 Web/客户端经营体验从一开始按完整系统设计；实施按“能力发现与纳管、跨项目复用、董事长交办与执行、用量观测、验收成长、外部寻访”纵向闭环推进，避免构建后续必须推翻的一次性原型。Claude Code 是首个生产 Runtime 和核心切入点，但不是产品可覆盖场景的永久边界。
