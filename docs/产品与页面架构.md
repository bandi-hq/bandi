## 2. 产品定位

### 2.1 一句话定位

**Bandi Desktop 是长期 Agent 配置资产与可追溯版本的本地管理工具：用户在 Desktop 中查看、修改和保存多 Agent 配置，再回到自己的 Claude Code CLI 中完成任务。**

现实公司的 Company、Department、Role 和委派关系是配置资产的组织建模方式，不表示 Bandi 正在实时复制或运行一家数字公司。Bandi Desktop 管理跨会话持续存在的配置、组织关系、正式记忆和版本；Claude Code 管理当前任务的目标、临时上下文、人员协作、一次性权限、执行冲突、审批、进度、汇报和验收。Plugin / CLI 按需读取长期配置，并且只提交用户明确要求长期化的建议。

品牌短句：

> 管理你的 AI 班底。

Bandi 不是随意生成虚拟 AI 公司的沙盒。一个 `Company` 对应一家现实公司的数字孪生；用户管理多个 Company，表示他们正在管理多家现实公司的本地映射。

### 2.2 核心用户与角色

首版优先服务已经使用 Claude Code CLI，并开始维护多个 Agent、Skill、MCP、项目规则和工作目录的个人开发者、一人公司经营者和小型 AI 原生团队负责人。

| 角色 | 定义 | 主要职责 |
| --- | --- | --- |
| 董事长 | 使用 Bandi 的真实用户 | 确定方向、建立组织、下达目标、审批关键事项和最终验收 |
| 董事长助理 Agent | 用户自己的 Claude Code CLI 中唯一默认的公司任务交互入口 | 理解目标，判断必要部门；低风险事项直接说明并推进，多部门复杂事项先给出简明方案供董事长确认；委派主管、协调跨部门依赖、处理升级并向董事长汇报 |
| 部门主管 Agent | Claude Code 执行现场中的部门管理与编排角色 | 根据职责、Skills、Workspace 与权限选择必要员工，驱动部门协作，审批部门交付并向助理汇报 |
| 专业 Agent | 产品、架构、研究等专业岗位 | 执行专业工作，并可在授权范围内编排岗位级或任务级子工作流 |
| 执行 Agent | 具体执行岗位 | 执行步骤，提交交付物、证据和阻塞；是否可编排由授权决定 |

董事长保留最终决定权。任何 Agent 都不能替董事长批准关键方案、伪造董事长同意或完成最终验收。

### 2.3 产品核心价值

1. **看得见**：让 Agent 的职责、Instructions、Memory、Skill、MCP、Rules、权限和 SOP 集中可见。
2. **配得清**：让 Agent 自有配置、显式共享引用、普通默认、强制边界和 Workspace 专属配置关系明确。
3. **改得稳**：保存目标、外部变化、校验失败和高风险长期变更都有明确反馈，不静默覆盖。
4. **记得清**：区分 Agent 长期记忆、Agent × Workspace 项目记忆、Workspace 公共记忆和 Department × Workspace 项目管理记忆。
5. **用得上**：提供 Workspace 与经验证的 cwd 目录交接，让用户回到自己的终端使用已保存配置。
6. **可追溯**：普通配置保存形成不可变 ConfigRevision，可比较、恢复；正式记忆使用独立 MemoryRevision。

## 3. 产品构成与责任边界

```text
Bandi Desktop ─────────┐
bandi CLI ─────────────┼──→ Rust Local Service ──→ 本地事实、策略与审计
Bandi Plugin ──────────┘           │
  ├── Skill                        ├── SQLite / AgentPackage / SourceAsset
  ├── 董事长助理 Agent             ├── Workspace / Git / Keychain
  ├── Bandi MCP                    └── 受限本地系统操作
  ├── Hooks
  └── settings
        ↓
用户自己的 Claude Code CLI

```

| 组成 | 负责 | 不负责 |
| --- | --- | --- |
| Bandi Desktop | Company、Department、Agent 组织关系，以及 Instructions、Skills、Memory、Rules、MCP、长期权限、Agent × Workspace 专属配置、SOP 等配置资产的查看、编辑、保存、版本比较与恢复；提供经验证的 cwd 目录交接 | 单次工具授权、任务冲突或审批、Session/Workflow/AgentExecution 状态、人员调度、执行推进、聊天、汇报、验收或终端状态跟踪 |
| Rust Local Service | 统一配置事实、策略、版本、审计、有效配置解析及受限系统能力 | 替用户作经营决定或保存终端运行状态 |
| `bandi` CLI | 系统 Shell 中的配置状态、诊断与 Claude Code 入口 | 维护另一套业务事实 |
| Bandi Plugin | Claude Code 侧稳定能力基线和 Local Service 适配 | 长期组织事实数据库 |
| Skill | 告诉 Claude 如何识别和完成 Bandi 流程 | 硬编码全部公司与员工关系 |
| SOP / WorkflowDefinition | 供 Claude Code 中的董事长助理解析的目标、步骤、分工、确认/升级条件与验收配置定义 | Desktop 内的任务模板执行器、待办或审批中心 |
| 董事长助理 Plugin Agent | 提供稳定的运行时身份、职责和工具边界 | 取代长期 AgentPackage |
| Bandi MCP | 为 Claude Code 中的助理提供组织、SOP、权限和配置的结构化查询，并按策略记录必要事实 | 定义 SOP、控制终端、替 Desktop 执行任务或决定组织关系 |
| Hooks | 工具门禁、审计和有限事件证据 | 绝对 fail-closed 安全边界或可靠 Connector |
| settings | Plugin 默认配置及支持的覆盖 | 公司与 Workspace 的动态事实 |
| Claude Code CLI | 用户实际对话与执行环境 | Bandi 的组织管理平面 |

### 3.1 Bandi Plugin 与外部 Plugin 的区别

- **Bandi Plugin**是产品自有集成基线，具有安装、版本、作用域和组件完整性状态；
- **第三方 Plugin**在导入或引用前属于 `SourceAsset`；
- **Plugin 中的董事长助理 Agent**是 Claude Code 运行时定义；
- **AgentPackage**才是董事长助理和其他长期员工的配置事实来源；
- **RuntimeProjection**引用 Bandi Plugin 基线并叠加公司、Workspace、Agent 和策略上下文，不等于重新安装 Plugin。

## 4. AI 编程工具交接

Desktop 只提供轻量衔接，不建立“接入模式”或“启动模式”的产品流程。统一入口按当前配置方案展示已加入工具；当前只有 Claude Code 具备经过验证的工作区交接：

```text
选择 Workspace
→ 查看 cwd、默认终端与交接能力证据
→ 请求白名单终端打开已登记 Workspace 的 canonical cwd，或复制路径
→ 用户在自己的终端中启动 Claude Code 并继续
```

固定边界：

- Desktop 不识别、接管或持续跟踪已有 Session；
- 路径已复制或终端已请求打开，都不代表 Claude Code、Bandi、Plugin 或 Session 已创建、已连接或已加载配置；
- 首轮交接只允许冻结的五字段请求，由后端重取 canonical cwd，并仅通过固定 `/usr/bin/open` 打开目录；Desktop 不生成、执行或回传命令；
- 当前会话中的上下文解析属于 Bandi Plugin；新终端或新会话由 CLI / Plugin 负责；
- Desktop 不保存接入记录、执行证据、工具调用、Todo、日志、Agent View 或运行状态；不建立 Task、Session、Chat 领域对象或对应页面；
- `RuntimeProjection` 如有需要，由 Plugin / CLI 从当前配置重建，不成为 Desktop 的常规页面、发布对象或待处理事项。

真实工具能力必须采用“一个工具一个 Adapter”的类型化边界，不以通用 Shell 模板猜测兼容性。首版内置目录固定为 Claude Code（`claude-code`）、Claude Desktop（`claude-desktop`）、Codex（`codex`）、Gemini CLI（`gemini-cli`）、Grok Build（`grok-build`）、OpenCode（`opencode`）、OpenClaw（`openclaw`）、Hermes（`hermes`）和 Pi（`pi`）共 9 项；目录身份只证明 Bandi 能稳定识别该工具，不证明安装、配置、交接或 Bandi 集成可用。实现优先级为 Claude Code、Codex、OpenClaw，再覆盖本机已安装工具和其余内置目录；每个 Adapter 分别声明探测、配置读取、配置写入、cwd 交接、Bandi 集成检查和写后验证中实际支持的能力。未完成、不可验证或仅能只读的能力必须保留在工具详情中，并逐项记录 `reason`、`evidence`、`remediation`；不得因为工具已加入配置方案、存在可执行文件或展示了入口，就推断其配置可写、可启动或已加载。首个端到端切片只覆盖 Claude Code 的 `instructions.md`：真实读取、编辑、基线检查、原子写入、重读验证和 ConfigRevision；其他文件类型与其他工具随后按 Adapter 逐项扩展。

首次建立未关联组织的个人 Workspace 后，Desktop 可在同一交接 Dialog 中生成一次性“协作规划说明”：用户用三个简短字段描述场景目标、现有参与者与资源、高频协作与边界，再主动复制到自己的 Claude Code 中继续澄清。Claude Code 应先判断个人工作区是否已足够；确有长期协作需要时才建议 Company、Department、岗位、真人职责、长期 Agent、权限/服务授权与 SOP。说明只存在于当前 Dialog，关闭即丢弃，不进入启动 argv、配置方案、Workspace、ConfigRevision、备份或 Session；它也不等同于 Claude Code 的 Plan permission mode。用户明确确认前，AI 不得创建或修改任何长期配置。

## 5. 产品主线与原则

### 5.1 Agent-first 初始化

```text
安装 Bandi Desktop
→ 导入一个已有 Claude Agent，或创建个人 Agent
→ 查看并按需修改受管配置
→ 安全保存并生成 ConfigRevision
→ 比较或恢复历史版本
→ 回到 Claude Code 使用
```

Company、Department、Role、Workspace、ServiceGrant 与 SOP 均保留，但不是首次使用、创建或导入 Agent 的前置条件。用户确有稳定组织协作和委派治理需求时再逐步关联；系统不得暗建默认公司、部门或岗位。

首次启动不申请整盘或宽泛文件访问，也不自动扫描用户的 Claude 配置。只有用户发起导入、登记 Workspace 等具体操作并通过系统选择器明确选择目标后，Desktop 才在该文件或目录边界内执行对应的受限读取或登记；单文件导入创建受管副本，不获得源文件写回权。设置中的“本地访问边界”只读展示受管 AgentPackage、已登记 Workspace、Claude Agent 导入来源和外部只读引用，不提供虚假的全局权限开关。

### 5.2 日常配置管理

```text
在 Desktop 的组织或 Agents 中选择员工
→ 查看完整配置：职责、Instructions、Skills、Memory、Rules、MCP、权限、Agent × Workspace 专属配置、SOP
→ 直接修改需要调整的配置
→ 按风险和资产类型执行必要校验
→ 保存到真实 AgentPackage 或其引用的真实配置文件
→ 写后验证成功并生成 ConfigRevision
→ 回到 Claude Code 使用更新后的配置
```

普通配置采用“查看—修改—保存”的直接心智模型，不强制经过草稿、Diff、影响分析、冲突处理、审批和发布。每个 AgentPackage 独立拥有该员工的配置，部门和岗位只描述组织、职责与委派关系，不向 Agent 隐式继承配置：

- Agent 自有配置直接保存回该 AgentPackage，写回目标明确；
- Company / 全局配置只提供 Claude Code 底层公共配置、普通默认值、共享资产和不可突破的安全边界；
- Agent 未设置普通配置时才使用全局默认；全局强制安全限制不能被 Agent 放宽；
- 公共 Skill、Rule、MCP 和 SOP 通过 AgentPackage 显式引用，不因所属部门或岗位自动生效；
- Agent 在特定 Workspace 中的专属配置仍归该 Agent 所有，通过 `agent.workspaceBindings` 表达；它是 Agent ↔ Workspace 关系的唯一规范事实，Workspace 端列表只作兼容字段，不参与页面派生或保存；
- 每个 Binding 的普通专属配置登记为 `workspaces/<workspace-id>/config.yaml`；没有正式项目记忆事实时不得预建或虚构 `memory.md`；
- 来源默认收起，用户需要区分自有、共享引用、全局默认或全局强制时再展示；
- Diff 仅在用户主动查看，或检测到保存期间发生外部并发修改时出现；
- 影响分析只针对被多个 Agent 显式引用的共享资产；
- 普通保存不需要审批或“发布”动作；保存成功后生成不可变 ConfigRevision；
- 权限范围扩大、敏感路径新增写入、危险 MCP/命令开放等高风险变更必须明确确认；
- Memory 不是普通配置例外的豁免项：所有正式 MemorySpace 变化仍必须先形成 MemoryCandidate，经审核后写入并生成 MemoryRevision。

### 5.3 日常执行

所有任务相关交互均留在用户自己的 Claude Code CLI，Desktop 只负责打开或衔接 Claude Code，不提供任务操作界面：

```text
用户按 cwd 指引在自己的终端进入 Claude Code
→ 董事长在终端向助理下达目标
→ 助理判断完成目标所必需的部门
→ 低风险事项：助理简要说明判断后直接委派
→ 多部门复杂事项：助理先在终端给出简明方案，董事长确认后委派主管
→ 主管根据岗位职责、Skills、Workspace 和权限选择必要员工
→ 专业与执行 Agent 在终端执行、协作并提交交付物与证据
→ 阻塞与一般审批逐级上报；高风险动作在执行前再次请求董事长确认
→ 员工向主管、主管向助理、助理向董事长逐级汇报
→ 董事长在终端完成最终验收
```

用户不需要在 Desktop 为每次任务预选部门或员工。临时协作方式默认留在当前终端上下文；只有确有复用价值时，助理才建议沉淀，并在用户同意后保存为 SOP 配置资产。

### 5.4 渐进式使用层级

Bandi 不设置“个人模式”开关，而是按用户实际需要渐进增强：

1. **长期 Agent**：从明确选择的 Claude Agent 文件导入受管副本，或直接创建个人 Agent；无需先创建 Workspace、Company、Department 或 Role。
2. **安全配置治理**：查看和修改长期配置，保存时执行外部变化保护并生成 ConfigRevision；需要时比较或恢复历史。
3. **Workspace 与宿主交接**：需要项目作用域、WorkspaceBinding 或 cwd 交接时再登记 Workspace；用户仍在自己的终端中启动 Claude Code。
4. **组织治理**：需要部门主责、岗位、服务授权、公司共享资产和安全边界时再建立 Company；没有组织关系的个人 Agent 始终是合法状态。

组织导航始终保留。没有 Company 是合法状态，组织页展示安静的创建引导；Workspace 可保持未关联组织且不因此产生配置错误。Bandi Plugin 与 `/bandi:bandi` 是安装后的可选增强入口，不替代标准 `claude` 主线。

### 5.5 首版原则

1. **现实公司优先**：Company、部门、岗位和 Workflow 表达真实经营关系。
2. **工作区是配置作用域**：它登记一个本地项目目录及长期配置关系；进入外部 CLI 时该本地目录作为 cwd，但工作区本身不是公司、部门、终端、会话或运行实例。
3. **多入口、单一中枢**：Desktop、CLI 和 Plugin 共用 Local Service，不产生多主事实。
4. **Agent 目录化且配置独立**：每个长期 Agent 是独立 AgentPackage，不是一个 Prompt 文件；部门和岗位不形成隐式配置继承。
5. **公共配置显式可见**：全局只提供底层公共配置、普通默认、显式共享资产和强制安全边界；Agent 自有设置优先于普通默认，公共资产必须显式引用。
6. **编排分层授权**：组织身份不自动授予权限；能力由显式配置的组织范围、Workflow、委派深度、审批和 Workspace 权限共同决定。Agent 可以自行收紧权限，但扩大权限必须由有权主体确认。
7. **管理与执行分离**：Desktop 管理，用户自己的 Claude Code 执行。
8. **Desktop 与运行分离**：Desktop 只提供经验证的 cwd 目录交接，不生成或执行宿主命令，也不保存 Session、接入或执行状态。
9. **Plugin 与投影分离**：Plugin 是稳定基线，RuntimeProjection 是 CLI / Plugin 内部可重建产物。
10. **SOP 定义协作边界**：SOP/WorkflowDefinition 是供 Claude Code 中的助理和主管解析的配置资产，不是 Desktop 执行器；MCP 只提供结构化连接。
11. **记忆按作用域治理**：MemorySpace 是领域边界，文件只是载体；不同 Agent、Workspace 和 Department 的记忆默认隔离。
12. **候选先审后写**：运行和人工编辑先产生 MemoryCandidate，任何 Agent、MCP 或 Hook 都不能直接改正式长期记忆。
13. **运行时只加载授权记忆**：MemoryProjection 由 CLI / Plugin 按当前配置和权限构建，不成为 Desktop 的运行状态。
14. **普通配置直接保存**：不把草稿、Diff、影响、冲突、审批和发布强加给每次编辑，只在用户主动查看、共享影响、真实冲突或高风险变更时介入。
15. **配置状态必须有证据**：写后验证、ConfigRevision、MemoryRevision、确认记录和备份快照分别表达；不推断 Runtime 或任务状态。
16. **CLI 承载完整任务交互**：下达目标、判断部门、复杂方案确认、跨部门委派、选员工、执行协作、阻塞/审批、逐级汇报和最终验收全部留在用户自己的 Claude Code CLI，由董事长与董事长助理完成主交互。
17. **Desktop 不参与单次任务**：不要求用户为每次任务选择部门或员工，不提供任务创建、运行、调度、确认、推进、聊天、汇报或验收界面。
18. **SOP 是配置，不是执行器**：SOP 供 Claude Code 助理解析；临时协作默认留终端，有复用价值且经用户同意后才保存为 SOP。

### 5.6 产品不是

- 内嵌终端或 Claude Code 替代品；
- 虚拟办公室、员工养成游戏或 Agent 群聊展示器；
- 任意生成虚拟公司的组织模拟器；
- 后台不可见地托管用户 CLI 的执行平台；
- 未经确认自动覆盖或删除本地配置的同步器；
- 把 Plugin 已安装、MCP 可连接或终端已打开当作任务已运行的监控系统；
- 镜像 Claude Code 的聊天、工具调用、Todo、日志或 Agent View 的执行看板；
- 在 Desktop 中创建或运行任务、选择当次任务的部门/员工、确认方案、人员调度、推进流程、聊天、处理阻塞/审批、汇报或验收；
- 把 SOP 当作由 Desktop 自动执行和推进的流程引擎。

## 6. 核心领域模型

### 6.1 Workspace

用户授权的本地执行上下文，包含路径、Git、Claude 项目配置、关联公司、项目责任关系、WorkspaceBinding 和入口偏好。一个 Company 可以关联多个 Workspace；一个 Workspace 可以暂不关联组织，但首版最多只能归属一个 Company，二者不互为别名。同一本地目录如需服务不同 Company，应建立各自独立的 Workspace 记录并保持公司上下文隔离，或把可复用内容建模为显式共享资产，不能让一个 Workspace 同时加载多家公司的组织、默认配置和安全边界。

首版业务语言中的“项目记忆”以 Workspace 为项目边界，规范字段继续使用 `Workspace`，不新增并列的 `Project` 对象。每个已关联 Company 的 Workspace 必须且只能设置一个来自该 Company 的主责部门，可设置零到多个同公司协作部门；主责部门主管同时作为默认项目负责人和 Workspace 公共记忆归口人。主责主管对项目总体结果、公共事实整理、跨部门进展汇总和向董事长助理汇报负责；协作主管只对本部门承接的目标、交付和部门项目记忆负责。董事长助理负责跨部门协调与升级，不接管项目台账。

Workspace 公共记忆始终归 Workspace 所有。更换项目负责人或主责部门时，必须明确确认新的主责部门与主管，保留公共记忆、各部门项目记忆和历史记录，只转移后续归口及相应权限；不得自动修改或删除 AgentPackage、WorkspaceBinding 和既有记忆。原主责部门可按用户选择转为协作部门或解除项目关系。

更换 Workspace 所属 Company 是高影响关系变更：必须重新选择新公司的主责部门、项目负责人和协作部门，并在确认前展示将失效的旧公司共享资产引用、委派关系、权限和记忆可见性。Workspace 本地目录、公共记忆、部门项目记忆与历史记录不被删除；旧公司的 Department × Workspace 记忆转为只读历史边界，除非用户另行迁移或归档。系统不得把旧部门自动映射到新公司，也不得静默保留跨公司权限。

### 6.2 Company、Department 与 Role

- `Company`：一家现实公司的本地数字孪生边界；
- `Department`：公司内具有上级关系的职责单元，可表达中心、部门或小组；
- `Role`：使命、职责、输入、交付、边界、升级条件和完成标准的结构化定义。

首版支持多公司与树形 Department，通过 `parent_department_id` 表达上下级。数据结构不硬编码层数，产品面向现实创业公司优化，建议组织深度不超过三层，过深时提示而非建设大型集团人事系统。组织管理支持创建公司、添加/编辑/移动部门、设置主管、岗位、成员 Agent 和委派边界；首版通过选择上级部门移动节点，不优先实现拖拽。

每个 Agent 可以暂不归属，但最多只有一个主属部门；主属部门决定直属主管、默认汇报链、主要岗位、长期记忆默认审核人和默认可参与的部门项目。Agent 可以通过零到多个显式服务授权为其他部门工作，每项授权必须限定服务部门、允许能力、适用 Workspace、有效期或状态及禁止事项；服务关系不改变主属部门、直属主管，也不授予管理目标部门成员、审批目标部门预算或修改其项目台账的权力。

Company、Department 与 Role 用于组织展示、职责定义和委派判断，不构成向 AgentPackage 自动注入配置的继承层。移动 Agent 的主属部门只改变组织、汇报和委派关系，不移动或自动改写 AgentPackage、Skills、Rules、MCP、权限或 WorkspaceBinding；原服务授权和委派关系失效时作为配置缺口提示。删除仍有下级或成员的部门时必须先选择迁移目标，不得连带删除 AgentPackage。只有被设为 Workspace 主责或协作方的部门，才建立对应的 `Department × Workspace` 项目关系和项目记忆；该记忆由部门主管归口维护，但不属于主管个人 AgentPackage，也不跨 Workspace 自动复用。

Agent 生命周期固定为 `active`、`inactive` 和 `archived`。暂时不用时优先停用，长期保留时归档；两者均保留稳定身份、AgentPackage、正式记忆、历史和引用，不允许被新的委派选中。永久删除 AgentPackage 是独立高风险操作，执行前必须展示仍存在的 WorkspaceBinding、共享资产引用、审核责任和记忆影响，并要求用户明确确认；从部门移除成员或删除组织关系不得隐式删除 AgentPackage。

### 6.3 AgentPackage

长期、独立、可成长的 Agent 配置事实来源：

```text
agents/
└── <stable-agent-id>/
    ├── agent.yaml
    ├── instructions.md
    ├── config/
    │   ├── context.yaml
    │   ├── skills.yaml
    │   ├── rules.yaml
    │   ├── mcp.yaml
    │   ├── permissions.yaml
    │   ├── sop.yaml
    │   ├── orchestration.yaml
    │   ├── hooks.yaml
    │   └── commands.yaml
    └── workspaces/
        └── <workspace-id>/
            └── config.yaml
```

这是 AgentPackage v1 的规范结构化路径集合；所有 Bandi 自管结构化 YAML 顶层使用 `schemaVersion: 1`。`agent.yaml` 是完整 manifest，保存稳定身份、显示名、`roleId`、`active/inactive/archived` 生命周期以及使命、职责、交付、边界、升级、禁止和完成定义；生命周期变化也必须以完整 manifest 快照进入同一保存、版本和恢复链路。Agent 可选头像固定为包根目录 `avatar.png`，manifest 只保存 `avatarPath: "avatar.png"` 引用；创建和身份编辑支持上传、替换与移除，仅接受最大 5 MiB 的 PNG。无头像或读取失败时显示名称首字符，外部只读及非 current 包不得改写头像。`parserVersion` 只属于未来资产索引，不写入用户配置，也不参与 package schema 比较。

兼容状态固定为：`current`（v1，可编辑）、`legacy`（已知旧版，只读）、`future`（未知更高版本，只读，禁止降级保存）和 `unverified`（外部只读引用，未读取时不得伪装为 v1）。首版不要求没有长期事实的可选文件预先生成；当前 Web Mock 对 WorkspaceBinding 只登记 `config.yaml`，不得虚构未登记文件或源码。`config/sop.yaml` 只保存显式引用，SOP 本体仍作为资产管理；`workspaces/<workspace-id>/config.yaml` 只保存该 Agent 面向目标 Workspace 的显式专属配置。正式记忆载体与 SOP 本体仍按各自领域契约管理，不因结构化配置路径冻结而被复制进这些文件。

首版 Bandi 自管 AgentPackage 默认位于 `~/.bandi/agents/<stable-agent-id>/`。Claude Agent 导入只支持用户明确选择的单个用户级或项目级 `.claude/agents/*.md`：预览读取 YAML frontmatter 中的 `name`、`description` 和 Markdown 正文，提交时重读并校验 source hash，再创建独立受管副本；原文件始终只读，未识别字段只展示诊断，不自动转换为 Rules、Skills、MCP、权限或正式 Memory。另保留“仅登记外部引用”模式，它只登记所选目录，不扫描、读取或复制内容。AgentPackage 以不可变 `agent-id` 定位，不从目录名、显示名、Company、部门或岗位推断身份。重命名、移动主属部门、增加跨部门服务授权、变更主管或更换 Workspace Company 均不移动 AgentPackage。允许用户从 Bandi 通过表单编辑，也允许打开真实目录和文件；外部编辑后 Local Service 必须重新扫描、读取和比较基线，不得静默覆盖。

董事长助理、部门主管、专业 Agent 和执行 Agent 使用同一目录模型，每个 AgentPackage 独立拥有其 Instructions、Skills、Rules、MCP、权限、编排和 Workspace 专属配置。身份标签不直接授予编排权，部门和岗位也不产生隐式配置继承。董事长助理仍是一个独立 Agent，其个人配置不能代替 Company / 全局配置；后者只承载 Claude Code 底层公共配置、普通默认值、共享资产注册和强制安全边界。

普通单值配置遵循“Agent 明确设置优先，否则使用全局默认”；全局强制安全边界不可被 Agent 放宽。共享 Skill、Rule、MCP 和 SOP 不自动注入，必须由 AgentPackage 显式引用。首版共享资产以 Company 内共享为主；跨 Company 复用必须把资产单独注册为跨公司共享并对目标 Company 明确授权，不能因名称、路径或同一创建者自动可见。共享资产本体由明确所有者维护，修改时提示全部有效引用者；Agent 如需局部定制，应创建自有配置或覆盖层，不直接篡改共享本体。删除仍有引用的共享资产前必须先解除、迁移或替换引用。

`memory/` 只承载该长期 Agent 跨 Workspace 延续的长期记忆；Workspace 公共记忆和部门项目记忆不存入任何个人 AgentPackage。组织身份、主管标签或服务关系本身不授予文件、命令、网络、MCP、记忆或委派权限；这些能力必须显式配置。Agent 可以在已有边界内自行收紧，但不得自行扩大；缺少权限时向上报告，由有权主体确认后写入配置。

### 6.4 SourceContainer 与 SourceAsset

`SourceContainer` 是需要整体加锁、校验基线和原子替换的物理文件或目录；`SourceAsset` 是其中可独立查看、引用和版本化的逻辑配置片段。一个 `.claude.json`、`settings.json` 或 `.mcp.json` 可以承载多个逻辑资产，因此 `assetId` 不能等同文件路径。写锁、并发基线和原子写绑定 container；ConfigRevision 绑定逻辑 asset，并同时记录 container hash、fragment 定位和 write receipt。

用户已有的 Custom Agent、Skill、MCP、Rules、Memory、Settings、Hook、第三方 Plugin、Command、Workflow 或脚本都可作为 SourceAsset。扫描只建立索引；保持引用时外部容器仍是来源事实。普通 Agent 配置显式导入后由 AgentPackage 纳管；Memory 导入必须先选择目标 MemorySpace，并以候选方式审核写回。

Claude Code 首批位置映射：

- 用户 settings：`$CLAUDE_CONFIG_DIR/settings.json`；未设置变量时由 Claude Code 默认配置根解析，不能硬编码用户名路径；
- 项目共享/本地 settings：`<workspace>/.claude/settings.json`、`<workspace>/.claude/settings.local.json`；
- 用户级及项目 local MCP：`.claude.json` 中对应 user/project fragment；项目共享 MCP：`<workspace>/.mcp.json`；
- Plugin 安装 scope：`user | project | local | managed`。Company 只表达 Bandi 治理、共享和授权，不是 Claude Code 安装 scope；
- Plugin cache 是 Claude Code 管理的可重建证据，不是普通编辑、版本恢复或备份目标；managed、cache 和 Session-only 事实默认不可普通写回。

### 6.5 WorkspaceBinding

```text
AgentPackage 主配置
+ 该 Agent 在目标 Workspace 的专属 Instructions / Rules
+ 该 Agent 在目标 Workspace 的 Skill / MCP 显式引用
+ Agent × Workspace 独立项目记忆引用
+ 当前可读取的公共/部门 MemorySpace 引用
+ 该 Agent 在目标 Workspace 使用的账号
+ 该 Agent 在目标 Workspace 的局部权限与模型设置
= WorkspaceBinding
```

`agent.workspaceBindings` 是 Agent ↔ Workspace 关系的唯一规范事实；Workspace 页面中的 Agent 列表、数量、健康状态和最近配置均由它与 ConfigRevision 派生。删除 Workspace 索引不会删除或改绑现有 Binding，而是保留为可修复的 dangling Binding。每个长期 Agent 在每个 Workspace 下可拥有独立项目记忆文件或逻辑文件；只有存在正式项目记忆事实时才创建相应载体。不同 WorkspaceBinding 的 Agent 项目记忆、MCP 账号和权限默认隔离。WorkspaceBinding 是 AgentPackage 内针对目标 Workspace 的专属配置，不是 Workspace 从外部覆盖所有 Agent 的公共继承层。它只引用当前可读取的共享 MemorySpace，不复制或取得其所有权。

### 6.6 MemorySpace、MemoryCandidate 与 MemoryRevision

`MemorySpace` 是具有独立作用域、所有权、归口人、审核策略、可见策略和文件载体的逻辑记忆边界。文件是持久化载体，MemorySpace 才是产品领域对象。

```text
id
scope_type / scope_key
owner
steward
review_policy
visibility_policy
storage_locator
current_revision
content_hash
updated_at
```

- `owner`：领域上拥有记忆的主体；
- `steward`：负责整理、去重和处理候选的归口人；
- `reviewer`：按策略批准、驳回或要求修改；
- Local Service：执行批准后的安全写入，不因此拥有内容。

首版固定四类 MemorySpace：

| 记忆空间 | 隔离键 | 所有者 | 默认归口 | 默认审核与自审升级 |
| --- | --- | --- | --- | --- |
| Agent 长期记忆 | Agent | 对应长期 Agent | 对应 Agent | 直属上级；董事长助理由董事长审核 |
| Agent Workspace 项目记忆 | Agent × Workspace | 对应 Agent | 对应 Agent | 直属上级；董事长助理由董事长审核 |
| Workspace 公共记忆 | Workspace | Workspace | 项目主责部门主管 | 主责主管审核；主管本人提出时升级董事长助理 |
| 部门项目记忆 | Department × Workspace | Department × Workspace 边界 | 部门主管 | 主管审核；主管本人提出时升级董事长助理 |

“每个 Agent”包括董事长助理、部门主管、专业 Agent 和执行 Agent。董事长助理的 Agent 长期记忆就是跨 Workspace 延续的总记忆，沉淀与董事长和部门主管交互形成的公司原则、长期偏好、重要决策和协调经验；其 Agent × Workspace 项目记忆只保存当前项目中的协调、汇报和待董事长决策摘要，不承担完整项目管理。项目目标、计划、进展、风险、依赖、分工和交付由负责项目的部门主管维护在 Department × Workspace 项目记忆中；Workspace 公共记忆由项目主责部门主管归口。Agent 项目记忆默认非共享，但仍受权限、审核和审计约束。

`MemoryCandidate` 是运行、会话或人工编辑产生的待审核建议，必须指定唯一目标 MemorySpace。创建候选只提交 `spaceId`、提议者、来源、摘要和建议内容；owner、steward、reviewer、可见性及存储位置由 Local Service 根据稳定 scope key 和组织事实裁决，前端不得提交审核者或路径。`MemoryRevision` 是候选获批并成功写入后的不可变版本记录，保存来源、审核、版本、哈希和写入结果。候选批准不等于文件已写入，文件写入也不等于 Runtime 已加载。

首版 `MemoryStorageResolver` 固定使用 `memory-v1`：Agent 长期记忆位于对应 AgentPackage 的 `memory/long-term.md`；Agent × Workspace 位于对应 AgentPackage 的 `workspaces/{workspaceId}/memory.md`；Workspace 公共记忆位于已登记 Workspace canonical root 的 `.bandi/memory/public.md`；部门项目记忆位于同一根下的 `.bandi/memory/departments/{departmentId}.md`。四类载体均为最大 1 MiB 的 UTF-8 Markdown。API 不接受绝对路径；不存在正式事实时不创建空文件，失去当前组织关系的部门空间仅保留只读历史。

### 6.7 SOP / WorkflowDefinition 与 OrchestrationPolicy

`SOP / WorkflowDefinition` 是由 Desktop 查看、编辑和保存，供 Claude Code 中董事长助理解析使用的配置定义，描述目标、步骤、依赖、并行、责任部门/岗位、交付物、确认条件、升级条件与验收标准。它不是 Desktop 执行器，不会自行创建任务、产生审批待办、选择人员或推进流程。

`OrchestrationPolicy` 只定义长期静态委派与安全边界，包括是否允许委派、最大深度、允许的 Agent/Role/Department 范围、WorkspaceBinding/SOP/跨部门 ServiceGrant 要求、升级目标与条件和禁止事项。有效委派能力始终是权限、组织边界、服务授权与策略的交集；Role 只表达职责，不能自动授予委派或其他能力。WorkspaceBinding 只能显式收紧根级策略：范围只能取子集，深度只能降低，必需条件和禁止事项只能增加。某次任务中的方案确认、人员选择、一次性工具授权、阻塞处理和审批均留在 Claude Code CLI，不持久化为 Desktop 运行对象。

### 6.8 ConfigRevision

普通配置在写后验证成功后生成不可变 `ConfigRevision`：

```text
id
asset_id / agent_id / path
parent_revision_id
restored_from_revision_id（可空）
content_hash
saved_at
summary
source_baseline_hash
confirmation_refs
write_receipt
```

`ConfigRevision` 用于单个配置资产的日常追溯。旧版本不可修改或删除；恢复历史版本是一笔新的受保护写入，成功后生成新 revision，并记录 `restored_from_revision_id`。失败、未写入或写后验证失败不得生成正式 revision。当前 Web Mock 中，预置版本标为 `demo-fixture`，本次页面操作生成的版本标为 `memory-only`；它只证明当前页面内存中的配置变更链，不得描述为真实文件已写入或验证成功。

### 6.9 类型化组件、输出契约与 PluginInstallation

`HookDefinition` 与 `CommandDefinition` 是两种独立的可信配置资产。Hook 声明受支持事件与用途；Command 声明稳定 command ID 与用途。两者只保存定义、来源、兼容性和显式引用，不接受脚本文本、Shell 字符串、可执行程序或 cwd，也不提供执行、测试或运行日志。Agent 根级引用分别保存到 `config/hooks.yaml`、`config/commands.yaml`；WorkspaceBinding 只保存局部显式引用。

`OutputProfile` 是可复用的长期响应契约，包含 `markdown/json/text` 格式、语言、必需章节、证据要求和类型化参数；destination 固定为 `response`。它不提供文件路径、网络、Webhook 或外部投递能力。界面统一称为“输出格式”；Agent 根级引用及默认绑定保存在 `config/context.yaml`，WorkspaceBinding 可显式覆盖。

Hook、Command 和 OutputProfile 的非敏感参数只允许 `string`、`number`、`boolean`、`string-list` 和 `enum`，并按稳定 parameter ID 绑定。模型从根上排除 secret、任意 object、环境变量、cwd、文件落点、可执行程序和 Shell 模板；保存与恢复均重新校验 required、类型、范围和 enum 选项。

Plugin 必须严格区分三层事实：Plugin 资产本体及组件清单、独立 `PluginInstallation`、Agent/Workspace 对组件的显式引用。Installation 至少记录作用域、安装/可用版本、回滚版本、兼容性、组件完整性和证据；安装、更新、回滚或卸载不得自动增删组件引用，失效引用保留并产生诊断。它不证明客户端或 Session 已加载或调用 Plugin，也不进入 Desktop 运行监控。当前 Web Mock 的管理动作只改变 React 页面内存，不探测、下载、执行安装脚本或写入文件。

### 6.10 RuntimeProjection

`RuntimeProjection` 是 CLI / Plugin 在需要时从 AgentPackage、WorkspaceBinding、授权 MemoryProjection、Skill/MCP 和策略重建的内部产物。它不是长期配置主源、普通配置版本、Desktop 发布对象或 Session 状态；Desktop 不提供“重新发布投影”的常规主操作。

### 6.11 配置操作证据

Desktop 只记录与长期配置治理直接相关的证据。页面展示任何状态时必须明确标注以下证据等级之一，且不得混用：

| 证据等级 | 含义 | 允许的页面措辞 |
| --- | --- | --- |
| `real` | Local Service 已读取真实来源，或完成真实写入并重读验证 | 已读取、已写入、已验证；同时展示路径、基线/内容哈希、时间或写入回执 |
| `memory-only` | 本次 React 页面内存中的用户操作结果，刷新会丢失 | 已保存到当前页面内存；不得称为已写入文件 |
| `demo-fixture` | 预置演示数据，仅用于展示页面与交互 | 演示数据、演示状态；不得暗示来自本机扫描 |
| `read-only` | 有真实或外部证据可读取，但当前 Adapter、权限或兼容状态不允许写入 | 只读；同时展示来源，并记录 `reason`、`evidence`、`remediation` |

长期配置证据包括：

- 配置保存的目标、基线哈希、写入回执与 ConfigRevision；
- 正式 Memory 的 ReviewDecision、写入回执与 MemoryRevision；
- 高风险长期权限变更、共享资产影响、恢复和永久删除的用户确认；
- BackupSnapshot 的范围、完整性与恢复记录；
- AI 编程工具 Adapter 的能力探测与未完成项；未完成项必须逐项保存 `reason`、`evidence`、`remediation`，不能只显示笼统“暂不支持”。

任务审批、一次性工具授权、任务交接、执行结果和 Session 事件不进入 Desktop 数据模型；Task、Session、Chat 也不作为产品领域对象。

- 当前 Company、Department 或 Agent；

组织页提供“当前 Workspace”和“全部组织”两个视角。公司详情是数字孪生核心页，优先展示现实组织与执行环境的关系，而不是统计卡片墙。

## 8. 关键用户流程

### 8.1 创建公司数字孪生

```text
创建 Company
→ 填写现实公司身份、使命和边界
→ 创建董事长助理 AgentPackage
→ 建立部门和岗位
→ 创建员工 AgentPackage 或显式导入 SourceAsset
→ 定义 Workflow 与 OrchestrationPolicy
→ 关联 Workspace
→ 检查 Claude Code 集成
```

### 8.2 从 AI 编程工具入口继续

```text
从 Desktop 的工作区、Agent 或资产上下文打开指引
→ 展示目标工作区、本地目录、由 Workspace Registry 重取的 canonical cwd 和交接能力证据
→ 从 Agent 上下文进入时，补充 AgentPackage 与当前工作区是否存在显式 WorkspaceBinding
→ 用户请求白名单终端打开 cwd，或复制路径后手动继续
→ 用户自行启动 Claude Code；后续全部任务交互发生在用户自己的 Claude Code CLI
```

WorkspaceBinding 只证明长期配置关系存在，不表示 CLI 已自动加载 Agent。非 Claude 宿主在尚无冻结 Adapter 时只展示配置入口与 `reason / evidence / remediation`，不得复用 Claude Code 的目录交接或猜测命令。Desktop 不创建接入记录、LaunchContext、AgentExecution 或 Session 状态。

### 8.3 Claude Code 中的分层协作

以下过程全部发生在用户自己的 Claude Code CLI 中，Desktop 不提供对应页面或状态：

```text
董事长向助理下达目标
→ 助理依据已保存配置判断必要部门
→ 方案确认、委派、执行、阻塞、一次性权限授权和任务审批均在当前对话处理
→ 主管选择员工并汇总部门结果
→ 助理汇总跨部门结果并向董事长汇报
→ 董事长最终验收
```

### 8.4 查看并修改 Agent 长期配置

```text
选择 Agent
→ 默认进入管理视图概览
→ 按业务领域查看和修改身份、Instructions、能力、边界、Workspace 专属配置或 SOP
→ 需要文件细节时切换 AgentPackage
→ 从目录树选择根级或 workspaces/<workspace-id>/ 文件
→ 查看结构化预览、只读源码或历史
→ 校验格式、路径、风险和当前基线
→ 必要时确认共享影响或长期权限扩大
→ 原子写入并重读验证
→ 生成 ConfigRevision
```

管理视图与 AgentPackage 是同一长期配置事实的两种视角，不建立第二状态源。缺省 URL 进入管理概览，`tab=package&path=<path>&view=<preview|source>` 表达可刷新、可前进后退的技术视图深链。宽屏 AgentPackage 使用“完整目录树 + 文件查看器”双栏；`<1280px` 文件查看器占满内容区，通过左侧 Sheet 选择文件。目录树只能来自已登记文件事实，不能为了填充界面虚构磁盘内容。

Skill 本体和引用关系分开管理：`资产 → Skills` 负责来源审查、安装、更新、回滚和卸载；Agent 的 Skills 配置只维护该 Agent 或 Agent × Workspace 的显式引用。安装或更新 Skill 本体不得自动分配给任何 Agent，卸载后失效引用继续可见并提示修复。

条件分支：

- 多个终端、编辑器或宿主客户端不会形成 Bandi 运行状态；其外部写入统一按“编辑基线 → 保存前复核 → `BaselineChanged` → 三方 Diff → 解决冲突后重新保存”处理，且没有可靠证据时只称“其他程序或终端”；
- 恢复历史版本仍重新执行基线、共享影响和长期权限风险检查；
- 恢复成功生成新 ConfigRevision，旧历史不变；
- 正式 Memory 不走 ConfigRevision，继续使用 MemoryCandidate → Review → MemoryRevision。

### 8.5 六类保存结果与页面行为

所有配置编辑器复用同一保存结果模型，但保持现有页面结构，不新增保存中心：

| 保存结果 | 页面行为 |
| --- | --- |
| 保存成功 | 保留当前页签与对象；更新查看态，显示证据等级、实际目标、ConfigRevision 和写后验证证据；`memory-only` 只更新页面内存 |
| 校验失败 | 停留编辑态；错误紧邻字段并聚焦首个错误；不写入、不生成 revision |
| 基线已变化 | 保留用户编辑，打开三方 Diff；允许载入外部版本、复制用户编辑或基于外部版本继续；不得静默覆盖 |
| 配置文件冲突 | 保留编辑与冲突内容，进入逐项解决；全部解决前禁用最终保存，不生成 revision |
| 只读或能力未完成 | 不发起写入；保留可复制内容，展示 `read-only` 及 `reason`、`evidence`、`remediation` |
| 写入或写后验证失败 | 停留编辑态并保留输入；显示失败阶段、目标和可安全重试的修复建议；不得显示成功或生成正式 revision |

取消保存只丢弃当前未保存编辑，不修改外部文件。恢复历史、正式记忆写回和共享资产保存仍复用相同结果语义，再叠加各自的风险确认或审核条件。

### 8.6 审核并写回记忆候选

```text
创建 MemoryCandidate，并指定唯一目标 MemorySpace
→ 校验提议权限和审核关系
→ 审核人批准 / 驳回 / 要求修改
→ 批准后重新校验基线与权限
→ 原子写入并生成 MemoryRevision
```

审核通过、文件写入成功和 Runtime 是否加载分别表达。任务摘要或终端中间状态不会自动进入正式记忆。

## 9. 配置状态与证据

Desktop 只展示长期配置管理可直接证明的状态：

```text
未修改 / 有未保存修改 / 校验失败
保存中 / 已保存到目标文件 / 保存失败
外部变化 / 配置文件冲突
ConfigRevision 已记录
MemoryCandidate 待审核 / MemoryRevision 已写入
BackupSnapshot 已创建 / 恢复成功或失败
长期权限变更已确认
```

禁止展示或推断：Session 已连接、Agent 在线或执行中、当前步骤、Todo、工具调用、实时日志、任务完成、Usage、停止或恢复。Plugin、MCP、Hooks 和 Settings 只表达安装或配置事实。

## 10. 视觉与布局基线

1. 公司数字孪生关系和工作区上下文优先，不以统计卡片墙为主视觉；
2. 三段式桌面 Shell，树、表格、关系行和证据时间线优先；
3. 使用紧凑但可读的桌面密度；
4. 路径、命令、版本和哈希使用等宽字体；
5. 状态由文字、图标和颜色共同表达；
6. 默认暗色，语义 Token 支持未来亮色；
7. 56px 配置管理 Rail 始终保留；Agent 上下文栏默认跟随窗口：`>=1280px` 使用 220px 展开栏，`<1280px` 使用 64px 紧凑栏；固定展开在 `960–1279px` 使用 188px、仅在 `<960px` 紧凑显示；用户可显式隐藏并从个性化设置恢复，无最近 Agent 时也自动隐藏且不改写偏好；
8. Shell 最多展示 6 个会话内最近访问 Agent，允许移除非当前项和清空其他记录，但不持久化，也不展示在线、运行、Session 或任务状态；客户端配置收进设置，Claude Code 主执行衔接保持独立；
9. Tauri 最小目标窗口 `960×640` 仍能完成核心流程；产品不承诺 `<960px` 的移动端信息架构，若开发预览窗口更窄，则只做安全收紧：隐藏或紧凑化 Agent 上下文栏、配置领域改选择器、Dialog 改全高 Sheet；
10. 宽表格和 Diff 在自身容器滚动，页面整体不横向滚动；
11. 所有假数据、假成功和无证据“运行中”均禁止。

## 11. 首版范围

### 11.1 必须实现

- Workspace 选择、扫描、绑定和最近使用；Workspace 可暂不关联但最多归属一个 Company，并管理该公司内唯一主责部门、默认项目负责人和多个协作部门；
- 多现实 Company、树形 Department、Role、部门主管、成员、Agent 唯一主属部门和带范围的跨部门服务授权管理；
- Agent 启用、停用与归档生命周期，以及永久删除的独立高风险确认；
- Company 内共享资产、跨 Company 单独注册与授权、引用保护和 Agent 局部定制；
- 董事长—助理—主管—专业/执行 Agent 的组织关系；
- 目录化 AgentPackage 与 WorkspaceBinding；
- 用户明确选择的单个 `.claude/agents/*.md` 两阶段安全导入：只读预览、source hash 复核、创建受管副本且不修改原文件；
- 外部目录的 reference-only 登记，与真实导入明确区分；
- 其他 SourceAsset 扫描、引用和显式导入能力按后续已验证切片扩展；
- 分层 SOP / WorkflowDefinition、OrchestrationPolicy 和静态循环检查；SOP 仅作为供 Claude Code 助理解析的配置定义；
- Desktop 只管理组织关系和配置资产并提供打开 Claude Code 的衔接，不提供任何单次任务操作界面；
- Claude Code 中按“助理选必要部门并委派主管、主管按职责/Skills/Workspace/权限选员工”完成分层委派，并支持复杂方案确认、高风险动作再确认和逐级汇报；
- 普通配置直接保存到真实文件，支持基线检查、原子写入和写后验证；按需 Diff、共享影响、配置文件冲突保护和长期权限扩大确认；
- 每次成功保存生成 ConfigRevision，支持上下文内历史、版本比较和恢复；恢复生成新 revision；
- 设置中以“配置与备份”作为稳定分类；该分类同屏管理配置方案、唯一的全局 Agent 根目录、外部变化保护、本地手动/自动快照、历史查看和按 Company、Agent 或文件恢复。单方案历史与恢复使用 `ConfigRevision`；跨资产容灾使用 `BackupSnapshot`，“全部配置”只包含 Bandi 自有的方案元数据，不代表宿主工具真实配置已备份。创建与恢复使用 Dialog，恢复前自动保存当前状态；旧 `/settings/backup` 仅作兼容跳转，不新增全局一级“配置管理”或“备份”菜单；
- Bandi Desktop、Rust Local Service 和 `bandi` CLI；
- Bandi Plugin：Skill、董事长助理 Agent、Bandi MCP、最小 Hooks 和 settings；
- PluginInstallation 和 Claude Code 集成状态；
- `/bandi:bandi` 标准入口；
- 四类 MemorySpace、独立逻辑文件载体和 owner/steward/reviewer 治理；
- MemoryCandidate、人工审核、自审升级、Diff、备份、原子写回与 MemoryRevision；
- macOS 首发所需的受限系统操作。

### 11.2 可选或渐进

- `/bandi` standalone 薄别名；
- 自然语言语义触发候选说明与低风险引导；
- 更多终端适配；
- GitHub 或自定义 Git 远程备份：Bandi 自动创建的仓库必须为 Private，不提供公开选项；连接已有远端时验证私有状态，明确公开时拒绝备份。

### 11.3 后续能力

只有可靠 Runtime Connector 存在后，才增加：

- 如未来评估运行观测能力，必须另立产品决策，且不得挤入配置管理主线；
- 自动测试、独立验收和交付报告仍留在 Claude Code；
- 从会话自动提炼记忆候选；
- 语义检索、向量索引、摘要压缩和自动遗忘/归档；
- 员工成长、记忆质量和能力缺口闭环；
- Windows、远程 Web 和多用户协作。

### 11.4 明确不做

- 内嵌终端；
- 后台隐藏托管 Claude Code；
- 面向大型集团的无限层级组织、人事、考勤或行政管理系统；
- 自动创建正式公司、部门、岗位或长期 Agent；
- 自动扫描或批量导入 Claude Agent，或把 `CLAUDE.md`、Rules、Skills、MCP、正式 Memory 在首期自动转换进受管包；
- 自动安装未知 Skill/MCP；
- 静默覆盖本地配置；
- 让普通主管或员工成为董事长的默认主会话入口；
- 伪装 Session 已连接、Agent 执行中或配置已加载；
- 一级“运行”模块；
- 镜像 Claude Code 聊天、工具调用、Todo、日志和 Agent View；
- Desktop 任务创建、运行、当次部门/员工选择、人员调度、方案或流程确认、推进、聊天、阻塞/审批、汇报和验收界面；
- Desktop SOP 执行器，或未经用户同意将临时协作自动保存为 SOP。

## 12. 首版验收标准

1. Desktop 默认主线是导入或创建 Agent、查看和修改配置、安全保存、查看或恢复 ConfigRevision，并回到 Claude Code；首次使用不依赖 Workspace 或组织；
2. 用户能管理多 Company、树形 Department、长期 AgentPackage、WorkspaceBinding 和显式共享资产；
3. AgentPackage 使用稳定 `agent-id`，不随组织关系移动；组织身份不形成隐式配置继承或权限授予；
4. 普通配置安全保存执行目标解析、校验、当前基线检查、原子写入与写后验证；
5. 每次成功保存生成不可变 ConfigRevision；失败不生成；历史可比较，恢复生成新 revision 并保留恢复来源；
6. ConfigRevision、MemoryRevision、BackupSnapshot 与 RuntimeProjection 的职责清晰且不可混用；
7. 配置文件外部变化不能被静默覆盖，真实配置冲突必须解决后保存；
8. 共享资产影响只在修改共享本体时出现；长期权限收紧普通保存，扩大时明确确认；
9. 所有正式 MemorySpace 变化遵循 MemoryCandidate → Review → MemoryRevision，提议者不能自审；
10. SOP 只定义责任、步骤、输入输出、依赖、确认/升级条件与验收，不在 Desktop 运行或产生待办；
11. Desktop 只提供 Workspace、cwd 和命令衔接，不记录接入、启动、Session 或执行证据；
12. 任务方案、人员分配、执行、阻塞、一次性权限授权、任务审批、汇报和验收全部在 Claude Code CLI；
13. 一级导航不包含运行、工作流、审批、历史或版本中心；历史从 Agent、资产或文件上下文按需进入；
14. Desktop 不镜像聊天、工具调用、Todo、日志、Agent View、Usage、停止/恢复和执行状态；
15. 备份与恢复独立于日常版本；远程 Git 仅允许私有仓库，凭据和执行过程永不备份，正式 Memory 远程备份需单独确认；
16. 960×640 下可完成配置查看、保存、历史比较/恢复、长期权限确认和正式记忆审核。
