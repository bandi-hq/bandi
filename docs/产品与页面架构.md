## 2. 产品定位

### 2.1 一句话定位

**Bandi 是现实创业公司的本地数字孪生：用户以董事长身份，在 Desktop 中可视化管理多 Agent 配置资产及其组织关系，并回到自己已有的 Claude Code CLI 中通过董事长助理指挥公司工作。**

Bandi Desktop 的唯一任务主线是多 Agent 配置资产与组织关系的可视化管理。它让用户选择员工、查看职责、Instructions、Skills、Memory、Rules、MCP、权限、Agent × Workspace 专属配置和 SOP 等完整配置，修改后保存到真实配置文件，并提供打开用户自己 Claude Code 的衔接。董事长下达目标、助理判断所需部门、复杂方案确认、跨部门委派、主管选择员工、执行协作、阻塞与审批、逐级汇报和最终验收，全部发生在用户自己的 Claude Code CLI 中，由董事长与董事长助理完成主交互；用户无需在 Desktop 为每次任务选择部门或员工。

品牌短句：

> 管理你的 AI 班底。

Bandi 不是随意生成虚拟 AI 公司的沙盒。一个 `Company` 对应一家现实公司的数字孪生；用户管理多个 Company，表示他们正在管理多家现实公司的本地映射。

### 2.2 核心用户与角色

首版优先服务已经使用 Claude Code CLI，并开始维护多个 Agent、Skill、MCP、项目规则和工作目录的个人开发者、一人公司经营者和小型 AI 原生团队负责人。

| 角色 | 定义 | 主要职责 |
| --- | --- | --- |
| 董事长 | 使用 Bandi 的真实用户 | 确定方向、建立组织、下达目标、审批关键事项和最终验收 |
| 董事长助理 Agent | 用户自己的 Claude Code CLI 中唯一默认的公司任务交互入口 | 理解目标，判断必要部门；低风险事项直接说明并推进，多部门复杂事项先给出简明方案供董事长确认；委派主管、协调跨部门依赖、处理升级并向董事长汇报 |
| 部门主管 Agent | Claude Code 执行现场中的部门管理与编排角色 | 根据职责、Skills、Workspace 与权限选择必要员工，驱动部门协作，审批部门交付并向助理汇报 |
| 专业 Agent | 产品、架构、研究等专业岗位 | 执行专业工作，并可在授权范围内编排岗位级或任务级子工作流 |
| 执行 Agent | 具体执行岗位 | 执行步骤，提交交付物、证据和阻塞；是否可编排由授权决定 |

董事长保留最终决定权。任何 Agent 都不能替董事长批准关键方案、伪造董事长同意或完成最终验收。

### 2.3 产品核心价值

1. **真实映射**：把现实公司的部门、岗位、责任与本地项目工作环境建立明确关系。
2. **看得见**：让 Agent 的灵魂、职责、记忆、Skill、MCP、规则、权限和编排范围集中可见。
3. **管得住**：通过策略、审批、WorkspaceBinding、不可变投影和审计约束执行。
4. **记得清**：区分 Agent 长期记忆、Agent × Workspace 项目记忆、Workspace 公共记忆和 Department × Workspace 项目管理记忆，并展示来源、所有权、归口与审核状态。
5. **用得上**：在用户自己的 Claude Code 中快速接入公司，或完整启动董事长助理新会话。
6. **可追溯**：配置、记忆候选、接入、启动、委派、交付和审批按实际证据呈现，不伪造运行状态。

## 3. 产品构成与责任边界

```text
Bandi Desktop ─────────┐
bandi CLI ─────────────┼──→ Rust Local Service ──→ 本地事实、策略与审计
Bandi Plugin ──────────┘           │
  ├── Skill                        ├── SQLite / AgentPackage / SourceAsset
  ├── 董事长助理 Agent             ├── Workspace / Git / Keychain
  ├── Bandi MCP                    └── 受限本地系统操作
  ├── Hooks
  └── settings
        ↓
用户自己的 Claude Code CLI

Runtime Connector（后续）
  └── 提供可靠 Session、执行、Usage、停止和恢复证据
```

| 组成 | 负责 | 不负责 |
| --- | --- | --- |
| Bandi Desktop | Company、Department、Agent 组织关系，以及 Instructions、Skills、Memory、Rules、MCP、权限、Agent × Workspace 专属配置、SOP 等配置资产的查看、编辑和保存；提供打开 Claude Code 的衔接 | 任务创建或运行、每次任务的部门/员工选择与调度、方案或流程确认、推进、聊天、汇报、审批和验收；Claude 推理执行、隐藏托管 CLI 或镜像 CLI 执行过程 |
| Rust Local Service | 统一事实、策略、投影、审计、接入匹配及受限系统能力 | 替用户作经营决定 |
| `bandi` CLI | 系统 Shell 中的状态、诊断、接入和完整启动入口 | 维护另一套业务事实 |
| Bandi Plugin | Claude Code 侧稳定能力基线和 Local Service 适配 | 长期组织事实数据库 |
| Skill | 告诉 Claude 如何识别和完成 Bandi 流程 | 硬编码全部公司与员工关系 |
| SOP / WorkflowDefinition | 供 Claude Code 中的董事长助理解析的目标、步骤、分工、审批、交接与验收配置定义 | Desktop 内的任务模板执行器、调度器或流程推进引擎 |
| 董事长助理 Plugin Agent | 提供稳定的运行时身份、职责和工具边界 | 取代长期 AgentPackage |
| Bandi MCP | 为 Claude Code 中的助理提供组织、SOP、权限和配置的结构化查询，并按策略记录必要事实 | 定义 SOP、控制终端、替 Desktop 执行任务或决定组织关系 |
| Hooks | 工具门禁、审计和有限事件证据 | 绝对 fail-closed 安全边界或可靠 Connector |
| settings | Plugin 默认配置及支持的覆盖 | 公司与 Workspace 的动态事实 |
| Claude Code CLI | 用户实际对话与执行环境 | Bandi 的组织管理平面 |
| Runtime Connector | 后续可靠关联 Session、执行与 Usage | 成为业务事实的并列写入者 |

### 3.1 Bandi Plugin 与外部 Plugin 的区别

- **Bandi Plugin**是产品自有集成基线，具有安装、版本、作用域和组件完整性状态；
- **第三方 Plugin**在导入或引用前属于 `SourceAsset`；
- **Plugin 中的董事长助理 Agent**是 Claude Code 运行时定义；
- **AgentPackage**才是董事长助理和其他长期员工的配置事实来源；
- **RuntimeProjection**引用 Bandi Plugin 基线并叠加公司、Workspace、Agent 和策略上下文，不等于重新安装 Plugin。

## 4. 进入 Bandi

### 4.1 入口表面

```ts
type EntrySurface =
  | 'desktop'
  | 'system_cli'
  | 'plugin_skill'
  | 'slash_alias'
  | 'semantic_trigger'
```

| 入口 | 确定性 | 产品语义 |
| --- | --- | --- |
| Bandi Desktop | 高 | 可视化选择接入当前会话或完整启动新会话 |
| `bandi` | 高 | 系统 Shell 入口，可诊断、选择上下文或完整启动 |
| `/bandi:bandi` | 高 | Bandi Plugin Skill 的标准命名空间入口 |
| `/bandi` | 高，但可选 | 额外 standalone Skill/Command 薄别名，只转发正式能力 |
| “小班”“班底”“bandi”“让董事长助理处理” | 低至中 | 自然语言语义触发候选，不是确定性唤醒词 |

自然语言在低置信度、存在多个公司或 Workspace、参数不完整、涉及写操作或启动操作时必须请求确认，不能绕过策略和审批。

### 4.2 两种进入模式

```ts
type EntryMode = 'attach_current' | 'launch_new'
```

#### 快速接入当前会话（`attach_current`）

```text
用户已经位于 Claude Code 会话
→ 从 Plugin 标准命令、可选别名或语义触发进入
→ 获取当前 cwd 与宿主能够证明的上下文
→ Local Service 匹配 Workspace、Company、董事长助理和策略
→ 有歧义时由董事长选择
→ 返回 AttachmentContext
→ 当前会话按接入限制使用 Bandi 能力
```

固定边界：

- 不创建新 Claude Session；
- 不打开新终端；
- 不声称能重写当前会话启动时的完整系统提示、Agent、模型、settings 或权限；
- 不要求完整编译新会话的 RuntimeProjection；
- 可以产生接入记录和有限 MCP/Hook 证据，但不自动证明 Session 已可靠关联。

#### 完整启动新会话（`launch_new`）

```text
从 Desktop、bandi CLI 或 Plugin 发起
→ 选择或确认 Company 与 Workspace
→ 解析董事长助理、可委派组织、Workflow 和策略
→ 校验 Plugin 基线与 Agent × Workspace 专属配置
→ 编译完整 RuntimeProjection
→ 建立 LaunchContext 和启动记录
→ 董事长确认
→ 创建新的董事长助理 Claude Code 会话上下文
```

固定边界：

- 新建董事长助理会话，而不是继续或恢复旧会话；
- 编译完整、不可变、可审计的 RuntimeProjection；
- 可以请求系统终端打开，但终端打开不等于 Session 已关联；
- Claude Code 的具体启动参数由实施版本验证，不在产品契约中写死。

| 差异 | `attach_current` | `launch_new` |
| --- | --- | --- |
| 新建 Session | 否 | 是 |
| 新开终端 | 否 | 视入口和用户选择而定 |
| 产物 | AttachmentContext | RuntimeProjection + LaunchContext |
| 完整重建启动配置 | 否 | 是 |
| 保留当前对话 | 是 | 新会话隔离 |
| 典型入口 | Plugin Skill、别名、语义触发 | Desktop、系统 CLI、Plugin Skill |

## 5. 产品主线与原则

### 5.1 公司数字孪生初始化

```text
安装 Bandi Desktop
→ 检查 Rust Local Service、bandi CLI 和 Claude Code
→ 安装或验证 Bandi Plugin
→ 选择或创建 Workspace
→ 建立现实 Company、部门与岗位映射
→ 创建或导入董事长助理及员工 AgentPackage
→ 配置 Workflow、权限、审批和 WorkspaceBinding
```

### 5.2 日常配置管理

```text
在 Desktop 的组织或 Agents 中选择员工
→ 查看完整配置：职责、Instructions、Skills、Memory、Rules、MCP、权限、Agent × Workspace 专属配置、SOP
→ 直接修改需要调整的配置
→ 按风险和资产类型执行必要校验
→ 保存到真实 AgentPackage 或其引用的真实配置文件
→ 回到 Claude Code 使用更新后的配置
```

普通配置采用“查看—修改—保存”的直接心智模型，不强制经过草稿、Diff、影响分析、冲突处理、审批和发布。每个 AgentPackage 独立拥有该员工的配置，部门和岗位只描述组织、职责与委派关系，不向 Agent 隐式继承配置：

- Agent 自有配置直接保存回该 AgentPackage，写回目标明确；
- Company / 全局配置只提供 Claude Code 底层公共配置、普通默认值、共享资产和不可突破的安全边界；
- Agent 未设置普通配置时才使用全局默认；全局强制安全限制不能被 Agent 放宽；
- 公共 Skill、Rule、MCP 和 SOP 通过 AgentPackage 显式引用，不因所属部门或岗位自动生效；
- Agent 在特定 Workspace 中的专属配置仍归该 Agent 所有，通过 Agent × Workspace 的 WorkspaceBinding 表达；
- 来源默认收起，用户需要区分自有、共享引用、全局默认或全局强制时再展示；
- Diff 仅在用户主动查看，或检测到保存期间发生外部并发修改时出现；
- 影响分析只针对被多个 Agent 显式引用的共享资产；
- 普通保存不需要董事长审批或“发布”动作；
- 权限范围扩大、敏感路径新增写入、危险 MCP/命令开放等高风险变更必须明确确认；
- Memory 不是普通配置例外的豁免项：所有正式 MemorySpace 变化仍必须先形成 MemoryCandidate，经审核后写入并生成 MemoryRevision。

### 5.3 日常执行

所有任务相关交互均留在用户自己的 Claude Code CLI，Desktop 只负责打开或衔接 Claude Code，不提供任务操作界面：

```text
快速接入当前 Claude Code 会话
或完整启动新的董事长助理会话
→ 董事长在终端向助理下达目标
→ 助理判断完成目标所必需的部门
→ 低风险事项：助理简要说明判断后直接委派
→ 多部门复杂事项：助理先在终端给出简明方案，董事长确认后委派主管
→ 主管根据岗位职责、Skills、Workspace 和权限选择必要员工
→ 专业与执行 Agent 在终端执行、协作并提交交付物与证据
→ 阻塞与一般审批逐级上报；高风险动作在执行前再次请求董事长确认
→ 员工向主管、主管向助理、助理向董事长逐级汇报
→ 董事长在终端完成最终验收
```

用户不需要在 Desktop 为每次任务预选部门或员工。临时协作方式默认留在当前终端上下文；只有确有复用价值时，助理才建议沉淀，并在用户同意后保存为 SOP 配置资产。

### 5.4 首版原则

1. **现实公司优先**：Company、部门、岗位和 Workflow 表达真实经营关系。
2. **Workspace 是执行环境**：它不是公司、部门或组织树。
3. **多入口、单一中枢**：Desktop、CLI 和 Plugin 共用 Local Service，不产生多主事实。
4. **Agent 目录化且配置独立**：每个长期 Agent 是独立 AgentPackage，不是一个 Prompt 文件；部门和岗位不形成隐式配置继承。
5. **公共配置显式可见**：全局只提供底层公共配置、普通默认、显式共享资产和强制安全边界；Agent 自有设置优先于普通默认，公共资产必须显式引用。
6. **编排分层授权**：组织身份不自动授予权限；能力由显式配置的组织范围、Workflow、委派深度、审批和 Workspace 权限共同决定。Agent 可以自行收紧权限，但扩大权限必须由有权主体确认。
7. **管理与执行分离**：Desktop 管理，用户自己的 Claude Code 执行。
8. **接入与启动分离**：AttachmentContext 不能伪装成完整 RuntimeProjection。
9. **Plugin 与投影分离**：Plugin 是稳定基线，投影是动态快照。
10. **SOP 定义协作边界**：SOP/WorkflowDefinition 是供 Claude Code 中的助理和主管解析的配置资产，不是 Desktop 执行器；MCP 只提供结构化连接。
11. **记忆按作用域治理**：MemorySpace 是领域边界，文件只是载体；不同 Agent、Workspace 和 Department 的记忆默认隔离。
12. **候选先审后写**：运行和人工编辑先产生 MemoryCandidate，任何 Agent、MCP 或 Hook 都不能直接改正式长期记忆。
13. **运行时只加载授权记忆**：完整启动生成可解释的 MemoryProjection，快速接入只提供有限 MemoryContext。
14. **普通配置直接保存**：不把草稿、Diff、影响、冲突、审批和发布强加给每次编辑，只在用户主动查看、共享影响、真实冲突或高风险变更时介入。
15. **状态必须有证据**：配置存在、候选批准、文件写入、投影重编译、Runtime 加载和任务完成分别表达。
16. **CLI 承载完整任务交互**：下达目标、判断部门、复杂方案确认、跨部门委派、选员工、执行协作、阻塞/审批、逐级汇报和最终验收全部留在用户自己的 Claude Code CLI，由董事长与董事长助理完成主交互。
17. **Desktop 不参与单次任务**：不要求用户为每次任务选择部门或员工，不提供任务创建、运行、调度、确认、推进、聊天、汇报或验收界面。
18. **SOP 是配置，不是执行器**：SOP 供 Claude Code 助理解析；临时协作默认留终端，有复用价值且经用户同意后才保存为 SOP。

### 5.5 产品不是

- 内嵌终端或 Claude Code 替代品；
- 虚拟办公室、员工养成游戏或 Agent 群聊展示器；
- 任意生成虚拟公司的组织模拟器；
- 后台不可见地托管用户 CLI 的执行平台；
- 未经确认自动覆盖或删除本地配置的同步器；
- 把 Plugin 已安装、MCP 可连接或终端已打开当作任务已运行的监控系统；
- 镜像 Claude Code 的聊天、工具调用、Todo、日志或 Agent View 的执行看板；
- 在 Desktop 中创建或运行任务、选择当次任务的部门/员工、确认方案、人员调度、推进流程、聊天、处理阻塞/审批、汇报或验收；
- 把 SOP 当作由 Desktop 自动执行和推进的流程引擎。

## 6. 核心领域模型

### 6.1 Workspace

用户授权的本地执行上下文，包含路径、Git、Claude 项目配置、关联公司、项目责任关系、WorkspaceBinding 和入口偏好。一个 Company 可以关联多个 Workspace；一个 Workspace 可以暂不关联组织，但首版最多只能归属一个 Company，二者不互为别名。同一本地目录如需服务不同 Company，应建立各自独立的 Workspace 记录并保持公司上下文隔离，或把可复用内容建模为显式共享资产，不能让一个 Workspace 同时加载多家公司的组织、默认配置和安全边界。

首版业务语言中的“项目记忆”以 Workspace 为项目边界，规范字段继续使用 `Workspace`，不新增并列的 `Project` 对象。每个已关联 Company 的 Workspace 必须且只能设置一个来自该 Company 的主责部门，可设置零到多个同公司协作部门；主责部门主管同时作为默认项目负责人和 Workspace 公共记忆归口人。主责主管对项目总体结果、公共事实整理、跨部门进展汇总和向董事长助理汇报负责；协作主管只对本部门承接的目标、交付和部门项目记忆负责。董事长助理负责跨部门协调与升级，不接管项目台账。

Workspace 公共记忆始终归 Workspace 所有。更换项目负责人或主责部门时，必须明确确认新的主责部门与主管，保留公共记忆、各部门项目记忆和历史记录，只转移后续归口及相应权限；不得自动修改或删除 AgentPackage、WorkspaceBinding 和既有记忆。原主责部门可按用户选择转为协作部门或解除项目关系。

更换 Workspace 所属 Company 是高影响关系变更：必须重新选择新公司的主责部门、项目负责人和协作部门，并在确认前展示将失效的旧公司共享资产引用、委派关系、权限和记忆可见性。Workspace 本地目录、公共记忆、部门项目记忆与历史记录不被删除；旧公司的 Department × Workspace 记忆转为只读历史边界，除非用户另行迁移或归档。系统不得把旧部门自动映射到新公司，也不得静默保留跨公司权限。

### 6.2 Company、Department 与 Role

- `Company`：一家现实公司的本地数字孪生边界；
- `Department`：公司内具有上级关系的职责单元，可表达中心、部门或小组；
- `Role`：使命、职责、输入、交付、边界、升级条件和完成标准的结构化定义。

首版支持多公司与树形 Department，通过 `parent_department_id` 表达上下级。数据结构不硬编码层数，产品面向现实创业公司优化，建议组织深度不超过三层，过深时提示而非建设大型集团人事系统。组织管理支持创建公司、添加/编辑/移动部门、设置主管、岗位、成员 Agent 和委派边界；首版通过选择上级部门移动节点，不优先实现拖拽。

每个 Agent 可以暂不归属，但最多只有一个主属部门；主属部门决定直属主管、默认汇报链、主要岗位、长期记忆默认审核人和默认可参与的部门项目。Agent 可以通过零到多个显式服务授权为其他部门工作，每项授权必须限定服务部门、允许能力、适用 Workspace、有效期或状态及禁止事项；服务关系不改变主属部门、直属主管，也不授予管理目标部门成员、审批目标部门预算或修改其项目台账的权力。

Company、Department 与 Role 用于组织展示、职责定义和委派判断，不构成向 AgentPackage 自动注入配置的继承层。移动 Agent 的主属部门只改变组织、汇报和委派关系，不移动或自动改写 AgentPackage、Skills、Rules、MCP、权限或 WorkspaceBinding；原服务授权和委派关系失效时作为配置缺口提示。删除仍有下级或成员的部门时必须先选择迁移目标，不得连带删除 AgentPackage。只有被设为 Workspace 主责或协作方的部门，才建立对应的 `Department × Workspace` 项目关系和项目记忆；该记忆由部门主管归口维护，但不属于主管个人 AgentPackage，也不跨 Workspace 自动复用。

Agent 生命周期固定为 `active`、`inactive` 和 `archived`。暂时不用时优先停用，长期保留时归档；两者均保留稳定身份、AgentPackage、正式记忆、历史和引用，不允许被新的委派选中。永久删除 AgentPackage 是独立高风险操作，执行前必须展示仍存在的 WorkspaceBinding、共享资产引用、审核责任和记忆影响，并要求用户明确确认；从部门移除成员或删除组织关系不得隐式删除 AgentPackage。

### 6.3 AgentPackage

长期、独立、可成长的 Agent 配置事实来源：

```text
agents/
└── <stable-agent-id>/
    ├── agent.yaml
    ├── soul.md
    ├── instructions.md
    ├── memory/
    │   └── long-term.md
    ├── config/
    │   ├── skills.yaml
    │   ├── rules.yaml
    │   ├── mcp.yaml
    │   ├── permissions.yaml
    │   └── orchestration.yaml
    ├── workflows/
    └── workspaces/
        └── <workspace-id>/
            ├── config.yaml
            ├── instructions.md
            └── memory.md
```

这是首版逻辑契约，不提前冻结 YAML 的全部字段，也不要求不存在内容的可选文件预先生成。`agent.yaml` 保存稳定身份、显示名、状态和岗位引用；`soul.md` 保存长期行为原则；根级 `instructions.md`、`config/`、`memory/long-term.md` 和 `workflows/` 属于跨 Workspace 的 Agent 配置；`workspaces/<workspace-id>/` 只保存该 Agent 面向目标 Workspace 的专属配置、说明和个人项目记忆。Skill、Rule、MCP 和 SOP 既可由 Agent 自有文件承载，也可在配置中保存显式共享引用。

首版 Bandi 自管 AgentPackage 默认位于 `~/.bandi/agents/<stable-agent-id>/`；外部 AgentPackage 可保持用户授权的原位置并作为 SourceAsset 引用或显式导入。AgentPackage 以不可变 `agent-id` 定位，不从目录名、显示名、Company、部门或岗位推断身份。重命名、移动主属部门、增加跨部门服务授权、变更主管或更换 Workspace Company 均不移动 AgentPackage。允许用户从 Bandi 通过表单编辑，也允许打开真实目录和文件；外部编辑后 Local Service 必须重新扫描、读取和比较基线，不得静默覆盖。

董事长助理、部门主管、专业 Agent 和执行 Agent 使用同一目录模型，每个 AgentPackage 独立拥有其 Instructions、Skills、Rules、MCP、权限、编排和 Workspace 专属配置。身份标签不直接授予编排权，部门和岗位也不产生隐式配置继承。董事长助理仍是一个独立 Agent，其个人配置不能代替 Company / 全局配置；后者只承载 Claude Code 底层公共配置、普通默认值、共享资产注册和强制安全边界。

普通单值配置遵循“Agent 明确设置优先，否则使用全局默认”；全局强制安全边界不可被 Agent 放宽。共享 Skill、Rule、MCP 和 SOP 不自动注入，必须由 AgentPackage 显式引用。首版共享资产以 Company 内共享为主；跨 Company 复用必须把资产单独注册为跨公司共享并对目标 Company 明确授权，不能因名称、路径或同一创建者自动可见。共享资产本体由明确所有者维护，修改时提示全部有效引用者；Agent 如需局部定制，应创建自有配置或覆盖层，不直接篡改共享本体。删除仍有引用的共享资产前必须先解除、迁移或替换引用。

`memory/` 只承载该长期 Agent 跨 Workspace 延续的长期记忆；Workspace 公共记忆和部门项目记忆不存入任何个人 AgentPackage。组织身份、主管标签或服务关系本身不授予文件、命令、网络、MCP、记忆或委派权限；这些能力必须显式配置。Agent 可以在已有边界内自行收紧，但不得自行扩大；缺少权限时向上报告，由有权主体确认后写入配置。

### 6.4 SourceAsset

用户已有的 Custom Agent、Skill、MCP、Rules、Memory、Settings、Hook、第三方 Plugin、Command、Workflow 或脚本。扫描只建立索引；保持引用时外部文件仍是来源事实。普通 Agent 配置显式导入后由 AgentPackage 纳管；Memory 导入必须先选择目标 MemorySpace，并以候选方式审核写回。

### 6.5 WorkspaceBinding

```text
AgentPackage 主配置
+ 该 Agent 在目标 Workspace 的专属 Instructions / Rules
+ 该 Agent 在目标 Workspace 的 Skill / MCP 显式引用
+ Agent × Workspace 独立项目记忆引用
+ 当前可读取的公共/部门 MemorySpace 引用
+ 该 Agent 在目标 Workspace 使用的账号
+ 该 Agent 在目标 Workspace 的局部权限与模型设置
= WorkspaceBinding
```

每个长期 Agent 在每个 Workspace 下都有独立的项目记忆文件或逻辑文件；不同 WorkspaceBinding 的 Agent 项目记忆、MCP 账号和权限默认隔离。WorkspaceBinding 是 AgentPackage 内针对目标 Workspace 的专属配置，不是 Workspace 从外部覆盖所有 Agent 的公共继承层。它只引用当前可读取的共享 MemorySpace，不复制或取得其所有权。

### 6.6 MemorySpace、MemoryCandidate 与 MemoryRevision

`MemorySpace` 是具有独立作用域、所有权、归口人、审核策略、可见策略和文件载体的逻辑记忆边界。文件是持久化载体，MemorySpace 才是产品领域对象。

```text
id
scope_type / scope_key
owner
steward
review_policy
visibility_policy
storage_locator
current_revision
content_hash
updated_at
```

- `owner`：领域上拥有记忆的主体；
- `steward`：负责整理、去重和处理候选的归口人；
- `reviewer`：按策略批准、驳回或要求修改；
- Local Service：执行批准后的安全写入，不因此拥有内容。

首版固定四类 MemorySpace：

| 记忆空间 | 隔离键 | 所有者 | 默认归口 | 默认审核与自审升级 |
| --- | --- | --- | --- | --- |
| Agent 长期记忆 | Agent | 对应长期 Agent | 对应 Agent | 直属上级；董事长助理由董事长审核 |
| Agent Workspace 项目记忆 | Agent × Workspace | 对应 Agent | 对应 Agent | 直属上级；董事长助理由董事长审核 |
| Workspace 公共记忆 | Workspace | Workspace | 项目主责部门主管 | 主责主管审核；主管本人提出时升级董事长助理 |
| 部门项目记忆 | Department × Workspace | Department × Workspace 边界 | 部门主管 | 主管审核；主管本人提出时升级董事长助理 |

“每个 Agent”包括董事长助理、部门主管、专业 Agent 和执行 Agent。董事长助理的 Agent 长期记忆就是跨 Workspace 延续的总记忆，沉淀与董事长和部门主管交互形成的公司原则、长期偏好、重要决策和协调经验；其 Agent × Workspace 项目记忆只保存当前项目中的协调、汇报和待董事长决策摘要，不承担完整项目管理。项目目标、计划、进展、风险、依赖、分工和交付由负责项目的部门主管维护在 Department × Workspace 项目记忆中；Workspace 公共记忆由项目主责部门主管归口。Agent 项目记忆默认非共享，但仍受权限、审核和审计约束。

`MemoryCandidate` 是运行、会话或人工编辑产生的待审核建议，必须指定唯一目标 MemorySpace。`MemoryRevision` 是候选获批并成功写入后的不可变版本记录，保存来源、审核、版本、哈希和写入结果。候选批准不等于文件已写入，文件写入也不等于 Runtime 已加载。

### 6.7 SOP / WorkflowDefinition 与 OrchestrationPolicy

`SOP / WorkflowDefinition` 是由 Desktop 查看、编辑和保存，供 Claude Code 中董事长助理解析使用的配置定义，描述目标、步骤、依赖、并行、分工、子流程、交付物、证据、审批、失败与验收。它不是 Desktop 执行器，不会自行创建任务、选择人员或推进流程；实际解释、委派、确认与执行均发生在用户自己的 Claude Code CLI。

`OrchestrationPolicy` 决定 Claude Code 执行现场中的某个 Agent 是否可以启动、委派、审批或组合工作流，至少检查：

```text
岗位职责 + 组织关系 + Workflow 权限 + 委派范围
+ 最大深度 + 审批/升级规则 + Workspace/工具权限
```

必须阻止跨组织越权、循环委派、无限递归、职责冲突和 Agent 自批自身最终交付。

### 6.8 WorkflowRun 与 WorkflowStepRun

`WorkflowRun` 是 Claude Code 中的助理解析已保存 SOP / WorkflowDefinition 后形成的一次运行事实，不等于 Claude Session，也不是 Desktop 中可创建或推进的任务对象。它记录目标、步骤、委派、交接、审批、证据和验收；董事长助理通常在终端创建公司级运行，主管与获授权专业 Agent 可以在委派范围内创建受限子运行。

### 6.9 PluginInstallation

Bandi Plugin 的安装事实，至少记录：

- 安装状态、版本和作用域；
- Skill、董事长助理 Agent、MCP、Hooks、settings 的完整性；
- 与 Local Service 的兼容性；
- 标准命令是否可用；
- 可选短别名是否单独安装；
- 最近检查和错误。

`PluginInstallation` 是 L0 配置事实，不证明某个会话已经调用 Plugin。

### 6.10 AttachmentContext

快速接入当前会话时解析出的有限上下文：

```text
entry_surface
+ current_cwd
+ matched Workspace / Company
+ chairman_assistant AgentPackage
+ available Workflow 摘要
+ OrchestrationPolicy 摘要
+ 权限过滤后的有限 MemoryContext
+ 当前会话限制
+ 证据等级
= AttachmentContext
```

它不是完整 RuntimeProjection，也不意味着新的 Claude 进程或 AgentExecution 已启动。有限 MemoryContext 只说明本次接入获准读取的记忆摘要，不保证当前会话已完整加载所有记忆层。

### 6.11 RuntimeProjection

完整启动或委派解析时生成的动态不可变快照：

```text
Bandi Plugin 安装基线
+ 董事长助理 Plugin Agent 投影
+ AgentPackage / WorkspaceBinding
+ 权限过滤、版本化的 MemoryProjection
+ 允许的 Skill / MCP
+ Hooks / settings 覆盖
+ Workflow 与策略上下文
+ 初始上下文
+ 配置版本、哈希和依赖
= RuntimeProjection
```

投影可审计、可重建，不反向成为长期配置或记忆主源；多个执行可以引用同一仍有效的不可变快照。

MemoryProjection 按以下来源从长期、共享到当前身份和任务逐步收窄：

```text
Agent 长期记忆
→ Workspace 公共记忆
→ 当前 Department × Workspace 部门项目记忆（按职责和权限）
→ Agent × Workspace 项目记忆
→ 当前 Workflow / Handoff / 临时上下文
```

对董事长助理而言，前两类 Agent 记忆分别承载长期总记忆和当前 Workspace 的协调/汇报摘要；项目管理事实仍由负责项目的部门主管维护在 Department × Workspace 中。

这不是普通配置的“后者静默覆盖前者”。每层必须保留来源、作用域、所有者、revision、hash、纳入原因和权限裁决；发生冲突时保留来源并显式标记。

### 6.12 LaunchContext

`launch_new` 的完整启动输入，包含 Company、Workspace、董事长助理、RuntimeProjection、入口、cwd、安全参数、命令预览和确认记录。它不等于已经运行的 Claude Session。

### 6.13 AgentExecution

一次接入、启动或工作流委派的执行上下文记录，至少包含：

```text
entry_mode / entry_surface
+ AttachmentContext 或 LaunchContext 引用
+ AgentPackage / WorkspaceBinding
+ RuntimeProjection（attach_current 可空）
+ WorkflowRun / WorkflowStepRun（可空）
+ 父执行与委派深度
+ Session 关联状态
+ EvidenceLevel
+ 可证明的入口或执行事件
```

快速接入记录不得伪装成新进程；完整启动记录也不能仅凭终端请求进入“运行中”。

### 6.14 Evidence、Approval 与 Handoff

- `Evidence`：配置、MCP、Hook、Connector、用户操作或交付物产生的证据；
- `Approval`：主管、董事长助理或董事长的明确审批事实；
- `Handoff`：目标、上下文、交付物、阻塞和下一责任人的结构化交接。

### 6.15 关系图

```text
董事长 1 ── * Company（现实公司数字孪生）
                    ├── 1 董事长助理 AgentPackage
                    ├── * Department ── * AgentPackage
                    ├── * Workspace
                    └── * WorkflowDefinition

AgentPackage 1 ── * WorkspaceBinding * ── 1 Workspace
      ├── * SourceAsset
      ├── * MemorySpace（Agent 长期 / Agent × Workspace）
      └── * AgentExecution ── 0..1 WorkflowRun

Workspace 1 ── 1 公共 MemorySpace
Workspace * ── * Department ── 1 部门项目 MemorySpace
MemorySpace 1 ── * MemoryCandidate ── 0..1 MemoryRevision

Bandi PluginInstallation 1 ── * RuntimeProjection
EntrySurface ── EntryMode ── AttachmentContext | LaunchContext
```

### 6.16 不得混用的概念

| 概念 | 不是 |
| --- | --- |
| 董事长 | Agent 或自动化角色 |
| Bandi Desktop | Claude Runtime、另一套 Claude Code、任务管理台、调度台、聊天台、汇报台或验收台 |
| SOP / WorkflowDefinition | Desktop 执行器、任务实例或无需确认即可自动推进的流程 |
| Company | 任意虚拟公司、Workspace 或 Git 仓库 |
| AgentPackage | Plugin Agent、单个文件、Session 或执行记录 |
| Bandi Plugin | AgentPackage、RuntimeProjection 或组织数据库 |
| 第三方 Plugin SourceAsset | Bandi 自有 Plugin 安装状态 |
| Skill | 确定性唤醒器或组织事实数据库 |
| MCP | Workflow、终端控制器或组织策略 |
| Hooks | 绝对安全边界或可靠 Runtime Connector |
| `bandi` | Claude Code Slash Command |
| `/bandi:bandi` | 系统 Shell 命令 |
| `/bandi` | Plugin 默认必然提供的入口 |
| Semantic Trigger | 确定性唤醒词 |
| AttachmentContext | 完整 RuntimeProjection、新 Session 或已完整加载的记忆 |
| LaunchContext | 已关联、正在运行的 Session |
| Agent 长期记忆 | Agent Workspace 项目记忆 |
| 董事长助理 Agent × Workspace 记忆 | 负责部门的完整项目管理台账 |
| 部门项目记忆 | 部门主管个人记忆 |
| MemorySpace | 固定物理目录或单纯 Markdown 文件 |
| MemoryCandidate | 已批准事实或已写入版本 |
| MemoryRevision | Runtime 已加载事实 |
| RuntimeProjection | Plugin 安装目录、长期配置源或长期记忆主源 |

| 终端打开请求 | Session 已关联 |

## 7. 信息架构

### 7.1 首次进入

```text
打开 Bandi Desktop
→ 检查 Local Service 与 Claude Code 集成
→ 选择已有目录 / 创建目录
→ 扫描 Git 与外部 Claude 配置
→ 创建 Workspace
→ 关联或创建现实 Company 数字孪生
→ 进入 Workspace 概览
```

扫描只创建 SourceAsset 索引和映射建议，不自动创建正式公司或长期 Agent。

### 7.2 一级导航

```text
首页
Agents
组织
Workspaces
资产
设置
```

## 8. 关键用户流程

### 8.1 创建公司数字孪生

```text
创建 Company
→ 填写现实公司身份、使命和边界
→ 创建董事长助理 AgentPackage
→ 建立部门和岗位
→ 创建员工 AgentPackage 或显式导入 SourceAsset
→ 定义 Workflow 与 OrchestrationPolicy
→ 关联 Workspace
→ 检查 Claude Code 集成
```

### 8.2 快速接入当前会话

```text
在 Claude Code 中调用 /bandi:bandi
→ 选择“快速接入当前会话”
→ Plugin 读取当前 cwd 和可证明上下文
→ Local Service 返回候选 Workspace / Company
→ 用户处理歧义并确认董事长助理
→ 展示 AttachmentContext、限制和 EvidenceLevel
→ 当前会话获得 Bandi 工作流能力
→ 写入接入记录，不创建新 Session
```

可选 `/bandi` 只做同一流程的薄转发；自然语言触发必须先完成同样的识别、补参和确认。

### 8.3 完整启动新会话

```text
从 Desktop、bandi CLI 或 /bandi:bandi 选择完整启动
→ 选择 Company 与 Workspace
→ 校验 Bandi Plugin 安装和版本
→ 解析董事长助理及可委派组织
→ 选择可用 Workflow 和策略范围
→ 编译并校验 RuntimeProjection
→ 展示新会话、cwd、投影、命令和证据边界
→ 董事长确认
→ 创建 LaunchContext 与 AgentExecution 启动记录
→ 请求新建董事长助理会话
```

### 8.4 Claude Code 中的分层协作

以下过程全部发生在用户自己的 Claude Code CLI 中，Desktop 不提供对应的任务交互页面：

```text
董事长向助理下达目标
→ 助理依据组织、职责、Skills、Workspace、权限和 SOP 判断必要部门
→ 低风险事项说明分配后直接推进；多部门复杂事项先提交简明协作方案确认
→ 助理向有权限的部门主管委派部门目标
→ 主管依据同类配置选择本部门必要员工
→ 专业与执行 Agent 在授权范围内完成工作
→ 阻塞、审批与高风险动作在终端按规则升级或确认
→ 主管汇总部门结果，助理汇总跨部门结果并向董事长汇报
→ 董事长最终验收
```

临时计划、分工、Todo、执行日志和过程状态默认留在当前终端。只有协作方式具有复用价值且董事长明确同意时，助理才将责任部门/岗位、输入输出、依赖、审批和升级条件整理为正式 SOP 配置。

### 8.5 查看并修改 AgentPackage

```text
从组织或 Agent 列表选择员工
→ 在同一详情中查看职责、Instructions、Skills、Memory、Rules、MCP、权限、Agent × Workspace 专属配置和 SOP
→ 修改普通配置
→ 校验格式、路径和依赖
→ 若无特殊风险，直接备份并原子写入真实配置文件
→ 保存成功后提示回 Claude Code 使用
```

条件分支：

- 用户主动要求时展示保存前 Diff；
- 检测到外部并发修改时展示三方 Diff，并仅对真实冲突要求处理；
- 修改共享 Skill、Rule、MCP、SOP 等资产时展示受影响的 Agent、Workspace 或组织单元；
- 扩大权限或开放危险能力时展示风险并要求明确确认；
- 修改 Memory 时不得走普通直写，转入 MemoryCandidate 审核流程；
- 保存后只标记确实依赖该配置的 RuntimeProjection 需要重新编译，不引入统一“发布”阶段。

### 8.6 审核并写回记忆候选

```text
运行或人工编辑产生值得保留的信息
→ 创建 MemoryCandidate，并指定唯一目标 MemorySpace
→ 校验提议权限、来源、敏感性、重复和冲突
→ 归口人整理并进入 review_policy 指定的审核
→ 提议者与审核人相同时向上级升级
→ 批准 / 驳回 / 要求修改 / 改投其他空间
→ 改投后重新校验权限和审核路径
→ 展示目标版本与写回 Diff
→ 再校验权限、基线 revision 和 content hash
→ 备份并原子写入
→ 生成 MemoryRevision、哈希和审计记录
→ 标记相关 RuntimeProjection 需重新编译
```

Agent、Plugin、MCP 和 Hooks 都不能直接修改正式长期记忆。一个候选只有一个主要目标空间；审核通过、文件写入成功、投影重编译和 Runtime 已加载必须分别表达。

## 9. 状态与证据

状态与证据是配置管理和接入流程的辅助信息，不构成一级“运行”产品。Runtime Connector、AgentExecution 与 L0/L1/L2 信息从 Workspace、Agent、Workflow、接入入口或 Claude Code 集成状态按需进入。聊天、工具调用、Todo、日志、Agent View 等执行中间状态由 Claude Code CLI 展示和保留，Desktop 不复制、不聚合、不伪造。

### 9.1 证据等级

| 等级 | 含义 | 可展示 |
| --- | --- | --- |
| L0 配置事实 | 安装、文件、设置或投影存在 | 已安装、已配置、快照已生成 |
| L1 有限事件证据 | MCP 或 Hook 产生可关联事件 | 已调用、已提交结果、有限 Session 候选关联 |
| L2 可靠 Runtime 证据 | Connector 提供稳定 Session、事件顺序、去重和恢复 | Session 已关联、执行中、步骤完成、Usage、停止/恢复 |

L1 不能自动升级为 L2。Hook 超时或事件缺失时，不能把未阻止解释为已批准。

### 9.2 允许状态

```text
Plugin 已安装 / 版本不兼容 / 组件缺失
Local Service 可用 / 不可用
标准命令可用
短别名未安装 / 已安装 / 有冲突
MCP 已配置 / 可连接 / 已调用
Hooks 已配置 / 最近触发 / 证据不完整
AttachmentContext 已确认
RuntimeProjection 已生成
LaunchContext 已创建
命令已复制
已请求打开终端
用户标记已结束
```

### 9.3 需要可靠证据的状态

```text
Session 已关联
Agent 正在执行
当前步骤
任务完成或失败
精确 Token / Usage
可停止或恢复
```

界面必须同时显示证据来源、时间、等级和限制，不能用一个绿色“已连接”混合 Plugin、MCP、Local Service 与 Session 状态。

## 10. 视觉与布局基线

1. 公司数字孪生关系和工作区上下文优先，不以统计卡片墙为主视觉；
2. 三段式桌面 Shell，树、表格、关系行和证据时间线优先；
3. 使用紧凑但可读的桌面密度；
4. 路径、命令、版本和哈希使用等宽字体；
5. 状态由文字、图标和颜色共同表达；
6. 默认暗色，语义 Token 支持未来亮色；
7. `>=1200px` 展开三栏，`960–1199px` 缩窄或折叠上下文栏，`<960px` 转为 Sheet；
8. Tauri 最小目标窗口 `960×640` 仍能完成核心流程；
9. 宽表格和 Diff 在自身容器滚动，页面整体不横向滚动；
10. 所有假数据、假成功和无证据“运行中”均禁止。

## 11. 首版范围

### 11.1 必须实现

- Workspace 选择、扫描、绑定和最近使用；Workspace 可暂不关联但最多归属一个 Company，并管理该公司内唯一主责部门、默认项目负责人和多个协作部门；
- 多现实 Company、树形 Department、Role、部门主管、成员、Agent 唯一主属部门和带范围的跨部门服务授权管理；
- Agent 启用、停用与归档生命周期，以及永久删除的独立高风险确认；
- Company 内共享资产、跨 Company 单独注册与授权、引用保护和 Agent 局部定制；
- 董事长—助理—主管—专业/执行 Agent 的组织关系；
- 目录化 AgentPackage 与 WorkspaceBinding；
- SourceAsset 扫描、引用和显式导入；
- 分层 SOP / WorkflowDefinition、OrchestrationPolicy 和静态循环检查；SOP 仅作为供 Claude Code 助理解析的配置定义；
- Desktop 只管理组织关系和配置资产并提供打开 Claude Code 的衔接，不提供任何单次任务操作界面；
- Claude Code 中按“助理选必要部门并委派主管、主管按职责/Skills/Workspace/权限选员工”完成分层委派，并支持复杂方案确认、高风险动作再确认和逐级汇报；
- 普通配置直接保存到真实文件，支持事务恢复和原子写入；按需 Diff、共享资产影响分析、真实并发冲突保护和高风险权限扩大确认；
- 设置中提供独立“备份与恢复”入口，首版支持本地手动/自动快照、历史查看和按 Company、Agent 或文件恢复；恢复前自动保存当前状态；
- Bandi Desktop、Rust Local Service 和 `bandi` CLI；
- Bandi Plugin：Skill、董事长助理 Agent、Bandi MCP、最小 Hooks 和 settings；
- PluginInstallation 和 Claude Code 集成状态；
- `/bandi:bandi` 标准入口；
- `attach_current` 与 `launch_new` 双模式；
- AttachmentContext、RuntimeProjection 和 LaunchContext；
- 四类 MemorySpace、独立逻辑文件载体和 owner/steward/reviewer 治理；
- MemoryCandidate、人工审核、自审升级、Diff、备份、原子写回与 MemoryRevision；
- 完整启动的 MemoryProjection 和快速接入的有限 MemoryContext；
- WorkflowRun、AgentExecution 和 L0/L1 证据记录下沉到相关对象与集成状态，不设一级运行模块；
- macOS 首发所需的受限系统操作。

### 11.2 可选或渐进

- `/bandi` standalone 薄别名；
- 自然语言语义触发候选说明与低风险引导；
- 更多终端适配；
- L1 Hook/MCP 事件的有限关联增强；
- GitHub 或自定义 Git 远程备份：Bandi 自动创建的仓库必须为 Private，不提供公开选项；连接已有远端时验证私有状态，明确公开时拒绝备份。

### 11.3 后续能力

只有可靠 Runtime Connector 存在后，才增加：

- 稳定 Session 关联和真实运行状态；
- 事件相关性、顺序、去重、重连和失败恢复；
- 精确 Usage、模型和 Skill/MCP 调用统计；
- 可靠停止、恢复和自动推进；
- 自动测试、独立验收和交付报告；
- 从会话自动提炼记忆候选；
- 语义检索、向量索引、摘要压缩和自动遗忘/归档；
- 员工成长、记忆质量和能力缺口闭环；
- Windows、远程 Web 和多用户协作。

### 11.4 明确不做

- 内嵌终端；
- 后台隐藏托管 Claude Code；
- 面向大型集团的无限层级组织、人事、考勤或行政管理系统；
- 自动创建正式公司和长期 Agent；
- 自动安装未知 Skill/MCP；
- 静默覆盖本地配置；
- 让普通主管或员工成为董事长的默认主会话入口；
- 在 L0/L1 证据下伪装 L2 运行能力；
- 一级“运行”模块；
- 镜像 Claude Code 聊天、工具调用、Todo、日志和 Agent View；
- Desktop 任务创建、运行、当次部门/员工选择、人员调度、方案或流程确认、推进、聊天、阻塞/审批、汇报和验收界面；
- Desktop SOP 执行器，或未经用户同意将临时协作自动保存为 SOP。

## 12. 首版验收标准

1. 用户能理解 Bandi 映射现实公司，而不是生成任意虚拟公司；
2. 用户能管理多公司、部门、岗位、助理、主管和员工；
3. 用户能区分 Desktop、Local Service、Plugin、CLI 和 Claude Code；
4. 所有入口读取同一事实与策略，不形成多主；
5. 用户能区分 Bandi Plugin、Plugin Agent、AgentPackage、SourceAsset 和 RuntimeProjection；
6. `/bandi:bandi` 明确为标准入口，`/bandi` 明确为可选薄别名；
7. 自然语言只表达为语义触发候选；
8. 快速接入不创建新 Session，也不声称完整重建启动配置；
9. 完整启动编译完整投影并创建新的董事长助理会话上下文；
10. Plugin、MCP、Hooks、Local Service 和 Session 状态分别展示；
11. 首版 MCP/Hooks 不被描述为可靠 Runtime Connector；
12. 主管和获授权专业 Agent 可按策略编排；
13. WorkflowRun 不等于 Claude Session；
14. 用户能从员工进入完整配置视图，查看职责、Instructions、Skills、Memory、Rules、MCP、权限、Agent × Workspace 专属配置和 SOP；
15. 普通配置无需草稿、审批或发布即可安全保存到真实配置文件，并具有基线检查、事务恢复和原子写入；
16. Agent 自有、全局默认、显式共享引用、全局强制和 Workspace 专属关系按需解释，Diff 只由用户主动查看或外部并发修改触发，影响只分析共享资产本体，冲突只处理真实冲突；
17. 扩大权限或开放危险能力必须明确确认；
18. 用户能区分四类 MemorySpace，并理解助理长期总记忆、助理 Workspace 协调摘要与部门项目管理记忆的职责边界；
19. Workspace 可以暂不关联组织，但首版最多归属一个 Company；主责部门、项目负责人和协作部门必须来自该 Company，不允许同时加载多家公司的组织、默认配置和安全边界；
20. 每个已关联组织的 Workspace 只有一个主责部门和默认项目负责人，但可有多个协作部门；主责主管负责总体结果、公共记忆归口和跨部门汇总，协作主管只负责本部门交付与部门项目记忆；
21. 每个 Agent 最多一个主属部门，可有多个带能力与 Workspace 边界的服务授权；停用或归档保留档案且不接受新委派，永久删除独立确认；
22. 共享资产默认 Company 内可用，跨 Company 必须单独注册和授权；组织身份不自动授予权限，Agent 不得自行扩大权限；
23. AgentPackage 使用稳定 `agent-id` 目录且不随部门移动，根级长期配置与 `workspaces/<workspace-id>/` 专属配置清晰分离；
24. 每个 Agent × Workspace 的项目记忆独立隔离，公共记忆和部门记忆不归个人 AgentPackage；
25. 所有正式 MemorySpace 变化只能先提交 MemoryCandidate，提议者不能自审，成功写入后必须生成 MemoryRevision；
26. MemoryProjection 保留来源、版本、哈希、纳入原因和权限裁决，冲突不静默覆盖；
27. 用户能区分候选批准、文件写入、投影重编译和 Runtime 加载；
28. 一级导航不包含“运行”，Runtime Connector、AgentExecution 和 L0/L1/L2 证据可从相关对象按需查看；
29. 董事长下达目标、助理判断部门、复杂方案确认、跨部门委派、主管选员工、执行协作、阻塞/审批、逐级汇报和最终验收全部在用户自己的 Claude Code CLI 完成；
30. Desktop 只管理 Company、Department、Agent 组织关系及 Instructions、Skills、Memory、Rules、MCP、权限、Agent × Workspace 专属配置、SOP 等配置资产，并提供打开 Claude Code 的衔接；
31. Desktop 不提供任务创建、运行、当次部门/员工选择、调度、流程确认、推进、聊天、汇报或验收界面，用户无需为每次任务在客户端选人；
32. SOP 明确是供 Claude Code 助理解析的配置定义，不是 Desktop 执行器；临时协作默认留终端，只有具备复用价值且用户同意时才保存为 SOP；
33. 助理按必要部门委派主管，主管按职责、Skills、Workspace 和权限选员工；低风险直接说明，多部门复杂事项先确认简明方案，高风险动作执行前再次确认；
34. Desktop 不镜像聊天、工具调用、Todo、日志和 Agent View，执行中间状态留在 Claude Code CLI；
35. MemoryCandidate 先审后写、自审升级、MemoryRevision 及状态分离契约保持不变；
36. 用户可从独立“备份与恢复”入口执行本地快照、查看历史和按范围恢复，恢复前系统先保存当前状态；
37. 远程 Git 备份仅允许私有仓库；凭据、Token、钥匙串内容、会话与执行日志永不进入备份，正式 MemorySpace 是否进入远程备份需用户单独确认。
38. 960×640 下可完成公司查看、Agent 完整配置查看与保存、记忆审核、模式选择和完整启动。
