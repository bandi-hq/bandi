> 文档版本：v1.8-draft

> 状态：配置事实闭环与桌面桥接技术收敛稿

## 1. 文档目标

本文定义 Bandi 首版的技术施工边界：

- Bandi Desktop 管理长期 Agent 配置资产与可追溯版本；现实公司组织关系只作为配置建模方式；
- Bandi Desktop、`bandi` CLI 和 Bandi Plugin 共用 Rust Local Service；
- Local Service 管理真实配置资产的发现、独立 Agent 配置组合、显式共享引用、Agent × Workspace 专属配置和受限写回；
- Bandi 管理组织、职责、Skills、WorkspaceBinding、权限、SOP 等配置资产，用户仍在自己的 Claude Code CLI 中完成全部任务交互与分层委派；
- 董事长可直接联系任意 `active` Agent；董事长助理是复杂、多部门事项的默认协调入口，助理按配置选择部门并委派主管，主管再按配置选择员工；直接联系不扩大目标 Agent 的权限、WorkspaceBinding、服务授权或委派范围；
- Desktop 和 Local API 不创建任务、不调度人员、不推进执行，也不提供聊天、汇报、验收或运行控制；
- Plugin/MCP 是 Claude Code 中读取配置事实、校验委派边界和提交必要持久化提议的适配层，不让 Desktop 或 Local Service 成为执行器；
- SOP/WorkflowDefinition 是配置资产，由 Claude Code 中的董事长助理解释执行；临时协作留在终端，只有用户同意才保存为正式 SOP；
- 普通配置保存是短事务，不引入通用草稿发布系统；
- 普通配置成功写后生成 ConfigRevision，支持版本比较和恢复；Claude Code 执行期配置投影仅是 CLI / Plugin 按需重建的内部产物；
- 四类 MemorySpace、MemoryCandidate 审核和版本写回继续构成独立的记忆治理契约；
- 终端内的计划、委派、工具调用、执行进度、汇报、验收和会话状态不采集、不镜像到 Bandi。

## 2. 技术原则

1. **本地优先**：源码、组织、配置、凭据引用和 Workspace 默认留在用户设备。
2. **三端一中枢**：Desktop、系统 CLI 和 Plugin 共享 Local Service，不分别保存公司事实或配置副本。
3. **真实资产优先**：外部配置文件保持自身身份；数据库只保存索引、绑定、策略、版本与审计，不制造第二份配置主源。
4. **配置关系可解释**：Local Service 区分 Agent 自有、全局普通默认、显式共享引用、全局强制边界和 Agent × Workspace 专属配置，而非返回来源不明的合并黑盒。
5. **普通保存短事务**：修改、校验和写回直接围绕当前文件基线完成，不引入通用发布审批状态机。
6. **按需展示 Diff**：普通保存不强制展示 Diff；用户主动查看或基线变化时才展示。
7. **冲突语义收敛**：多个终端、编辑器或宿主客户端只在真实配置文件发生并发修改时进入“编辑基线 → 保存前复核 → `BaselineChanged` → 三方 Diff → 解决后重新保存”；Bandi 不建立终端或 Session 状态，也不在无证据时推断修改来源。
8. **共享影响有边界**：只有同一真实资产被多个 Workspace、Agent 或绑定引用时，才提示共享影响。
9. **长期权限扩大额外确认**：永久扩大 AgentPackage 工具、目录、网络、命令、MCP、委派或数据范围时确认；某次工具调用的一次性授权只在 Claude Code。
10. **受限系统能力**：React UI 无通用 Shell 和任意文件系统权限，写回只能通过类型化 Local Service 命令。
11. **文件安全**：所有写回执行路径授权、符号链接边界检查、基线复核、原子替换和写后验证。
12. **记忆独立治理**：正式记忆变化始终由 MemoryCandidate 先审后写，不复用普通配置保存流程。
13. **投影可重建**：Claude Code 执行期配置投影由 CLI / Plugin 按需从真实配置、绑定、策略和记忆投影生成，不进入 SQLite 长期事实、Desktop 页面状态或发布流程，也不表示 Session 已加载。
14. **执行边界清晰**：用户自己的 Claude Code CLI 是唯一任务交互与执行现场；Desktop、Local Service 和 Local API 均不是任务执行器。
15. **董事长可直接联系、助理默认协调**：董事长可在 CLI 中直接联系任意 `active` Agent；复杂、多部门事项默认由助理选择部门并委派主管，主管选择员工。直接联系只改变沟通路径，不改变任何长期权限或安全边界。
16. **配置约束委派**：每次选择必须同时满足部门职责、岗位与 Skills、WorkspaceBinding、MCP 与权限、委派关系及 SOP 适用范围；无合适 Agent 时报告配置缺口，不静默越权或降级绕过。
17. **临时协作不沉淀**：Claude Code 中的临时计划、分工与协作上下文默认留在终端；只有用户明确同意，才形成正式 SOP/WorkflowDefinition 配置变更。
18. **跨平台准备**：macOS 首发，领域契约避免依赖 Mac 专属语义。
19. **安装事实与引用分离**：Skill 的来源、安装版本和生命周期属于资产事实；Agent 与 WorkspaceBinding 只保存显式引用，安装、更新、回滚或卸载不得隐式改写引用集合。
20. **阶段能力不伪装**：当前 React Web Mock 的 onboarding、目录树、Skill 操作、普通配置 Revision 和快照只修改页面内存；预置事实标记为 `demo-fixture`，本次操作标记为 `memory-only`；真实目录、安装、保存、备份和 Claude Code 探测必须等待类型化系统能力接入。
21. **规范关系单源**：当前前端以 `agent.workspaceBindings` 作为 Agent ↔ Workspace 唯一规范关系，Workspace 侧派生列表不得成为第二写入源。
22. **桌面桥能力显式化**：当前 Tauri 壳的应用自定义 command 全部通过 `AppManifest::commands` 纳入 ACL，仅向 `main` 窗口逐项授权；系统选择器只取得用户明确选择的目标，Rust command 仍须独立执行路径规范化和领域校验。不得把 capability、用户选择和后端信任混为一层，也不得扩张为通用文件系统、Shell、进程、剪贴板或全局快捷键能力。
23. **能力以证据为准**：`demo-fixture`、`memory-only`、原生 command 成功回执、持久化注册记录和重新读取验证是不同证据等级；UI 不得从目录项、配置值、文件存在或按钮可见性推断安装、连接、保存、启动、Plugin 加载或 Session 状态。
24. **注册表拒绝任意执行**：规划中的 Workspace Registry 以稳定 Workspace ID 绑定经验证的 canonical path；AI Adapter Registry 以稳定 adapter ID 绑定受支持客户端的固定能力和后端实现。通用 `executable`、`argv` 和 Shell 模板废弃，不作为产品或跨进程契约。

## 3. 产品形态与技术栈

### 3.1 发布形态

```text
第一阶段：macOS Bandi Desktop + Rust Local Service + bandi CLI + Bandi Plugin
第二阶段：Windows 客户端及平台适配
第三阶段：按真实需求扩展远程连接或宿主集成
```

首版所有任务交互、分层委派、执行推进、汇报与验收都发生在用户自己的 Claude Code CLI。Desktop 与 Local API 不提供任务创建、人员调度、聊天、汇报、验收、停止、恢复或其他运行控制 UI/API，也不以持续观察 Claude Code 会话为前提。

### 3.2 技术栈

| 层 | 技术 | 职责 |
| --- | --- | --- |
| 桌面壳 | Tauri 2 | 窗口、系统权限、目录选择、文件和终端唤起 |
| 前端 | React + TypeScript + Vite | 配置浏览、编辑、来源解释、保存反馈与类型化 ViewModel |
| UI | Tailwind CSS v4 + shadcn/ui + Radix + Lucide | 语义 Token、可访问组件与图标 |
| 本地核心 | Rust Local Service（规划） | 本机领域服务；配置发现、解析、RestrictedConfigWriter、Workspace Registry、AI Adapter Registry、版本与审计的唯一受控边界 |
| 数据库 | SQLite/WAL（规划） | WAL 模式下保存组织、注册表、绑定、策略、资产索引、版本、记忆治理和审计；不保存可替代真实配置文件的日常主副本 |
| 本地通信 | Tauri Command / localhost 类型化 API | 当前 Desktop 的配置管理 command 经 manifest 登记并由 `main` capability 逐项授权；未来 Desktop、CLI、Plugin 共用 Local Service 的配置查询、校验和受限持久化接口，不含任务运行 API |
| Claude 集成 | Bandi Plugin | Claude Code 中的董事长助理、配置事实读取、委派边界校验、SOP 解释与必要持久化提议 |
| 系统入口 | `bandi` CLI | doctor、status、配置检查和 Claude Code 入口 |
| 凭据 | 系统钥匙串 | MCP 和外部服务的安全引用 |
| UI 更新 | Tauri Event 或请求刷新 | 文件扫描、保存、备份和恢复等配置操作进度；不发布 Session/执行进度 |

Node Sidecar 与 Claude Agent SDK 不属于首版必选路径。若未来增加宿主集成，仍须服从 Rust 的配置、策略和业务事实边界。

## 4. 总体架构：三端一中枢

```text
┌────────────────────┐
│ Bandi Desktop      │ React UI + Tauri
└─────────┬──────────┘
          │ 类型化查询 / 业务命令
┌─────────▼──────────────────────────────────────┐
│ Rust Local Service                            │
│                                               │
│ Workspace / Organization                     │
│ Config Asset Discovery                       │
│ Effective Config Resolver                    │
│ Workspace Override Service                   │
│ Restricted Config Writer                     │
│ AgentPackage / SOP / Policy                  │
│ Delegation Constraint Validator              │
│ Memory Service / Projection Compiler         │
│ Config Revision / Audit / Local Ops           │
└─────────┬──────────────────────────────────────┘
          │
          ├── SQLite：索引、绑定、策略、版本与审计
          ├── AgentPackage / SourceAsset：真实配置资产
          ├── Workspace / Git / Claude 配置根
          ├── Keychain
          └── 操作系统终端：受限唤起，不接管会话

┌────────────────────┐        ┌────────────────────────────┐
│ bandi CLI          │        │ Bandi Claude Code Plugin   │
│ 系统 Shell         │        │ Skill · Agent · MCP · Hook │
└─────────┬──────────┘        └─────────────┬──────────────┘
          └──────────────► Local Service ◄──┘
                           配置事实 / 边界校验 / 持久化提议
                                      │
                           用户自己的 Claude Code CLI
               董事长 → 任意 active Agent
                    └→ 董事长助理 → 部门主管 → 员工 Agent
                  （直接沟通或默认协调、分层委派、执行、汇报与验收）
```

### 4.1 Rust Local Service 职责

Local Service 是规划中的本机领域服务。落地后，它是 SQLite/WAL 业务事实的唯一写入者，也是配置资产操作的唯一受控入口；当前最小 Tauri command 只是过渡期窄适配，不应被描述为完整 Local Service。Local Service 负责：

- 发现授权根内的 AgentPackage、Claude 配置和其他 SourceAsset；
- 识别资产类型、作用域、格式、物理路径、稳定身份、引用关系和当前哈希；
- 组合 Company / 全局基础配置、AgentPackage 自有配置、显式共享资产引用和 Agent 自有 WorkspaceBinding，计算可解释的有效配置；
- 管理全局普通默认、全局强制安全边界、共享资产显式引用和 Agent × Workspace 专属配置；
- 为编辑选择唯一真实写回目标，加载基线并验证修改；
- 在写入前复核当前基线、权限、路径、格式、互斥约束和共享引用；
- 通过同目录临时文件、刷盘和原子替换完成受限写回；
- 写后重新读取、解析并验证期望结果，更新资产索引和审计；
- 管理 Workspace、Company、树形 Department、Role、部门主管、成员、Agent 唯一主属部门和带范围的跨部门服务授权；
- 管理 Agent 的 active/inactive/archived 生命周期；停用或归档保留 AgentPackage、正式记忆与历史并排除新委派，永久删除使用独立高风险事务；
- 保证 Workspace 可暂不关联但最多归属一个 Company，并隔离不同 Company 的组织、默认配置与安全边界；
- 管理 Workspace 的唯一主责部门、默认项目负责人和多个同公司协作部门关系，并保证同一 Workspace 不存在多个主责方；
- 校验部门父子关系、循环、组织深度提示、主管归属、Workspace 项目责任关系和删除/移动前的成员迁移方案；
- 管理 AgentPackage 元数据、Skills、SOP/WorkflowDefinition 和 OrchestrationPolicy 等配置资产；
- 提供委派约束校验：部门职责、岗位与 Skills、WorkspaceBinding、MCP 与权限、组织委派关系、SOP 适用范围；
- 对无合适 Agent、配置缺失或约束不满足返回可解释诊断，不替 Claude Code 选择或调度人员；
- 管理 PluginInstallation、兼容性和组件完整性；
- 管理四类 MemorySpace、MemoryCandidate、审核、正式写回和 MemoryRevision；
- 按 CLI / Plugin 请求临时编译 Claude Code 执行期配置投影与 MemoryProjection；
- 为 Desktop 提供经验证的 cwd 目录交接与白名单终端能力证据；
- 提供受限的文件、目录、编辑器与终端操作；
- 记录 ConfigRevision、记忆审核、长期权限扩大和高风险配置操作审计。

Local Service 不负责：

- 替用户审批经营决策；
- 创建任务、选择或调度人员、推进执行、组织聊天、收集汇报、执行验收或控制运行；
- 直接执行 Claude 推理，或承载董事长、助理、主管、员工之间的任务交互；
- 采集或镜像终端中的计划、委派、提示词、工具调用、中间结果、进度、汇报、验收、用量和会话生命周期；
- 根据终端窗口、MCP 连接或 Hook 事件推断“执行中”“已完成”等状态；
- 允许 Plugin 或 UI 绕过策略直接写 SQLite 或配置文件；
- 允许任何 Agent、MCP 或 Hook 绕过 Memory Service 直接修改正式长期记忆；
- 把 RuntimeProjection 当成日常配置编辑或持久化主源。

### 4.2 客户端边界

React UI 不直接读写任意文件、拼接 Shell、读取凭据或写 SQLite。Tauri 只暴露配置资产查询、有效配置解析、受限保存、版本比较/恢复、委派约束校验、记忆审核和 cwd 目录交接等类型化命令；交接不接受或回传 executable、argv、Shell、env、stdin 或脚本，也不暴露任务创建、人员调度、执行推进、聊天、汇报、验收或运行控制命令。

受管 AgentPackage 的头像是该边界内的类型化配置资产：固定文件名 `avatar.png`，仅由可选 `avatarPath` 引用。创建使用同父目录 staging 后提交；身份与头像变更通过单一命令执行 baseline 复核、原子 manifest 写入和失败回滚。PNG 字节不进入 YAML、ConfigRevision、前端持久状态或 localStorage；前端只持有选择阶段的 `File` 与显示阶段的可回收 Object URL。Desktop 启动只读取后端返回的 canonical 受管 Agent，不由 React 扫描目录。

当前仓库中的 React Web Mock 进一步收紧为纯页面内存演示：onboarding 只记录 `active/completed`，业务状态刷新后恢复初始 fixture，不写 `localStorage`、文件、Tauri、SQLite 或后端；仅严格白名单、版本化的本机 `UiPreferences` 可使用单一 `bandi-ui-preferences-v1` key，不得序列化整个 `State`、`SettingsState` 或业务对象；旧主题与主菜单 key 只作为一次性迁移输入。`UiPreferences` 包含主题偏好、受控强调色、界面/等宽字体、字号、密度、背景样式、主菜单布局和本机工作台辅助名称，并逐字段运行时校验；有效主题由 `system | light | dark` 偏好与 `prefers-color-scheme` 派生。Logo 与背景图由 Tauri 固定 `logo` / `background` 槽位保存到应用数据目录，Rust 校验 PNG/JPEG 签名和大小并原子替换，不暴露任意路径或宽泛文件系统权限。上述偏好及图片不进入 SQLite、配置文件、ConfigRevision、BackupSnapshot、Git 或 RuntimeProjection。`state.uiPreferences` 是唯一已保存 canonical；个性化编辑草稿通过 App Context 中不持久化的 transient 覆盖层生成 `effectiveUiPreferences`，实时驱动根节点和真实 Shell，取消、放弃离开或未保存卸载时清空覆盖并恢复 canonical。DOM 应用与 `localStorage` 持久化 effect 分离，只有 canonical 更新才写入 `bandi-ui-preferences-v1`；临时 Logo/背景 Object URL 仅存在于运行时，不进入 reducer、持久化、版本或备份。保存时先提交不再引用废弃图片的逻辑偏好，再对固定槽位执行幂等清理。该流程不承诺 Logo、背景和 localStorage 之间的跨资源事务，单槽位图片导入仍由 Rust 临时文件与原子替换保证。Agent 上下文栏布局由 `preference × matchMedia('(min-width: 1280px)') × matchMedia('(min-width: 960px)') × hasRecentAgents → effectiveLayout` 派生：显式 `hidden` 优先于最近记录和视口，没有最近 Agent 时也隐藏；跟随窗口仅在 `>=1280px` 展开，固定展开在 `>=960px` 展开，紧凑显示始终使用 64px 栏；窄屏降级不改写已保存偏好。`recentAgentIds` 仍是最多 6 项的纯页面内存 MRU，移除与清空动作不进入 `UiPreferences`、Local Service DTO、配置版本或备份；当前路由 Agent 由 Shell 作为页面上下文临时置顶。设置统一为“工具与交接、终端、数据与恢复、外观”四个分类；无消费方的 Workspace 设置级默认和编辑器偏好被删除。Desktop 的工具方案由 SQLite 持久化，完整快照包含全局 revision、当前方案、内置工具目录、自定义工具和方案工具 ID；写操作携 expected revision 并以后端返回快照为事实来源。至少保留一个方案，删除当前方案时事务内选择确定性替代，被引用的自定义工具不得删除。工具方案不映射 Gateway、Provider、凭据、安装状态或真实工具配置，也不属于 Agent / Workspace 覆盖轴；纯 Web 演示仍只存在页面内存。统一 AI 编程工具入口仅按当前方案的 `clientIds` 呈现 0/1/多个工具状态，并通过静态、强类型 Adapter descriptor 将已验证的 Claude Code/Codex 目录交接与其他工具的“仅配置”入口分开；该前端能力判断不是本机安装探测。入口使用工具图标，不展示未注册的快捷键符号，也不新增默认工具、最近工具或快捷键设置；所有交接只走现有五字段 Desktop bridge，不增加 Shell 或通用进程入口。方案内容变更可形成页面内存中的演示 `ConfigRevision`，单纯切换当前方案不产生版本。`NetworkProxySettings` 独立记录跟随系统、不使用代理或手动代理的选择；当前不读取或应用系统代理，不注入环境变量或重启客户端。`recentAgentIds` 是最多 6 项的纯页面内存 MRU，可移除非当前项或清空其他记录，但不持久化。上述业务对象都不表示安装、探测、连接、启动、在线或 Session 状态，也不进入 Local Service DTO。Claude Code、Codex、OpenClaw 等是宿主工具入口；DeepSeek 等 Model / Provider 应留在实际宿主工具中。首次“选择目录”在 Desktop 中通过仅授权 `dialog:allow-open` 的 Tauri Dialog Plugin 取得单个目录路径，在 Web Mock 中仍由用户输入演示路径；两端第二步都只登记能力边界，不扫描、验证或改写目录，新 Workspace 初始为“未验证”。“演示扫描”“演示安装”“演示连接”“演示保存”和“演示快照”都不能被描述为真实系统结果。预置配置证据为 `demo-fixture`，当前页面操作为 `memory-only`。

当前 Tauri 壳并非 event/title-only：除文件/目录选择、菜单语义事件和窗口标题外，已注册 Workspace Registry、配置 discovery/load/save/revision/recovery/restore、WorkspaceBinding 创建、Organization/Workspace 领域读写、工具方案、AI 工具交接、固定 UI 图片槽位、Claude Agent 导入、受管 AgentPackage 和恢复出厂等窄 command。恢复出厂 preview 不接受路径，只返回逻辑目标；commit 绑定 requestId、previewRef、固定确认文字、有效期和目标指纹。固定目标先 rename 到可信父目录内 quarantine，任一步失败逆序回滚；全部成功后写 committed marker，并在下次启动只清理 marker 精确列出的 quarantine。所有相关写 command 与 reset commit 共用进程内 mutation lock，避免重置过程中重新创建数据。所有应用自定义 command 由 `build.rs` 的 `AppManifest::commands` 纳入 Tauri ACL，`capabilities/default.json` 仅绑定 `main` 窗口并逐项 `allow-*`，不使用通配符。该 ACL 只裁决窗口能否调用 command；系统选择器只证明用户明确选择了目标；Rust command 仍将前端路径视为不可信输入，独立执行 canonicalize、类型、symlink、目标范围、基线和内容校验。Organization/Workspace 事实保存在 `app_data_dir()/bandi.db`，SQLite 启用 foreign keys、WAL、`synchronous=NORMAL` 与 5 秒 busy timeout，并通过 `PRAGMA user_version` 执行版本化 migration；Company、Department、Role、Workspace 和 ServiceGrant 保存均在 Rust 领域事务中校验。公司内名称唯一、部门树无环、主管必须属于部门、Role 与 Workspace 组织关系不得跨公司、ServiceGrant 按 Agent 整体替换。Company 的 `departmentIds/workspaceIds` 在读取快照时由关系表派生，避免展示字段成为第二事实源。旧 `workspaces/<workspace-id>.json` Registry 仍作为兼容入口：数据库无记录时读取规范路径并幂等导入最小 Workspace；后续交接优先从 SQLite 重取 canonical cwd。Desktop 空数据库呈现真实空态，不使用 Web demo fixture 冒充已落库组织。Company、Department、Role、Workspace 和 ServiceGrant 保存成功后，React 必须使用 Rust 返回的 canonical DTO 即时同步当前状态；不能等待重启，也不能继续使用提交前草稿伪装后端结果。AgentPackage、旧 Workspace Registry 与 Organization SQLite 之间没有跨存储事务：Agent 创建、Workspace 登记和身份编辑一旦前置存储已成功、后续组织写入失败，页面必须明确显示部分成功并只重试未完成步骤；重启后分别依赖 AgentPackage discovery、Workspace Registry 和 Organization Snapshot 恢复真实事实，不宣称全局原子提交。`request_client_handoff` 只接受 `clientId / adapterId / workspaceId / terminalId / intent`，由强类型静态 Adapter Registry 校验组合并从 Workspace Registry 重取 canonical cwd；只有 Claude Code/Codex 的已验证 Adapter 会请求固定 `/usr/bin/open`，其余状态和错配组合不触发外部动作。这些能力仍不构成任意 fs、通用 Shell/process、Skill 安装器或备份后端。未来扩展工具能力必须逐项登记真实证据，不能从 Mock、命令存在或任意可执行文件反推。

`bandi` CLI 和 Plugin 调用同一 Local Service，不复制资产发现、覆盖解析、保存安全、Company 匹配、策略或投影逻辑。任务交互与分层委派只在用户自己的 Claude Code CLI 中进行：董事长可直接联系任意 `active` Agent；复杂、多部门事项默认由助理读取 Local Service 提供的组织、职责、Skills、WorkspaceBinding、权限和 SOP 配置后按需选择部门并委派主管，主管再在同一约束下选择员工。直接联系不绕过这些约束。Local Service 只返回事实与校验结论，不参与任务执行。

## 5. 配置资产模型

### 5.1 AgentPackage 目录投影

AgentPackage 的物理目录事实由 Local Service 发现并登记；React 不自行扫描目录。前端目录树只能由当前 Agent 已登记的 `AgentFile[]` 构建：

```text
AgentFile[]
→ 路径规范化与重复/非法路径过滤
→ buildAgentPackageTree()
→ ARIA tree
→ 选择 path
→ 结构化预览 / 只读源码 / ConfigRevision 历史
```

根级文件表达跨 Workspace 的长期配置，`workspaces/<workspace-id>/` 表达 Agent 自有的 WorkspaceBinding 文件。没有登记的路径不得以占位内容伪装为磁盘文件；外部只读 AgentPackage 没有可靠内容时不得生成虚假源码。AgentPackage 路由以配置领域、路径和 `preview|source` 模式构成稳定深链。

### 5.2 当前前端规范配置模型

当前 React Web Mock 使用以下模块建立页面内存中的单一配置闭环：

```text
agent-config-model.ts
  受控 AgentConfigPayload、规范路径、稳定序列化与运行时校验
        ↓
state.tsx / SAVE_AGENT_CONFIG
  原子更新 canonical Agent、对应 AgentFile 与 ConfigRevision
        ↓
config-revisions.ts
  owner/path 查询、内容去重、parent/restore 链和 evidence
        ↓
domain-selectors.ts
  Agent / Workspace 健康、dangling Binding、最近保存和历史
```

普通 Agent 配置只允许映射到：

```text
agent.yaml
instructions.md
config/context.yaml
config/skills.yaml
config/rules.yaml
config/mcp.yaml
config/permissions.yaml
config/sop.yaml
config/orchestration.yaml
config/hooks.yaml
config/commands.yaml
workspaces/<workspace-id>/config.yaml
```

所有 Bandi 自管结构化 YAML 顶层使用 `schemaVersion: 1`；`parserVersion` 只属于未来资产索引，不写入用户配置或参与 schema 比较。AgentPackage 兼容状态为 `current`、`legacy`、`future`、`unverified`：只有 current v1 可进入结构化保存；legacy/future 保持只读，unverified 不生成虚假源码或 revision。

`agent.yaml` revision 必须是完整 manifest 快照，包含稳定 ID、schema、生命周期和完整职责字段；`companyId / primaryDepartmentId / roleId` 必须全部为空（个人 Agent）或全部存在且作用域一致（组织 Agent），不得保存半组织状态。生命周期不得使用绕过 manifest 的局部 payload。`agent.workspaceBindings` 是 Agent ↔ Workspace 唯一规范关系。创建或编辑 Binding 时登记对应 `config.yaml`，不因普通配置保存创建 `memory.md`。`SAVE_AGENT_CONFIG` 在一次 reducer 转换中比较 canonical payload、应用受控变更、序列化内容、upsert AgentFile 并追加 memory-only ConfigRevision；相同内容不生成重复版本。恢复前必须以当前关系重验 owner/path/kind、schema 与稳定 ID、Role 作用域、资产和 Plugin 组件、参数、Workspace 编排收紧及权限边界；任一失败都保持 canonical state 和 revision 不变，成功则生成新版本并保留 `restoredFromRevisionId`。

这组模块只是当前前端 Mock 的行为实现，不取代未来 Local Service 的基线检查、原子文件写入与写后验证契约。

### 5.3 资产身份

Claude Code 发现规则由版本化 discovery profile 管理；profile 冻结已验证的位置、官方 scope、容器格式、fragment 解析器和写入策略，不能把某一版本的目录猜测散落在 UI 或 writer 中。

```ts
type ConfigAssetKind =
  | 'agent_package'
  | 'global_config'
  | 'shared_asset'
  | 'agent_workspace_binding'
  | 'claude_user_config'
  | 'claude_project_config'
  | 'plugin_config'
  | 'other_supported_source'

interface SourceContainer {
  id: string
  canonicalPath: string
  rootKind: 'workspace' | 'claude_user' | 'managed' | 'bandi' | 'authorized_external'
  format: 'json' | 'jsonc' | 'toml' | 'yaml' | 'markdown' | 'directory'
  contentHash: string
  writable: boolean
}

interface ConfigAsset {
  id: string
  containerId: string
  kind: ConfigAssetKind
  scope: 'user' | 'workspace' | 'project' | 'local' | 'managed' | 'plugin' | 'bandi'
  fragment?: string
  owner: string
  contentHash: string
  parserVersion: string
  writable: boolean
  references: AssetReference[]
  discoveredAt: string
}
```

`SourceContainer.id` 表示需要整体基线检查和原子替换的物理文件或目录；`ConfigAsset.id` 表示其中逻辑资产的稳定身份，不因扫描批次变化。多个 asset 可共享一个 container，例如 `.claude.json` 的多个 MCP server entry。写锁与 container hash 绑定物理容器，revision 与逻辑 asset 绑定并记录 fragment。外部资产默认保持 SourceAsset 身份；只有用户明确导入时才转为 Bandi 管理的 AgentPackage 或覆盖资产。首期 Claude Agent 导入是独立窄切片：仅接受用户通过系统选择器明确选择的单个用户级或项目级 `.claude/agents/*.md`，预览阶段只读并返回 canonical source path、SHA-256 hash、`name`、可选 `description`、正文及识别/忽略字段；提交阶段重新读取并验证 hash 后复用受管 Agent 创建、ConfigRevision 与 recovery 链。源文件不写入、不链接、不成为后续受管写回目标；目录 reference-only 登记仍是不同命令和语义。

### 5.4 发现

发现过程只扫描用户已授权的根目录：

1. 规范化授权根和候选路径；
2. 识别受支持文件、目录和作用域；
3. 拒绝越过授权根的符号链接或路径；
4. 读取必要元数据与内容哈希；
5. 使用对应解析器验证资产可识别；
6. 记录或更新资产索引、引用和诊断；
7. 不因“发现”自动导入、复制或改写资产。

无法解析的文件仍可作为带诊断的已发现资产展示，但不能在结构化编辑器中保存，除非用户先修复解析问题或明确使用受支持的原文修复入口。

首批 Claude Code discovery profile 必须准确表达：用户 settings 位于 `$CLAUDE_CONFIG_DIR/settings.json`；项目共享/本地 settings 位于 `.claude/settings.json` 与 `.claude/settings.local.json`；用户和项目 local MCP 是 `.claude.json` 内不同 fragment，项目共享 MCP 位于 `.mcp.json`；Plugin 官方安装 scope 为 `user | project | local | managed`。Company 不是安装 scope。Plugin cache 仅是可重建发现证据，不是普通 SourceAsset 写入、恢复或备份目标。

### 5.5 有效配置解析

Local Service 返回最终值及其明确关系：

```ts
interface EffectiveConfig<T> {
  value: T
  sources: ConfigSourceRef[]
  references: AssetReference[]
  constraints: EnforcedConstraint[]
  diagnostics: ConfigDiagnostic[]
  effectiveHash: string
}
```

共享资产默认属于一个 Company，并由明确所有者维护；跨 Company 使用必须注册为独立的跨公司共享资产并逐个授权目标 Company。Agent 的局部定制必须落入 Agent 自有配置或 WorkspaceBinding，不修改共享本体；删除存在有效引用的共享资产前必须解除、迁移或替换引用。

配置关系只允许四类：

1. **全局普通默认**：Agent 未设置对应普通配置时兜底；
2. **Agent 自有配置**：由该 AgentPackage 独立拥有，明确设置时优先于全局普通默认；
3. **显式共享引用**：公共 Skill、Rule、MCP、SOP 只有被 AgentPackage 明确引用后才生效；
4. **全局强制边界**：公司安全限制和 Claude Code 底层硬约束对所有 Agent 生效，Agent 只能进一步收紧，不能放宽。

解析器必须：

- 不把 Company、Department、Role 或 Workspace 当作向 AgentPackage 隐式注入普通配置的继承层；
- 对每个有效字段保留自有、全局默认、共享引用或全局强制的来源资产与路径；
- 区分“Agent 未设置并使用默认”“Agent 明确设置”“显式引用”“强制约束”和“显式清空”；
- 集合类资产按显式引用组合，权限类配置先应用全局强制边界，Memory 按 MemoryProjection 独立组合；
- 不把计算后的有效配置整体写回某个来源文件；
- 遇到互斥设置或无法确定唯一语义时返回解析冲突，不猜测结果；
- 解析器版本变化时可重新计算，不依赖旧投影作为事实。

不同配置族不使用一种通用覆盖算法：settings 按字段及字段类型解析；MCP 以完整 server entry 为语义单元；`CLAUDE.md` 与 rules 保留有序贡献集合和来源；Skills、Agents、Commands 按名称、来源与 Plugin namespace 识别；Plugin 的 marketplace known、installed、enabled 和当前 Session loaded 是四类不同事实。解析器必须保留这种差异，不能把后者从 cache 或文件存在性推断出来。

### 5.6 Agent × Workspace 专属配置

WorkspaceBinding 是 AgentPackage 面向唯一 Workspace 的专属真实配置，不是 Workspace 对全部 Agent 的公共覆盖层。它必须：

- 同时绑定唯一 AgentPackage 与唯一 Workspace；
- 普通可写配置只保存该 Agent 在目标 Workspace 中明确设置的 Instructions、Rule/Skill/MCP 引用、Context override、OutputProfile/参数、Hook/Command 引用和 Orchestration override；不保存账号、凭据、运行期模型状态或 MemoryRevision；
- 继续遵守全局强制安全边界；
- Orchestration override 只能收紧根策略：集合取子集、深度降低、要求与禁止增加；
- 不从 Department、Role 或 Workspace 自动复制普通配置；
- 移除某项专属设置后恢复该 Agent 的通用配置；Agent 通用配置未设置时才使用全局普通默认；
- `agent.workspaceBindings` 是 Agent ↔ Workspace 唯一写入事实，Workspace 侧列表、数量和健康状态均由其派生；
- `memoryRevision` 由正式 MemorySpace / MemoryRevision 派生，只读展示，不进入普通 WorkspaceBinding DTO、canonical 文件或普通 ConfigRevision 正文；
- 新建 Binding 只接受稳定 Agent/Workspace ID，由 Local Service 重新验证 Workspace Registry 后推导固定路径；已有保存、补记和历史恢复同样重验 Registry；
- 通过与其他 AgentPackage 配置相同的 baseline、受限原子写入、重读验证和不可变 Revision 流程写入。

### 5.7 类型化组件、输出契约与 Plugin 安装事实

Hook、Command、OutputProfile 都是可信定义资产，不是执行对象：Hook 与 Command 分别声明事件或稳定 command ID、用途、来源、兼容性和参数定义；OutputProfile 只声明 `markdown/json/text` 响应格式、语言、必需章节、证据要求、固定 `response` destination 和参数。Agent 根级通过 `config/hooks.yaml`、`config/commands.yaml` 和 `config/context.yaml` 显式引用，WorkspaceBinding 只能保存局部引用或覆盖。

组件参数使用按 parameter ID 绑定的判别联合，只允许 `string`、`number`、`boolean`、`string-list`、`enum`。codec 在保存和恢复时验证 required、类型、数值范围和 enum 选项；类型层禁止 secret、任意 object、环境变量、cwd、路径落点、可执行程序和 Shell 模板。可信参数只能约束声明的配置行为，不能扩大权限或引入新的文件、网络、进程能力。

Plugin 资产本体/组件清单、`PluginInstallation`、enablement 与 Agent/Workspace 组件引用是独立事实。Installation 的官方作用域只允许 `user | project | local | managed`，并保存版本历史、兼容性、组件完整性和证据；Company 归属只表达 Bandi 治理。安装、更新、回滚、卸载只改变 Installation，不自动增删引用或 enablement，失效引用由诊断暴露；cache 存在不能推断 enabled 或 Session loaded。当前 Web Mock 只做页面内存状态转换，不探测、下载、执行安装脚本、写文件或加载 Session。

### 5.8 Skill 安装事实与引用事实

Skill 资产至少区分以下两组事实：

- **本体事实**：资产身份、来源、来源信任、已安装版本、可更新版本、兼容性和生命周期状态；
- **引用事实**：AgentPackage 的 `skillRefs` 和 WorkspaceBinding 的专属 Skill 引用。

安装、更新、回滚和卸载只修改本体事实，不自动增删或重写引用事实。卸载后引用仍保留为可诊断的失效引用，用户可重新安装、替换或显式移除。真实实现的 Skill 安装器必须经独立安全设计处理来源、签名/哈希、目标路径、脚本执行和回滚；当前 Web Mock 仅演示状态迁移，不下载内容、不复制文件、不执行安装脚本。

## 6. 普通配置保存

### 6.1 服务契约

```ts
interface ConfigAssetService {
  discover(input: DiscoveryInput): Promise<DiscoveryResult>
  resolveEffective(input: ResolveEffectiveInput): Promise<EffectiveConfig<unknown>>
  loadEditor(input: LoadEditorInput): Promise<ConfigEditorModel>
  save(input: SaveConfigInput): Promise<SaveConfigResult>
  listRevisions(input: ListConfigRevisionsInput): Promise<ConfigRevision[]>
  compareRevisions(input: CompareConfigRevisionsInput): Promise<ConfigDiff>
  restoreRevision(input: RestoreConfigRevisionInput): Promise<SaveConfigResult>
}

interface RestrictedConfigWriter {
  resolveTarget(input: SaveConfigInput): Promise<WriteTarget>
  loadBaseline(target: WriteTarget): Promise<ConfigBaseline>
  validateEdit(input: ValidateEditInput): Promise<ValidatedEdit>
  checkCurrentBaseline(input: BaselineCheckInput): Promise<BaselineCheck>
  atomicallyWrite(input: AtomicWriteInput): Promise<WriteReceipt>
  rereadAndVerify(input: VerifyWriteInput): Promise<VerifiedWrite>
}
```

这些名称只表达 Local Service 内部职责，不要求前端逐步调用，也不是公开 API 的冻结命名。跨 Rust / TypeScript 边界只采用[《本地服务与前端联调契约》](./本地服务与前端联调契约.md)冻结的类型化请求、结果和事件。

### 6.2 保存流程

普通保存固定为：

```text
ResolveTarget
→ LoadBaseline
→ ValidateEdit
→ CheckCurrentBaseline
→ AtomicallyWrite
→ Re-read/Verify
→ Record ConfigRevision
→ Saved
```

各步骤语义：

1. **ResolveTarget**：根据字段来源、编辑作用域和用户意图解析唯一真实目标；禁止把有效配置整体写回错误层级。
2. **LoadBaseline**：读取逻辑 asset 与物理 container 当前内容、元数据、解析结果及双重哈希，返回可重建的 `baselineRef`；敏感值在跨进程前脱敏。
3. **ValidateEdit**：验证 Schema、格式、业务规则、作用域、权限、路径和互斥约束，针对 fragment 生成最小 patch，并保留同一容器中的未知字段和无关逻辑资产。
4. **CheckCurrentBaseline**：写入前重新读取 container；asset hash 或 container hash 变化都进入 `BaselineChanged`，不得静默覆盖。
5. **AtomicallyWrite**：先登记 write journal，再在同一文件系统内写临时文件、保留必要权限、刷盘并原子替换目标，生成不含 secret 的 `WriteReceipt`。
6. **Re-read/Verify**：重新读取和解析整个容器，确认目标 fragment、未知字段保留及有效配置符合预期。
7. **Record ConfigRevision**：写后验证成功后记录不可变版本、container/fragment、双重哈希、父版本、来源基线、确认引用和 write receipt；SQLite 失败时由 journal 暴露可恢复状态，不能把真实已写文件误报为未变化。
8. **Saved**：仅在 revision 记录成功后返回，并更新索引、哈希与审计。

这是一笔短事务，不创建长期存在的通用草稿对象，也不要求普通配置经过审批或发布。写入失败、写后验证失败或 revision 记录失败均不得显示“已保存”。

### 6.3 UI 状态

普通情况下 UI 只显示：

```text
修改 → 保存 → 已保存
```

只有出现实际分支时增加状态：

- `BaselineChanged`：目标在编辑期间被外部修改，展示基线、当前内容与待保存修改的 Diff，允许用户重新应用或放弃；
- 校验失败：在对应字段或文件位置展示可操作诊断；
- 写入失败：说明未完成写入，提供重试或打开目标位置；
- 写后验证失败：标记保存未成功，并按安全恢复策略处理，不显示“已保存”；
- 权限扩大：展示扩大项及影响，等待额外确认。

前端不得把内部步骤扩张为日常向导，也不得在写后验证前乐观显示“已保存”。

### 6.4 Diff、共享影响与冲突

Diff 只在以下场景出现：

1. 用户主动选择“查看更改”；
2. `CheckCurrentBaseline` 发现 `BaselineChanged`，需要辅助合并或重新应用。

普通保存不强制弹出 Diff。高风险权限扩大使用结构化权限变化摘要；用户仍可展开查看对应文件 Diff。

共享影响只在目标 `ConfigAsset` 存在多个有效引用时提示，例如同一 AgentPackage 同时被多个 Workspace 绑定。仅名称相同、内容相似、同属一个目录或可能被未来引用，都不算共享影响。

冲突仅包括：

- **真实并发冲突**：编辑基线后同一目标被其他进程或入口改动；
- **互斥冲突**：两个配置项按已验证规则不能同时生效；
- **解析冲突**：来源链、格式或覆盖关系无法得到唯一一致的有效配置。

普通覆盖、继承、多个来源按确定优先级合并、共享资产提示和权限扩大都不是冲突。

### 6.5 权限扩大确认

以下变化视为高风险权限扩大：

- 新增或扩大可访问目录、文件或 Workspace；
- 新增工具、命令执行、网络访问或外部服务能力；
- 扩大数据读取、写入、删除或跨作用域可见范围；
- 放宽原有 deny/ask 约束；
- 将个人或局部资产改为更多主体共享使用。

Local Service 在写入前基于有效配置比较权限边界，展示“当前权限 → 新权限”、影响主体和可逆方式，并要求一次额外确认。非权限扩大且无并发变化的普通保存不重复确认。

## 7. 配置版本与文件安全

### 7.1 ConfigRevision

```ts
interface ConfigRevision {
  id: string
  assetId: string
  path: string
  parentRevisionId?: string
  restoredFromRevisionId?: string
  contentHash: string
  savedAt: string
  summary: string
  sourceBaselineHash: string
  confirmationRefs: string[]
  writeReceipt: string
}
```

ConfigRevision 是单个普通配置资产的日常追溯记录。正式 Memory 使用 MemoryRevision，不进入普通配置历史。历史内容不可变；保留策略可将大内容放入内容寻址存储，但索引、哈希和父子关系必须稳定。

恢复流程固定为：

```text
加载目标 revision
→ 读取并检查当前基线
→ 校验目标内容
→ 重新检查共享影响和长期权限风险
→ 必要时取得当前操作确认
→ 原子写入并重读验证
→ 生成新的 ConfigRevision（记录 restoredFromRevisionId）
```

恢复不会删除或改写旧 revision。ConfigRevision 用于逐资产追溯；BackupSnapshot 用于跨资产容灾，二者均不能绕过基线检查。

### 7.2 路径安全


所有配置操作只能作用于用户授权的 Workspace、Claude 配置根、AgentPackage 根和 Bandi 数据目录。每次写入都必须：

- 对授权根和目标执行规范化，并验证目标仍位于授权根内；
- 使用安全文件句柄或等价机制降低检查后替换路径的竞态；
- 拒绝符号链接逃逸、路径穿越、设备文件和不受支持的文件类型；
- 验证目标资产身份、作用域和写权限；
- 保留安全的文件权限，不意外扩大访问范围；
- 不通过 Shell 字符串完成文件替换。

### 7.3 原子写入

写入实现至少满足：

1. 在目标同目录创建权限受限的唯一临时文件；
2. 写入规范化后的完整内容；
3. 刷新文件内容，必要时刷新目录元数据；
4. 再次确认待替换目标与已检查目标一致；
5. 使用同文件系统原子替换；
6. 重新读取、解析并校验内容哈希和有效语义；
7. 记录成功审计和新基线。

不以“创建了备份”代替基线检查和原子写入。对不可由原始基线可靠恢复的高风险文件，可在写入事务内创建受控备份；普通配置不为每次保存制造永久备份。若原子替换后验证失败，优先从事务基线安全恢复，并把恢复结果明确告知用户。

### 7.4 备份与恢复

首版只有一个全局 `settings.agentRoot`，所有 AgentPackage 位于该根目录下基于稳定 Agent ID 的独立子目录，不随部门或工作区变化。配置方案管理、Agent 根目录、外部变化保护、快照历史和备份策略共同归入“配置与备份”单屏，但仍是相互独立的领域能力：Agent 根目录不是备份目录，方案版本使用 `ConfigRevision`，跨资产容灾使用 `BackupSnapshot`；创建快照和恢复继续使用 Dialog，旧 `/settings/backup` 仅作兼容跳转。本轮 Web Mock 只更新页面内存，不创建、移动或扫描目录，也不引入目录迁移、文件系统、Git、凭据或 Tauri 能力。该 UI 合并不改变 `BaselineChanged`、三方 Diff、原子写入和写后验证架构。

备份是独立于单次保存事务的容灾能力：

- 首版使用 Bandi 数据目录内的本地快照，支持手动备份、修改停止后的延迟自动备份、历史枚举和按 Company、Agent 或文件恢复；
- 快照包含 Company/组织配置、AgentPackage、显式共享资产、WorkspaceBinding、SOP 和正式 MemorySpace；不包含 Workspace 项目源码、可重建缓存、Claude Code 会话与执行过程；
- API Key、Token、Cookie、SSH 私钥、系统钥匙串内容和其他凭据永不写入快照或 Git；只保存必要的非秘密引用；
- 恢复前必须先创建当前状态快照，再复核目标范围、路径授权和快照完整性；恢复仍使用原子写入与写后验证，不能绕过外部变化检测；
- 正式 MemorySpace 默认进入本地快照；是否进入远程备份由用户单独开启并确认。

远程 Git 备份是渐进能力：

- Bandi 通过服务 API 自动创建的仓库固定为私有仓库，不提供公开可见性选项；
- 连接已有 GitHub 仓库时必须验证私有状态，确认公开时拒绝上传；自定义 Git 无法可靠验证可见性时必须显示强风险提示并取得明确确认；
- GitHub/OAuth/PAT 等凭据只存入系统钥匙串，不进入 Git remote URL、提交内容、日志或普通配置；
- 首阶段只保证本地到远端的版本化备份，不承诺多设备自动双向同步和自动冲突合并；
- 断开当前设备只移除本机连接与凭据，不删除远端数据；删除远程仓库必须独立确认仓库身份并作为高风险操作审计。

备份实现必须保存快照清单、内容哈希、创建时间、设备标识、范围和来源版本。恢复成功、恢复失败、恢复前安全快照和远端上传分别记录，不把“已提交”或“已推送”与本地配置已安全写入混为同一状态。

### 7.5 文件监听

文件监听用于使资产索引和编辑页面失效重载，不用于建立执行状态：

- 外部变化使相关缓存和有效配置失效；
- 正在编辑的目标变化时标记 `BaselineChanged`；
- 未在编辑的资产可自动重新发现和解析；
- 监听事件必须去抖，并以重新读取结果为准；
- 监听丢失时通过聚焦刷新、手动刷新或周期性轻量校验恢复一致性。

## 8. 领域事实与存储

### 8.1 SQLite/WAL

规划中的 Local Service 使用 SQLite 作为本机领域事实库并启用 WAL：写事务保持短小，由 Rust 单写者串行化领域变更；读者可读取一致快照，checkpoint、迁移、备份和异常恢复由 Local Service 管理。WAL 不把 SQLite 变成配置主源，也不用于任务日志、终端输出或 Session 追踪。

SQLite 管理：

- Workspace、可空、单值外键 `company_id`（不设唯一约束，多个 Workspace 可引用同一 Company）、Company、Department（含 `parent_department_id`）、Role、主管/成员关系，以及 Workspace 唯一主责部门、默认项目负责人和同公司协作部门关系；
- Agent 稳定身份、active/inactive/archived 状态、可空、单值外键的主属部门（多个 Agent 可属于同一 Department），以及包含目标部门、允许能力、Workspace 范围、有效状态和禁止事项的跨部门服务授权；
- AgentPackage 元数据、WorkspaceBinding、SourceAsset 索引和引用关系；
- 配置资产身份、规范路径、作用域、格式、解析器版本、哈希和诊断摘要；
- 全局默认与强制边界、共享资产显式引用、Agent × Workspace 专属绑定；
- ConfigRevision 的父版本、恢复来源、内容哈希、保存时间、摘要、来源基线、确认引用和写入回执；
- 作为配置资产的 SOP/WorkflowDefinition、WorkflowVersion 及其适用范围；
- OrchestrationPolicy、允许的委派关系；
- 正式 Memory ReviewDecision，以及长期权限扩大、恢复、删除等高风险长期配置操作的用户确认；
- PluginInstallation；
- MemorySpace 元数据、逻辑定位、owner、steward、审核与可见策略；
- MemoryCandidate、ReviewDecision、MemoryRevision、哈希和写入审计；
- MemoryProjection 的版本与来源元数据；Claude Code 执行期配置投影不作为长期事实或快照写入 SQLite；
- 本地 BackupSnapshot 清单、范围、内容哈希、设备、创建原因、恢复记录和远程备份连接元数据；
- 设置、长期权限配置和配置操作审计事件。

SQLite 不保存可替代真实配置文件的整份日常配置副本；备份内容存放在独立快照目录或私有 Git 仓库中，SQLite 只保存索引与状态。SQLite 不保存终端执行过程镜像，也不为 Claude Code 中的临时任务创建 WorkflowRun、Assignment、Handoff、聊天、汇报或验收记录。只有用户明确同意持久化的 SOP/WorkflowDefinition 或其他正式配置提议，才进入对应配置保存流程。

Workspace Registry 是 SQLite 中的受控注册关系，不是目录扫描缓存：它以稳定 `workspaceId` 绑定用户明确登记的原始路径、canonical path、验证状态和最近验证证据。涉及目录或终端交接的请求只传 `workspaceId`，Local Service 必须重新取出并复核登记路径，不信任前端重复提交 cwd。

AI Adapter Registry 同样是受控事实：每条记录包含稳定 `adapterId`、支持的客户端、固定启动实现、支持能力、平台/版本约束和最近验证证据。它不保存用户提供的可执行文件、任意 argv、Shell 模板、环境变量或脚本正文。未登记、未验证或证据过期的 adapter 只能显示“未验证/不可用”，不能宣称已安装、已连接或可启动。

### 8.2 本地文件

```text
真实配置资产
├── Company / 全局配置              底层公共配置、普通默认与强制安全边界
├── 共享资产                        Company 内共享；跨 Company 需单独注册和授权
├── agents/
│   └── <stable-agent-id>/          不随显示名、岗位或部门移动
│       ├── agent.yaml              稳定身份、显示信息、生命周期状态与岗位引用
│       ├── soul.md                 长期行为原则
│       ├── instructions.md         跨 Workspace 主指令
│       ├── memory/long-term.md     Agent 长期正式记忆载体
│       ├── config/
│       │   ├── context.yaml        上下文策略与 OutputProfile 引用
│       │   ├── skills.yaml         Skill 显式引用
│       │   ├── rules.yaml          Rule 显式引用
│       │   ├── mcp.yaml            MCP 显式引用
│       │   ├── permissions.yaml    长期权限边界
│       │   ├── sop.yaml            SOP 显式引用
│       │   ├── orchestration.yaml  静态编排边界
│       │   ├── hooks.yaml          Hook 显式引用
│       │   └── commands.yaml       Command 显式引用
│       └── workspaces/
│           └── <workspace-id>/     该 Agent 面向目标 Workspace 的专属配置
│               └── config.yaml
├── Claude 用户/项目配置            外部 SourceAsset
├── Plugin 配置                     安装基线与受支持设置
├── 其他 MemorySpace 逻辑文件       Workspace 公共和 Department × Workspace
└── BackupSnapshot                  独立本地快照；可选推送至私有 Git 远端
```

上述目录是逻辑文件契约：首版不冻结全部 YAML 字段，也不为没有内容的可选项创建空文件。Bandi 自管 AgentPackage 默认根为 `~/.bandi/agents/`；外部 AgentPackage 保持用户授权的规范路径并以 SourceAsset 引用，只有显式导入才复制到自管根。AgentPackage 的稳定身份来自 `agent-id`，不从路径中的显示名、Company、部门或岗位推断；组织移动只更新关系数据，不移动目录。Bandi 表单与原始文件编辑映射到同一真实资产；用户在外部编辑后，Local Service 重新发现并比较基线，编辑中的变化触发 `BaselineChanged`，不得静默覆盖。

外部 Claude Code 配置保持 SourceAsset 身份，除非用户明确导入。数据库中的哈希、解析摘要和版本用于发现变化、解释来源和审计，不取代原文件。

### 8.3 Claude Code 执行期配置投影

`RuntimeProjection` 仅作为 CLI / Plugin 内部实现名，表示按需生成且可重建的临时配置视图：

```text
Bandi Plugin 安装基线
+ Company / 全局底层配置、普通默认与强制安全边界
+ Plugin Agent
+ 目标 AgentPackage / Agent 自有 WorkspaceBinding
+ Agent 显式引用的共享资产
+ 权限过滤、版本化的 MemoryProjection
+ 允许的 Skill / MCP / settings
+ Workflow / Policy / 初始上下文
+ 来源、版本与哈希
= RuntimeProjection
```

约束：

- 只在 CLI / Plugin 明确需要当前配置上下文时临时编译；
- 输入未变时可在调用方内部复用，输入变化后重新生成；
- 不反向发布到源配置，不进入 SQLite 长期事实、Desktop 资产、版本、页面状态或待处理事项；
- 缺失时可从真实资产重建，不作为配置编辑器基线或日常保存主源；
- 不表示终端或 Session 已加载，不产生启动、attach 或运行跟踪 API。

上下文策略由 `ContextPolicy` 表达，Agent 根级 `contextWindowTokens` 保存规划窗口，Agent × Workspace 仅保存既有策略的局部 override；codec 在生成 `ConfigRevision` 前校验窗口、比例、轮次和“目标至少低于触发 10 个百分点”的约束。未来 Claude Code RuntimeProjection 可将窗口和触发比例映射为 `CLAUDE_CODE_AUTO_COMPACT_WINDOW` 与 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`；Desktop 当前只保存源配置，不注入环境变量，也不表示当前 Session 已应用。配置方案使用 `configuration-environments/<environment-id>.yaml` 作为页面内存版本逻辑路径，保存稳定 ID、名称和去重后的 `clientIds`；所有工具共享唯一当前方案，Agent 配置不引用配置方案。网络代理是独立的普通设置，手动模式使用标准 `URL` 校验协议、userinfo、查询参数、fragment、控制字符和不走代理条目。当前 Web Mock 的配置方案、工具加入状态和代理设置均只在 React 页面内存，不写文件、不读取系统代理、不注入环境变量，也不调用 Gateway。

### 8.4 凭据

Token、API Key 和账号密钥只保存于系统钥匙串、Claude Code 受管位置或用户授权 Secret Manager。SQLite 只保存安全引用、授权状态和验证时间。

## 9. 记忆治理

### 9.1 四类 MemorySpace

每个 MemorySpace 使用独立逻辑文件载体，由版本化 `MemoryStorageResolver` 解析物理位置。首版冻结 `memory-v1` profile；公开 DTO 只携带稳定 scope key、`storageProfileVersion` 与相对 locator，不接受绝对路径：

```text
agent_long_term(agent_id)
  root: managed AgentPackage(agt_{agent_id})
  relative: memory/long-term.md

agent_workspace(agent_id, workspace_id)
  root: managed AgentPackage(agt_{agent_id})
  relative: workspaces/{workspace_id}/memory.md

workspace_shared(workspace_id)
  root: Workspace Registry 中该 Workspace 的 canonical root
  relative: .bandi/memory/public.md

department_workspace(department_id, workspace_id)
  root: Workspace Registry 中该 Workspace 的 canonical root
  relative: .bandi/memory/departments/{department_id}.md
```

`memory-v1` 内容格式固定为 UTF-8 Markdown，最大 1 MiB；稳定 ID 只能使用 `[A-Za-z0-9._-]`，不得出现空路径分量、`.` 或 `..`。解析时必须从数据库与 Workspace Registry 重取 canonical root，拒绝包根、中间目录或目标符号链接以及任何越界；不存在正式事实时不预建空文件。跨公司关系变化后失效的部门空间保留 `read_only_history` 元数据和 Revision，不再接受候选。

- `agent_long_term`：单个 Agent 跨 Workspace 的长期记忆；董事长助理用它维护与董事长和主管交互形成的长期总记忆；
- `agent_workspace`：单个 Agent 在单个 Workspace 的项目记忆；董事长助理只在其中维护项目级协调、汇报和待董事长决策摘要；
- `workspace_shared`：Workspace 内按策略共享的公共记忆，由唯一主责部门主管归口；
- `department_workspace`：主责部门或协作部门在单个 Workspace 的项目记忆，由对应部门主管维护本部门的目标、计划、进展、风险、依赖、分工、决策和交付等项目管理事实。

Workspace 的 `company_id` 可空且为单值外键，但该列不设唯一约束，多个 Workspace 可引用同一 Company；非空时必须指向一个有效 Company；主责部门、默认项目负责人和协作部门都必须属于该 Company。解析有效配置、委派关系和 RuntimeProjection 时只能使用这一 Company 的上下文，禁止把多个 Company 的普通默认、共享引用或强制安全边界合并进同一 Workspace。

每个已关联组织的 Workspace 必须且只能有一个主责部门，可有零到多个协作部门；主责部门主管是默认项目负责人，负责总体结果、公共记忆归口、跨部门进展汇总和向董事长助理汇报。协作主管只负责本部门交付与 `department_workspace`，不能接管公共记忆或其他部门台账。董事长助理负责跨部门协调、冲突升级和董事长决策摘要，不维护完整项目台账。

更换主责部门或项目负责人必须作为显式关系变更处理：先校验新主责部门及主管有效，再转移后续归口与相应权限；`workspace_shared`、所有 `department_workspace`、MemoryRevision 和审计历史保持不变，不自动修改或删除 AgentPackage、WorkspaceBinding 或既有记忆。原主责部门按用户选择转为协作部门或解除项目关系。

更换或清除 `company_id` 是高影响关系事务：在写入前计算旧公司共享资产引用、委派关系、权限和记忆可见性失效范围；关联新公司时要求重新选择主责部门、默认项目负责人和协作部门。事务不得删除 Workspace 目录、`workspace_shared`、MemoryRevision 或审计历史；旧公司的 `department_workspace` 转为只读历史边界，除非用户另行执行迁移或归档。不得按名称自动映射跨公司部门，也不得保留未经新公司授权的访问能力。

不再建立独立的 `assistant_workspace_management` 空间。Workspace 公共记忆不能存入助理 AgentPackage，部门项目记忆不能存入主管 AgentPackage，不同 Workspace 的 Agent 项目记忆不能解析到同一逻辑文件。

### 9.2 Memory Service 与权限

```text
resolveReadableSpaces
buildMemoryProjection
proposeCandidate
reviewCandidate
writeApprovedCandidate
```

以上是职责名称，不是冻结的公开 API。Workflow 权限不能隐式替代记忆权限；读取、提议、审核和正式写入分别裁决。

| 身份 | 默认可读记忆 |
| --- | --- |
| 董事长助理 | 自身长期总记忆、Agent × Workspace 协调/汇报摘要、Workspace 公共；部门项目记忆仅按协调授权读取必要部分 |
| 部门主管 | 自身长期、Agent × Workspace 项目、Workspace 公共、本部门当前 Workspace 项目管理记忆 |
| 专业/执行 Agent | 自身长期、Agent × Workspace 项目、Workspace 公共、所属部门当前 Workspace 项目记忆 |

跨部门参与不自动授予全部部门记忆。审核责任使用 `ReviewPrincipal` 表达为 `{ kind: 'agent', agentId }` 或 `{ kind: 'chairman_user', companyId }`；它表达本机单董事长模型中的责任归属，不宣称多用户认证。Agent 提议者不能由同一 Agent principal 审核，董事长 principal 与 Agent 提议者不是同一主体。无有效直属主管时由所属 Company 的董事长兜底；Workspace/Department 归口人自提时优先升级有效董事长助理，无可用助理时由董事长审核。候选改投其他 MemorySpace 或正式审核前必须重新计算可见性、提议权限和审核策略；当前 principal 与 Candidate、MemorySpace 或请求中的 `expectedReviewPrincipal` 不一致时返回 `governance_changed`，不得记录决定或复用旧批准写入。客户端不得提交 actor。

### 9.3 MemoryCandidate 独立状态机

```text
Proposed → Validated → PendingReview
→ Approved | Rejected | ChangesRequested
→ WritePrepared → AtomicallyWritten → RevisionRecorded
```

- 所有正式记忆变化都必须先形成 MemoryCandidate；
- 每个候选只有一个主要目标 MemorySpace；
- `Approved` 只表示审核通过，不表示文件写入成功；
- `AtomicallyWritten` 只表示批准内容已写入目标文件；
- `RevisionRecorded` 记录不可变版本、来源、审核、基线和哈希；
- 投影是否重新编译与终端是否加载均不是候选状态机的下一状态。

记忆写回前必须重新校验目标 revision、content hash、权限、路径和符号链接边界，展示候选 Diff，并使用受控备份和原子替换。普通配置的简化保存流程不得绕过这套审核。

### 9.4 MemoryProjection

CLI / Plugin 按当前 Agent、Workspace、Department、SOP 和权限解析 MemoryProjection：

```text
Agent 长期记忆
→ Workspace 公共记忆
→ 当前 Department × Workspace 部门项目记忆（按职责和权限）
→ Agent × Workspace 项目记忆
→ 当前任务临时上下文（仅在 Claude Code 内，不持久化）
```

每层保存 `scope`、`owner`、`revision`、`content_hash`、来源、纳入原因和权限裁决。组合顺序表示上下文逐步收窄，不是后层静默覆盖前层；内容冲突必须保留来源并阻止或显式降级投影。董事长助理的长期总记忆与 Workspace 协调摘要来自其与董事长、部门主管的正式交互提炼，不复制负责部门的完整项目管理台账。

## 10. Bandi Plugin 与 Claude Code 衔接

### 10.1 Plugin 定位

Bandi Plugin 是 Claude Code 侧稳定安装基线，也是当前会话按需读取 Bandi 配置事实、校验委派边界和提交长期化建议的适配层。它不向 Desktop 暴露当前会话的 attach、启动或运行状态。

Plugin / MCP 可以读取授权配置、校验委派边界，并在用户明确要求长期化时提交结构化的 SOP/普通配置建议或 MemoryCandidate。普通配置建议必须在 Desktop 或等价可信界面确认具体变更，由 Local Service 校验、受控写入、写后验证并生成 ConfigRevision；MemoryCandidate 继续走独立审核流程。Plugin / MCP 不直接写 SQLite、AgentPackage 或正式 Memory，也不把任务、一次性权限授权、执行状态或 Session 生命周期写入 Local Service。

### 10.2 Desktop 衔接契约

```ts
interface ClaudeCodeGuideService {
  inspectConfig(input: GuideInspectionInput): Promise<GuideInspection>
  buildGuide(input: BuildGuideInput): Promise<ClaudeCodeGuide>
  requestClientHandoff(input: {
    clientId: 'claude-code'
    adapterId: 'claude-code-terminal-v1'
    workspaceId: string
    terminalId: string
    intent: 'continue_workspace'
  }): Promise<ClientHandoffResult>
}
```

Desktop 可展示 Workspace 登记路径、已验证 adapter 能力和 Bandi Plugin 入口。Local Service 根据 `workspaceId` 从 Workspace Registry 重取 canonical cwd，根据 `adapterId` 从 AI Adapter Registry 选择固定启动实现；前端不得提交通用 executable、argv、Shell、环境变量、stdin 或脚本。启动请求成功只表示操作系统接受请求，不证明 Claude Code、Plugin、`/bandi:bandi` 或 Session 已加载；Local Service 不继续发布 Session 或执行进度事件。

个人 Workspace 的规划入口只在 React `client-guide` Dialog 中保存三个局部字段，并在前端生成一次性协作规划说明供用户主动复制。字段与生成文本不进入业务 `State` 集合、配置方案、Workspace、RuntimeProjection、Tauri command、Local Service、ConfigRevision、备份、遥测或 Session；关闭 Dialog 即丢弃。当前实现中的 `executable + args + enterBandiOnStart` DTO 是待迁移的过渡协议，不再作为有效架构契约；首轮 Claude Code Adapter 只按冻结的 `continue_workspace` 意图打开已登记 Workspace 的 canonical cwd，不执行或追加 `/bandi:bandi`。规划文本只约束对话顺序，不声明覆盖 Claude Code 的真实权限模式。

CLI / Plugin 可在自身边界内按需生成 Claude Code 执行期配置投影。临时工具授权不得自动写回长期权限；只有用户明确选择永久化时，才提交普通配置建议，并在 Desktop 或等价可信界面完成长期权限变更确认与 ConfigRevision 记录。终端请求的跨进程 DTO 以[《本地服务与前端联调契约》](./本地服务与前端联调契约.md)为准。

## 11. SOP、委派与策略服务

SOP/WorkflowDefinition 是描述适用场景、分工边界、必要检查和交付要求的配置资产，不是由 Local Service 驱动的运行实例。它由 Claude Code 中的董事长助理结合当前任务解释执行，并可继续委派主管；主管再选择员工。具体任务、步骤、交接、汇报和验收始终留在用户自己的 Claude Code CLI。

```ts
interface WorkflowDefinitionService {
  create(input: WorkflowDefinitionInput): Promise<WorkflowDefinition>
  validateDefinition(id: string): Promise<WorkflowValidation>
  saveVersion(id: string, input: WorkflowDefinitionInput): Promise<WorkflowVersion>
  compose(parentId: string, childId: string, nodeId: string): Promise<void>
}

interface DelegationConstraintService {
  evaluateCandidate(input: DelegationCandidate): Promise<DelegationDecision>
  explainGap(input: DelegationGapInput): Promise<DelegationGap>
  validateDefinitionScope(input: WorkflowScopeInput): Promise<WorkflowValidation>
  detectCycle(input: DelegationGraph): Promise<CycleDetection>
}
```

每次委派必须同时校验：

1. **部门职责**：任务属于候选部门的明确职责范围；
2. **岗位与 Skills**：候选 Agent 的岗位职责和已配置 Skills 覆盖任务需要；
3. **WorkspaceBinding**：候选 Agent、部门及配置资产允许用于当前 Workspace；
4. **MCP 与权限**：所需 MCP、工具、目录、网络和数据权限已配置且未超出边界；
5. **委派关系**：董事长可直接联系任意 `active` Agent，或默认委托董事长助理协调；助理只向允许的主管委派，主管默认只向本部门员工委派；直接联系和跨部门候选都必须满足有效服务授权、任务能力、Workspace 和禁止事项等既有边界；
6. **Agent 状态**：只有 `active` Agent 可以接受新委派，`inactive` 和 `archived` 只保留档案与历史；
7. **SOP 适用范围**：使用的 SOP/WorkflowDefinition 适用于当前 Company、Department、Role、Workspace 和任务类型。

组织身份、主管标签、岗位或服务关系本身不授予文件、命令、网络、MCP、记忆和继续委派权限；这些能力必须由权限配置显式授予。Agent 可以在有效边界内收紧权限，但任何扩大都必须向上报告并由有权主体确认后写入，不能在执行中自行放宽。

Local Service 只返回配置事实、校验结论和缺口诊断；MCP 只是 Claude Code 中的适配层，不定义 SOP、不决定组织关系、不创建任务或调度人员。若没有候选 Agent 同时满足约束，必须报告缺失项并请求补充配置、调整目标或由用户明确决策，不得静默越权。

终端中的临时计划、分工、交接、工具进度、汇报和验收不创建 WorkflowRun 或 WorkflowStepRun，也不进入 Local Service。只有用户明确同意把可复用做法沉淀为正式 SOP 时，Plugin/MCP 才提交配置变更，经校验与受限写回形成不可变版本。`saveVersion` 只表达保存版本，不具有发布审批语义。

## 12. 外部 CLI 与终端安全

### 12.1 `bandi` 系统 CLI

```text
bandi                 查看配置状态与 Claude Code 入口指引
bandi status          查看 Local Service、Plugin 和配置资产状态
bandi doctor          诊断 CLI、Plugin、MCP、Hooks、配置解析和权限
bandi config inspect  查看有效配置、来源和诊断
bandi open            在目标 Workspace 中打开 Claude Code（具体参数待验证）
```

命令名称和参数在实现时验证。本质要求是调用同一 Local Service，而不是复制配置或入口逻辑。

### 12.2 终端启动安全

- 目标跨进程请求顶层只传 `clientId`、`adapterId`、`workspaceId`、`terminalId`、`intent`；不得增加 `requestId`、受控布尔选项、cwd、bundle ID、`executable`、`argv`、Shell 字符串、环境变量、stdin 或脚本正文；
- Local Service 从 Workspace Registry 重取 canonical cwd，从 AI Adapter Registry 选择固定、版本化的客户端目录交接实现；前端配置方案不能新增可执行文件或参数模板；
- 已移除 `launch_workspace_terminal` 的 cwd、executable 和 args 过渡协议；当前 `request_client_handoff` 只接受冻结五字段，未知字段由 Rust `deny_unknown_fields` 拒绝；
- `claude-code-terminal-v1` 与 `codex-terminal-v1` 只允许 Rust 使用固定 `/usr/bin/open` 请求白名单终端打开 canonical cwd；不执行或追加 Claude Code、Codex、`/bandi:bandi` 或其他命令，也不回传 fallback 命令；
- 用户必须明确选择具体终端；默认选择 macOS Terminal.app，不展示或声称读取“系统默认终端”；旧版 `system` 值只能在迁移输入中归一化为 `terminal`，不得进入 wire DTO；
- 每个终端 adapter 必须有经过验证的能力证据；不能安全打开所选终端时，只能按能力事实降级为复制 cwd 后手动继续，不能虚报执行；
- 交接配置不得包含密钥；不读取输出、不等待进程、不保存 PID、不管理 Session；
- `accepted` 只表示操作系统接受打开目录请求，不等于 Claude Code、Bandi、Plugin 或 Session 已成功加载。

- 可展示委派约束的配置与静态诊断，但不提供“派人执行”按钮或运行控制入口。

### 13.1 当前前端命令与桌面桥

当前应用通过前端桥接模块协调桌面壳，不建立第二套业务状态：

- `route-metadata.ts`：由 pathname 与实体集合解析主导航归属和页面标题；同一结果用于 Shell、`document.title` 与 Tauri 原生窗口标题；
- `editor-session.tsx`：只注册当前活动编辑器的 `{ id, dirty, canSave, save, cancel }`；草稿、校验、权限扩大确认和离开保护仍归编辑器自身；
- `app-commands.ts`：只接受固定白名单导航、主题和编辑命令；未知命令返回 no-op；
- `desktop-bridge.ts`：浏览器环境安全降级；Tauri 环境监听 `bandi://app-command` 并设置当前窗口标题。

系统菜单与 Web 快捷键复用同一语义命令。`Cmd/Ctrl+S` 仅在活动 Editor Session 可保存时拦截；`Cmd+,` 进入设置；不定义全局 Escape 取消。Rust 菜单只发送白名单 command id，不接受任意字符串执行请求。

当前 capability 只绑定 `main` 窗口，保留以下平台权限，并为 `AppManifest::commands` 中每个应用 command 逐项配置对应的 `allow-<command>`；不得使用 `*` 通配符：

```text
core:event:allow-listen
core:event:allow-unlisten
core:window:allow-set-title
dialog:allow-open
allow-<每个已登记应用 command>
```

capability ACL、系统文件/目录选择器与 Rust 领域校验构成三层独立边界：前者限制可调用窗口，中间层取得用户明确选择，后者重新验证不可信路径和操作前置条件。选择结果本身不授予通用文件系统访问，也不替代 canonical path、symlink、目标范围、基线和内容校验。

当前 `invoke_handler` 精确注册配置管理所需的窄 command，覆盖：

```text
Workspace Registry
配置 discovery / editor load / save / revision / recovery / restore
WorkspaceBinding 创建
request_client_handoff
固定 UI 图片槽位
受管 AgentPackage identity / avatar
```

command 能力边界分别是已登记配置资产的受限读写与版本、受限目录交接、应用数据目录中的两个固定 UI 图片槽位，以及受管 AgentPackage 的创建、身份清单与 PNG 头像。它们不授权通用 fs、Shell、任意 process、clipboard 或 global-shortcut；AI 交接响应不包含 cwd、命令、PID、输出或 Session 状态。主窗口启动尺寸为 `1280×800`，最小尺寸为 `960×640`；56px 配置管理 Rail 始终保留。存在会话内最近 Agent 时，`>=1280px` 的跟随窗口布局使用 220px Agent 上下文栏，`<1280px` 使用 64px 紧凑栏；固定展开在 `960–1279px` 使用 188px，仅 `<960px` 紧凑显示。没有最近 Agent或用户显式选择隐藏时，上下文栏不渲染；显式隐藏偏好只写入版本化 `UiPreferences`，可从个性化设置恢复。

packages/

## 15. 分阶段实施

### 阶段 0：契约验证

- 确认真实配置资产、作用域、Agent 独立配置、全局默认/强制、显式共享引用与 WorkspaceBinding 语义；
- 验证目标 Claude Code 版本的配置优先级、格式、Plugin、Skill、Agent、MCP、Hooks 和 settings 能力；
- 建立脱敏配置样例和解析、写回安全测试矩阵。

### 阶段 1：本地中枢与 Desktop 骨架

- Tauri、React、Rust、SQLite；
- Local Service 生命周期、受限 API 与三段式 Desktop Shell（应用壳布局，不是命令行 Shell）；
- Workspace、Company、Claude CLI 和授权根探测。

### 阶段 2：配置资产发现与有效配置

- AgentPackage、Claude 配置和 Plugin 配置发现；
- 稳定资产身份、SourceAsset、引用关系和诊断；
- Agent 自有配置、全局普通默认、显式共享引用、全局强制边界与 WorkspaceBinding 解析；
- 先落地单个 `.claude/agents/*.md` 的只读预览、hash 复核和受管副本导入；目录扫描、批量导入及其他资产自动转换不进入该切片。

### 阶段 3：受限写回

- `ResolveTarget → LoadBaseline → ValidateEdit → CheckCurrentBaseline → AtomicallyWrite → Re-read/Verify → Saved`；
- 主动 Diff 与 `BaselineChanged` 处理；
- 多引用资产共享影响；
- 并发、互斥和解析冲突；
- 权限扩大确认、路径安全、原子替换和事务恢复测试；
- 本地 BackupSnapshot、自动备份合并、历史和按范围恢复；恢复前安全快照。

### 阶段 4：组织、AgentPackage、Workflow 与策略

- 公司、树形部门、岗位和分层 Agent；
- 部门父子关系、主管、成员、跨部门服务与委派边界；
- 循环检测、移动与删除前迁移校验；组织关系变化不改写 AgentPackage 配置；
- WorkspaceBinding 与 AgentPackage 管理；
- SOP/WorkflowDefinition 定义、版本、适用范围和静态委派约束校验；
- 部门职责、岗位/Skills、WorkspaceBinding、MCP/权限、委派关系和 SOP 范围缺口诊断；
- 不建设 WorkflowRun、任务调度、执行推进、聊天、汇报或验收服务。

### 阶段 5：分层记忆治理

- 四类 MemorySpace 与逻辑文件定位；
- 每个 Agent × Workspace 的独立项目记忆载体；
- MemoryCandidate、审核、自审升级、Diff、备份和原子写回；
- MemoryRevision 与分层 MemoryProjection。

### 阶段 6：Bandi Plugin 与 Claude Code 使用衔接

- Plugin 安装和版本状态；
- Skill、作为复杂协作默认入口的董事长助理 Agent、Bandi MCP、最小 Hooks、settings，并支持董事长在 CLI 中直接联系任意 `active` Agent；
- Claude Code 中“助理选部门与主管、主管选员工”的分层委派，以及无合适 Agent 时的缺口报告；
- 临时协作留终端、用户同意后才提交正式 SOP 提议；
- `bandi` CLI、`/bandi:bandi` 和可选薄别名；
- Plugin 按需读取长期配置并生成 Claude Code 执行期配置投影；
- Desktop canonical cwd 目录交接、终端适配和复制路径后的手动降级。

首版到此为止。所有任务交互、分层委派、执行推进、汇报和验收由用户自己的 Claude Code CLI 承载；Bandi 只管理配置事实、校验边界和处理用户同意的持久化提议，不采集、不镜像执行过程，也不据此维护前端执行页面、人员调度台或状态轴。

## 16. 技术验收标准

1. Desktop、CLI 和 Plugin 读取同一 Local Service 事实、配置解析和策略；
2. Rust 是 SQLite 业务事实唯一写入者，也是配置文件受限写回的唯一入口；
3. React UI 无通用 Shell、任意文件系统和凭据读取权限；
4. 已授权根中的真实配置资产可发现，稳定身份、作用域、格式、路径和引用可解释；
5. 外部配置保持 SourceAsset 身份，未经明确导入不复制为 Bandi 主源；
6. 有效配置能逐字段解释 Agent 自有设置、全局普通默认、显式共享引用、全局强制边界、显式清空和 Agent × Workspace 专属设置；
7. Company、Department、Role 和 Workspace 不向 AgentPackage 隐式注入普通配置；WorkspaceBinding 是 Agent 面向特定 Workspace 的独立真实配置；
8. Department 通过 `parent_department_id` 构成无环组织树；创建、移动和删除均校验循环、主管归属与成员迁移，组织调整不改写 AgentPackage 配置；
9. Agent 最多一个主属部门，可有多个带目标部门、能力、Workspace 与禁止事项边界的服务授权；停用和归档保留档案且不接受新委派，永久删除使用独立高风险事务；
10. 共享资产默认 Company 内共享，跨 Company 必须单独注册和授权，局部定制不修改共享本体，删除前处理全部有效引用；
11. 组织身份不授予执行或委派权限；Agent 可收紧但不能自行扩大，缺少权限时返回缺口并由有权主体确认；
12. Bandi 自管 AgentPackage 使用 `~/.bandi/agents/<stable-agent-id>/`，不随显示名或部门移动；个人 Agent 无需组织关系，组织 Agent 的 Company/Department/Role 必须完整且同作用域；根级长期配置与 `workspaces/<workspace-id>/` 专属配置映射到同一组可外部编辑的真实资产；
12a. 单个 Claude Agent 文件导入执行只读预览、提交前重读和 source hash 复核，创建独立受管副本并保证原文件不变；reference-only 不读取或复制目录内容；
13. Workspace 的 `company_id` 可空但不可多值；关联后主责部门、项目负责人和协作部门必须来自同一 Company，有效配置与安全边界不得跨公司合并；
14. 每个已关联组织的 Workspace 只能存在一个主责部门和默认项目负责人，可存在多个协作部门；变更主责关系保留公共记忆、部门记忆和历史，不自动改写 AgentPackage 或 WorkspaceBinding；
15. 普通保存严格执行 `ResolveTarget → LoadBaseline → ValidateEdit → CheckCurrentBaseline → AtomicallyWrite → Re-read/Verify → Saved`；
16. UI 普通流程只显示“修改 → 保存 → 已保存”，且写后验证前不得显示成功；
17. Diff 只在用户主动查看或 `BaselineChanged` 时出现；
18. 共享影响只针对存在多个有效引用的同一真实资产；
19. 冲突只用于真实并发、互斥规则和无法一致解析，不把普通覆盖或权限变化称为冲突；
20. 权限扩大在写入前显示边界变化、影响主体和可逆方式，并要求额外确认；
21. 写回防止路径穿越、符号链接逃逸、跨 Workspace 越权和静默覆盖；
22. 原子替换后必须重新读取和解析，内容与有效语义均验证成功才返回 `Saved`；
23. 文件监听以重新读取为准，能使缓存失效并触发编辑中的 `BaselineChanged`；
24. 每次普通配置成功保存生成不可变 ConfigRevision；失败不生成；
25. 可列出和比较 ConfigRevision；恢复复用安全写入链并生成新 revision，记录恢复来源；
26. ConfigRevision 与 BackupSnapshot 分工清晰，均不替代基线检查；
27. RuntimeProjection 可由 CLI / Plugin 按需重建，不是 Desktop 日常配置主源或 Session 状态；
28. Desktop 只展示 canonical cwd、交接能力证据并可请求白名单终端打开目录；不生成、执行或回传宿主命令，结果不等于宿主、Plugin 或 Session 已创建、已连接或已加载配置；
29. 所有任务交互、分层委派、执行推进、汇报和验收只发生在用户自己的 Claude Code CLI；
30. 董事长可直接联系任意 `active` Agent，董事长助理是复杂、多部门事项的默认协调入口；直接联系不扩大权限或绕过配置约束；
31. 每次委派同时校验部门职责、岗位/Skills、WorkspaceBinding、MCP/权限、委派关系和 SOP 适用范围；
32. 无合适 Agent 时返回明确配置缺口，不静默跨部门、突破委派关系、扩大权限或使用未配置替代能力；
33. Desktop 和 Local API 不提供任务创建、人员调度、执行推进、聊天、汇报、验收或运行控制 UI/API；
34. Plugin/MCP 只读取配置事实、校验委派边界和提交必要持久化提议，不成为任务执行器；
35. SOP/WorkflowDefinition 作为配置资产由 Claude Code 中的助理解释执行，临时协作只有经用户同意才保存为正式 SOP；
36. Local Service 不持久化任务审批、一次性工具授权、任务冲突、WorkflowRun 或执行状态，也不向 Desktop 发布 Session/执行进度事件；
37. Bandi 不采集或镜像终端计划、委派、提示词、工具调用、中间结果、进度、汇报、验收、用量和会话生命周期；
38. 前端不提供 WorkflowRun、人员调度台或基于推断的执行中、完成、停止、恢复状态；
39. 四类 MemorySpace 的 owner、steward、reviewer 和 Local Service 写入执行者严格分离；
40. 每个 Agent × Workspace 使用独立项目记忆载体，共享与部门记忆不存入个人 AgentPackage；
41. SOP/Workflow 权限不自动授予记忆读取、提议、审核或写入权限；
42. 所有正式记忆变化先形成 MemoryCandidate，提议者不能自审；
43. MemoryCandidate 批准、原子写入、Revision 记录和投影重编译分别建模；
44. MemoryProjection 保留来源、版本、哈希、纳入原因和权限裁决，冲突不静默覆盖；
45. 960×640 下可完成资产发现、有效配置查看、Agent × Workspace 专属配置、普通保存、版本比较/恢复、SOP 配置、委派约束诊断和记忆审核；
46. 用户可创建本地快照、查看历史并按 Company、Agent 或文件恢复；恢复前自动生成当前状态快照；
47. Bandi 自动创建的 Git 备份仓库固定为私有；已知公开仓库不得上传，凭据和执行过程永不进入备份，正式记忆远程备份需单独确认。
