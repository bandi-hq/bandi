## 1. 文档目标

本文定义 Bandi 首版的技术施工边界：

- Bandi 是现实创业公司的本地数字孪生；
- Bandi Desktop、`bandi` CLI 和 Bandi Plugin 共用 Rust Local Service；
- Local Service 管理真实配置资产的发现、独立 Agent 配置组合、显式共享引用、Agent × Workspace 专属配置和受限写回；
- Bandi 管理组织、职责、Skills、WorkspaceBinding、权限、SOP 等配置资产，用户仍在自己的 Claude Code CLI 中完成全部任务交互与分层委派；
- 董事长只与董事长助理交互；助理按配置选择部门并委派主管，主管再按配置选择员工；
- Desktop 和 Local API 不创建任务、不调度人员、不推进执行，也不提供聊天、汇报、验收或运行控制；
- Plugin/MCP 是 Claude Code 中读取配置事实、校验委派边界和提交必要持久化提议的适配层，不让 Desktop 或 Local Service 成为执行器；
- SOP/WorkflowDefinition 是配置资产，由 Claude Code 中的董事长助理解释执行；临时协作留在终端，只有用户同意才保存为正式 SOP；
- 普通配置保存是短事务，不引入通用草稿发布系统；
- 普通配置成功写后生成 ConfigRevision，支持版本比较和恢复；RuntimeProjection 仅是 CLI / Plugin 内部可重建产物；
- 四类 MemorySpace、MemoryCandidate 审核和版本写回继续构成独立的记忆治理契约；
- 终端内的计划、委派、工具调用、执行进度、汇报、验收和会话状态不采集、不镜像到 Bandi。

## 2. 技术原则

1. **本地优先**：源码、组织、配置、凭据引用和 Workspace 默认留在用户设备。
2. **三端一中枢**：Desktop、系统 CLI 和 Plugin 共享 Local Service，不分别保存公司事实或配置副本。
3. **真实资产优先**：外部配置文件保持自身身份；数据库只保存索引、绑定、策略、版本与审计，不制造第二份配置主源。
4. **配置关系可解释**：Local Service 区分 Agent 自有、全局普通默认、显式共享引用、全局强制边界和 Agent × Workspace 专属配置，而非返回来源不明的合并黑盒。
5. **普通保存短事务**：修改、校验和写回直接围绕当前文件基线完成，不引入通用发布审批状态机。
6. **按需展示 Diff**：普通保存不强制展示 Diff；用户主动查看或基线变化时才展示。
7. **冲突语义收敛**：只有真实并发修改、互斥规则不满足或配置无法一致解析才称为冲突。
8. **共享影响有边界**：只有同一真实资产被多个 Workspace、Agent 或绑定引用时，才提示共享影响。
9. **长期权限扩大额外确认**：永久扩大 AgentPackage 工具、目录、网络、命令、MCP、委派或数据范围时确认；某次工具调用的一次性授权只在 Claude Code。
10. **受限系统能力**：React UI 无通用 Shell 和任意文件系统权限，写回只能通过类型化 Local Service 命令。
11. **文件安全**：所有写回执行路径授权、符号链接边界检查、基线复核、原子替换和写后验证。
12. **记忆独立治理**：正式记忆变化始终由 MemoryCandidate 先审后写，不复用普通配置保存流程。
13. **投影可重建**：RuntimeProjection 由 CLI / Plugin 按需从真实配置、绑定、策略和记忆投影重新生成，不进入 Desktop 状态。
14. **执行边界清晰**：用户自己的 Claude Code CLI 是唯一任务交互与执行现场；Desktop、Local Service 和 Local API 均不是任务执行器。
15. **单一董事长入口**：董事长只与董事长助理交互；助理选择部门并委派主管，主管选择员工，不向董事长暴露平行人员调度入口。
16. **配置约束委派**：每次选择必须同时满足部门职责、岗位与 Skills、WorkspaceBinding、MCP 与权限、委派关系及 SOP 适用范围；无合适 Agent 时报告配置缺口，不静默越权或降级绕过。
17. **临时协作不沉淀**：Claude Code 中的临时计划、分工与协作上下文默认留在终端；只有用户明确同意，才形成正式 SOP/WorkflowDefinition 配置变更。
18. **跨平台准备**：macOS 首发，领域契约避免依赖 Mac 专属语义。
19. **安装事实与引用分离**：Skill 的来源、安装版本和生命周期属于资产事实；Agent 与 WorkspaceBinding 只保存显式引用，安装、更新、回滚或卸载不得隐式改写引用集合。
20. **阶段能力不伪装**：当前 React Web Mock 的 onboarding、目录树、Skill 操作和快照只修改页面内存；真实目录、安装、备份和 Claude Code 探测必须等待类型化系统能力接入。

## 3. 产品形态与技术栈

### 3.1 发布形态

```text
第一阶段：macOS Bandi Desktop + Rust Local Service + bandi CLI + Bandi Plugin
第二阶段：Windows 客户端及平台适配
第三阶段：按真实需求扩展远程连接或宿主集成
```

首版所有任务交互、分层委派、执行推进、汇报与验收都发生在用户自己的 Claude Code CLI。Desktop 与 Local API 不提供任务创建、人员调度、聊天、汇报、验收、停止、恢复或其他运行控制 UI/API，也不以持续观察 Claude Code 会话为前提。

### 3.2 技术栈

| 层 | 技术 | 职责 |
| --- | --- | --- |
| 桌面壳 | Tauri 2 | 窗口、系统权限、目录选择、文件和终端唤起 |
| 前端 | React + TypeScript + Vite | 配置浏览、编辑、来源解释、保存反馈与类型化 ViewModel |
| UI | Tailwind CSS v4 + shadcn/ui + Radix + Lucide | 语义 Token、可访问组件与图标 |
| 本地核心 | Rust | 配置发现、解析、覆盖、校验、安全写回、领域服务与审计 |
| 数据库 | SQLite/WAL | 组织、绑定、策略、资产索引、版本、记忆治理和审计 |
| 本地通信 | Tauri Command / localhost 类型化 API | Desktop、CLI、Plugin 的配置查询、校验和受限持久化接口，不含任务运行 API |
| Claude 集成 | Bandi Plugin | Claude Code 中的董事长助理、配置事实读取、委派边界校验、SOP 解释与必要持久化提议 |
| 系统入口 | `bandi` CLI | doctor、status、配置检查和 Claude Code 入口 |
| 凭据 | 系统钥匙串 | MCP 和外部服务的安全引用 |
| UI 更新 | Tauri Event 或请求刷新 | 文件扫描、保存、备份和恢复等配置操作进度；不发布 Session/执行进度 |

Node Sidecar 与 Claude Agent SDK 不属于首版必选路径。若未来增加宿主集成，仍须服从 Rust 的配置、策略和业务事实边界。

## 4. 总体架构：三端一中枢

```text
┌────────────────────┐
│ Bandi Desktop      │ React UI + Tauri
└─────────┬──────────┘
          │ 类型化查询 / 业务命令
┌─────────▼──────────────────────────────────────┐
│ Rust Local Service                            │
│                                               │
│ Workspace / Organization                     │
│ Config Asset Discovery                       │
│ Effective Config Resolver                    │
│ Workspace Override Service                   │
│ Restricted Config Writer                     │
│ Agent Package / SOP / Policy                 │
│ Delegation Constraint Validator              │
│ Memory Service / Projection Compiler         │
│ Config Revision / Audit / Local Ops           │
└─────────┬──────────────────────────────────────┘
          │
          ├── SQLite：索引、绑定、策略、版本与审计
          ├── AgentPackage / SourceAsset：真实配置资产
          ├── Workspace / Git / Claude 配置根
          ├── Keychain
          └── 操作系统终端：受限唤起，不接管会话

┌────────────────────┐        ┌────────────────────────────┐
│ bandi CLI          │        │ Bandi Claude Code Plugin   │
│ 系统 Shell         │        │ Skill · Agent · MCP · Hook │
└─────────┬──────────┘        └─────────────┬──────────────┘
          └──────────────► Local Service ◄──┘
                           配置事实 / 边界校验 / 持久化提议
                                      │
                           用户自己的 Claude Code CLI
               董事长 → 董事长助理 → 部门主管 → 员工 Agent
                  （任务交互、分层委派、执行、汇报与验收）
```

### 4.1 Rust Local Service 职责

Local Service 是 SQLite 业务事实的唯一写入者，也是配置资产操作的唯一受控入口，负责：

- 发现授权根内的 AgentPackage、Claude 配置和其他 SourceAsset；
- 识别资产类型、作用域、格式、物理路径、稳定身份、引用关系和当前哈希；
- 组合 Company / 全局基础配置、AgentPackage 自有配置、显式共享资产引用和 Agent 自有 WorkspaceBinding，计算可解释的有效配置；
- 管理全局普通默认、全局强制安全边界、共享资产显式引用和 Agent × Workspace 专属配置；
- 为编辑选择唯一真实写回目标，加载基线并验证修改；
- 在写入前复核当前基线、权限、路径、格式、互斥约束和共享引用；
- 通过同目录临时文件、刷盘和原子替换完成受限写回；
- 写后重新读取、解析并验证期望结果，更新资产索引和审计；
- 管理 Workspace、Company、树形 Department、Role、部门主管、成员、Agent 唯一主属部门和带范围的跨部门服务授权；
- 管理 Agent 的 active/inactive/archived 生命周期；停用或归档保留 AgentPackage、正式记忆与历史并排除新委派，永久删除使用独立高风险事务；
- 保证 Workspace 可暂不关联但最多归属一个 Company，并隔离不同 Company 的组织、默认配置与安全边界；
- 管理 Workspace 的唯一主责部门、默认项目负责人和多个同公司协作部门关系，并保证同一 Workspace 不存在多个主责方；
- 校验部门父子关系、循环、组织深度提示、主管归属、Workspace 项目责任关系和删除/移动前的成员迁移方案；
- 管理 AgentPackage 元数据、Skills、SOP/WorkflowDefinition 和 OrchestrationPolicy 等配置资产；
- 提供委派约束校验：部门职责、岗位与 Skills、WorkspaceBinding、MCP 与权限、组织委派关系、SOP 适用范围；
- 对无合适 Agent、配置缺失或约束不满足返回可解释诊断，不替 Claude Code 选择或调度人员；
- 管理 PluginInstallation、兼容性和组件完整性；
- 管理四类 MemorySpace、MemoryCandidate、审核、正式写回和 MemoryRevision；
- 按 CLI / Plugin 请求编译 RuntimeProjection 与 MemoryProjection；
- 为 Desktop 提供 cwd、标准命令和受限终端打开参数；
- 提供受限的文件、目录、编辑器与终端操作；
- 记录 ConfigRevision、记忆审核、长期权限扩大和高风险配置操作审计。

Local Service 不负责：

- 替用户审批经营决策；
- 创建任务、选择或调度人员、推进执行、组织聊天、收集汇报、执行验收或控制运行；
- 直接执行 Claude 推理，或承载董事长、助理、主管、员工之间的任务交互；
- 采集或镜像终端中的计划、委派、提示词、工具调用、中间结果、进度、汇报、验收、用量和会话生命周期；
- 根据终端窗口、MCP 连接或 Hook 事件推断“执行中”“已完成”等状态；
- 允许 Plugin 或 UI 绕过策略直接写 SQLite 或配置文件；
- 允许任何 Agent、MCP 或 Hook 绕过 Memory Service 直接修改正式长期记忆；
- 把 RuntimeProjection 当成日常配置编辑或持久化主源。

### 4.2 客户端边界

React UI 不直接读写任意文件、拼接 Shell、读取凭据或写 SQLite。Tauri 只暴露配置资产查询、有效配置解析、受限保存、版本比较/恢复、委派约束校验、记忆审核和 cwd/命令衔接等类型化命令；不暴露任务创建、人员调度、执行推进、聊天、汇报、验收或运行控制命令。

当前仓库中的 React Web Mock 进一步收紧为纯页面内存演示：onboarding 只记录 `active/completed`，业务状态刷新后恢复初始 fixture，不写 `localStorage`、文件、Tauri、SQLite 或后端；仅主题偏好可使用 `localStorage`。首次“选择目录”是文本输入，“演示扫描”“演示安装”“演示连接”和“演示快照”都不能被描述为真实系统结果。本轮信息架构优化不新增 Tauri command、Local Service API、目录适配器、Skill 安装器或备份后端。

`bandi` CLI 和 Plugin 调用同一 Local Service，不复制资产发现、覆盖解析、保存安全、Company 匹配、策略或投影逻辑。任务交互与分层委派只在用户自己的 Claude Code CLI 中进行：董事长只对话董事长助理，助理读取 Local Service 提供的组织、职责、Skills、WorkspaceBinding、权限和 SOP 配置后按需选择部门并委派主管，主管再在同一约束下选择员工。Local Service 只返回事实与校验结论，不参与任务执行。

## 5. 配置资产模型

### 5.1 AgentPackage 目录投影

AgentPackage 的物理目录事实由 Local Service 发现并登记；React 不自行扫描目录。前端目录树只能由当前 Agent 已登记的 `AgentFile[]` 构建：

```text
AgentFile[]
→ 路径规范化与重复/非法路径过滤
→ buildAgentPackageTree()
→ ARIA tree
→ 选择 path
→ 结构化预览 / 只读源码 / ConfigRevision 历史
```

根级文件表达跨 Workspace 的长期配置，`workspaces/<workspace-id>/` 表达 Agent 自有的 WorkspaceBinding 文件。没有登记的路径不得以占位内容伪装为磁盘文件；外部只读 AgentPackage 没有可靠内容时不得生成虚假源码。AgentPackage 路由以配置领域、路径和 `preview|source` 模式构成稳定深链。

### 5.2 资产身份

```ts
type ConfigAssetKind =
  | 'agent_package'
  | 'global_config'
  | 'shared_asset'
  | 'agent_workspace_binding'
  | 'claude_user_config'
  | 'claude_project_config'
  | 'plugin_config'
  | 'other_supported_source'

interface ConfigAsset {
  id: string
  kind: ConfigAssetKind
  canonicalPath: string
  scope: 'user' | 'workspace' | 'project' | 'plugin' | 'bandi'
  format: 'json' | 'jsonc' | 'toml' | 'yaml' | 'markdown' | 'directory'
  owner: string
  contentHash: string
  parserVersion: string
  writable: boolean
  references: AssetReference[]
  discoveredAt: string
}
```

`ConfigAsset.id` 表示同一真实资产的稳定身份，不因扫描批次变化。外部资产默认保持 SourceAsset 身份；只有用户明确导入时才转为 Bandi 管理的 AgentPackage 或覆盖资产。

### 5.3 发现

发现过程只扫描用户已授权的根目录：

1. 规范化授权根和候选路径；
2. 识别受支持文件、目录和作用域；
3. 拒绝越过授权根的符号链接或路径；
4. 读取必要元数据与内容哈希；
5. 使用对应解析器验证资产可识别；
6. 记录或更新资产索引、引用和诊断；
7. 不因“发现”自动导入、复制或改写资产。

无法解析的文件仍可作为带诊断的已发现资产展示，但不能在结构化编辑器中保存，除非用户先修复解析问题或明确使用受支持的原文修复入口。

### 5.4 有效配置解析

Local Service 返回最终值及其明确关系：

```ts
interface EffectiveConfig<T> {
  value: T
  sources: ConfigSourceRef[]
  references: AssetReference[]
  constraints: EnforcedConstraint[]
  diagnostics: ConfigDiagnostic[]
  effectiveHash: string
}
```

共享资产默认属于一个 Company，并由明确所有者维护；跨 Company 使用必须注册为独立的跨公司共享资产并逐个授权目标 Company。Agent 的局部定制必须落入 Agent 自有配置或 WorkspaceBinding，不修改共享本体；删除存在有效引用的共享资产前必须解除、迁移或替换引用。

配置关系只允许四类：

1. **全局普通默认**：Agent 未设置对应普通配置时兜底；
2. **Agent 自有配置**：由该 AgentPackage 独立拥有，明确设置时优先于全局普通默认；
3. **显式共享引用**：公共 Skill、Rule、MCP、SOP 只有被 AgentPackage 明确引用后才生效；
4. **全局强制边界**：公司安全限制和 Claude Code 底层硬约束对所有 Agent 生效，Agent 只能进一步收紧，不能放宽。

解析器必须：

- 不把 Company、Department、Role 或 Workspace 当作向 AgentPackage 隐式注入普通配置的继承层；
- 对每个有效字段保留自有、全局默认、共享引用或全局强制的来源资产与路径；
- 区分“Agent 未设置并使用默认”“Agent 明确设置”“显式引用”“强制约束”和“显式清空”；
- 集合类资产按显式引用组合，权限类配置先应用全局强制边界，Memory 按 MemoryProjection 独立组合；
- 不把计算后的有效配置整体写回某个来源文件；
- 遇到互斥设置或无法确定唯一语义时返回解析冲突，不猜测结果；
- 解析器版本变化时可重新计算，不依赖旧投影作为事实。

### 5.5 Agent × Workspace 专属配置

WorkspaceBinding 是 AgentPackage 面向唯一 Workspace 的专属真实配置，不是 Workspace 对全部 Agent 的公共覆盖层。它必须：

- 同时绑定唯一 AgentPackage 与唯一 Workspace；
- 保存该 Agent 在目标 Workspace 中明确设置的 Instructions、Rules、Skill/MCP 引用、账号、权限、模型和项目记忆定位；
- 继续遵守全局强制安全边界；
- 不从 Department、Role 或 Workspace 自动复制普通配置；
- 移除某项专属设置后恢复该 Agent 的通用配置；Agent 通用配置未设置时才使用全局普通默认；
- 通过与其他 AgentPackage 配置相同的安全保存流程写入。

### 5.6 Skill 安装事实与引用事实

Skill 资产至少区分以下两组事实：

- **本体事实**：资产身份、来源、来源信任、已安装版本、可更新版本、兼容性和生命周期状态；
- **引用事实**：AgentPackage 的 `skillRefs` 和 WorkspaceBinding 的专属 Skill 引用。

安装、更新、回滚和卸载只修改本体事实，不自动增删或重写引用事实。卸载后引用仍保留为可诊断的失效引用，用户可重新安装、替换或显式移除。真实实现的 Skill 安装器必须经独立安全设计处理来源、签名/哈希、目标路径、脚本执行和回滚；当前 Web Mock 仅演示状态迁移，不下载内容、不复制文件、不执行安装脚本。

## 6. 普通配置保存

### 6.1 服务契约

```ts
interface ConfigAssetService {
  discover(input: DiscoveryInput): Promise<DiscoveryResult>
  resolveEffective(input: ResolveEffectiveInput): Promise<EffectiveConfig<unknown>>
  loadEditor(input: LoadEditorInput): Promise<ConfigEditorModel>
  save(input: SaveConfigInput): Promise<SaveConfigResult>
  listRevisions(input: ListConfigRevisionsInput): Promise<ConfigRevision[]>
  compareRevisions(input: CompareConfigRevisionsInput): Promise<ConfigDiff>
  restoreRevision(input: RestoreConfigRevisionInput): Promise<SaveConfigResult>
}

interface RestrictedConfigWriter {
  resolveTarget(input: SaveConfigInput): Promise<WriteTarget>
  loadBaseline(target: WriteTarget): Promise<ConfigBaseline>
  validateEdit(input: ValidateEditInput): Promise<ValidatedEdit>
  checkCurrentBaseline(input: BaselineCheckInput): Promise<BaselineCheck>
  atomicallyWrite(input: AtomicWriteInput): Promise<WriteReceipt>
  rereadAndVerify(input: VerifyWriteInput): Promise<VerifiedWrite>
}
```

这些名称表达内部职责，不要求前端逐步调用，也不是公开 API 的冻结命名。

### 6.2 保存流程

普通保存固定为：

```text
ResolveTarget
→ LoadBaseline
→ ValidateEdit
→ CheckCurrentBaseline
→ AtomicallyWrite
→ Re-read/Verify
→ Record ConfigRevision
→ Saved
```

各步骤语义：

1. **ResolveTarget**：根据字段来源、编辑作用域和用户意图解析唯一真实目标；禁止把有效配置整体写回错误层级。
2. **LoadBaseline**：读取目标当前内容、元数据、解析结果和内容哈希，形成该次编辑的基线。
3. **ValidateEdit**：验证 Schema、格式、业务规则、作用域、权限、路径和互斥约束，生成最小目标变更。
4. **CheckCurrentBaseline**：写入前重新读取目标；若哈希或关键元数据变化，进入 `BaselineChanged`，不得静默覆盖。
5. **AtomicallyWrite**：在同一文件系统内写临时文件、保留必要权限、刷盘并原子替换目标。
6. **Re-read/Verify**：重新读取和解析文件，确认写入内容、目标语义及有效配置符合预期。
7. **Record ConfigRevision**：写后验证成功后记录不可变版本、父版本、内容哈希、来源基线、确认引用和写入回执。
8. **Saved**：仅在 revision 记录成功后返回，并更新索引、哈希与审计。

这是一笔短事务，不创建长期存在的通用草稿对象，也不要求普通配置经过审批或发布。写入失败、写后验证失败或 revision 记录失败均不得显示“已保存”。

### 6.3 UI 状态

普通情况下 UI 只显示：

```text
修改 → 保存 → 已保存
```

只有出现实际分支时增加状态：

- `BaselineChanged`：目标在编辑期间被外部修改，展示基线、当前内容与待保存修改的 Diff，允许用户重新应用或放弃；
- 校验失败：在对应字段或文件位置展示可操作诊断；
- 写入失败：说明未完成写入，提供重试或打开目标位置；
- 写后验证失败：标记保存未成功，并按安全恢复策略处理，不显示“已保存”；
- 权限扩大：展示扩大项及影响，等待额外确认。

前端不得把内部步骤扩张为日常向导，也不得在写后验证前乐观显示“已保存”。

### 6.4 Diff、共享影响与冲突

Diff 只在以下场景出现：

1. 用户主动选择“查看更改”；
2. `CheckCurrentBaseline` 发现 `BaselineChanged`，需要辅助合并或重新应用。

普通保存不强制弹出 Diff。高风险权限扩大使用结构化权限变化摘要；用户仍可展开查看对应文件 Diff。

共享影响只在目标 `ConfigAsset` 存在多个有效引用时提示，例如同一 AgentPackage 同时被多个 Workspace 绑定。仅名称相同、内容相似、同属一个目录或可能被未来引用，都不算共享影响。

冲突仅包括：

- **真实并发冲突**：编辑基线后同一目标被其他进程或入口改动；
- **互斥冲突**：两个配置项按已验证规则不能同时生效；
- **解析冲突**：来源链、格式或覆盖关系无法得到唯一一致的有效配置。

普通覆盖、继承、多个来源按确定优先级合并、共享资产提示和权限扩大都不是冲突。

### 6.5 权限扩大确认

以下变化视为高风险权限扩大：

- 新增或扩大可访问目录、文件或 Workspace；
- 新增工具、命令执行、网络访问或外部服务能力；
- 扩大数据读取、写入、删除或跨作用域可见范围；
- 放宽原有 deny/ask 约束；
- 将个人或局部资产改为更多主体共享使用。

Local Service 在写入前基于有效配置比较权限边界，展示“当前权限 → 新权限”、影响主体和可逆方式，并要求一次额外确认。非权限扩大且无并发变化的普通保存不重复确认。

## 7. 配置版本与文件安全

### 7.1 ConfigRevision

```ts
interface ConfigRevision {
  id: string
  assetId: string
  path: string
  parentRevisionId?: string
  restoredFromRevisionId?: string
  contentHash: string
  savedAt: string
  summary: string
  sourceBaselineHash: string
  confirmationRefs: string[]
  writeReceipt: string
}
```

ConfigRevision 是单个普通配置资产的日常追溯记录。正式 Memory 使用 MemoryRevision，不进入普通配置历史。历史内容不可变；保留策略可将大内容放入内容寻址存储，但索引、哈希和父子关系必须稳定。

恢复流程固定为：

```text
加载目标 revision
→ 读取并检查当前基线
→ 校验目标内容
→ 重新检查共享影响和长期权限风险
→ 必要时取得当前操作确认
→ 原子写入并重读验证
→ 生成新的 ConfigRevision（记录 restoredFromRevisionId）
```

恢复不会删除或改写旧 revision。ConfigRevision 用于逐资产追溯；BackupSnapshot 用于跨资产容灾，二者均不能绕过基线检查。

### 7.2 路径安全


所有配置操作只能作用于用户授权的 Workspace、Claude 配置根、AgentPackage 根和 Bandi 数据目录。每次写入都必须：

- 对授权根和目标执行规范化，并验证目标仍位于授权根内；
- 使用安全文件句柄或等价机制降低检查后替换路径的竞态；
- 拒绝符号链接逃逸、路径穿越、设备文件和不受支持的文件类型；
- 验证目标资产身份、作用域和写权限；
- 保留安全的文件权限，不意外扩大访问范围；
- 不通过 Shell 字符串完成文件替换。

### 7.3 原子写入

写入实现至少满足：

1. 在目标同目录创建权限受限的唯一临时文件；
2. 写入规范化后的完整内容；
3. 刷新文件内容，必要时刷新目录元数据；
4. 再次确认待替换目标与已检查目标一致；
5. 使用同文件系统原子替换；
6. 重新读取、解析并校验内容哈希和有效语义；
7. 记录成功审计和新基线。

不以“创建了备份”代替基线检查和原子写入。对不可由原始基线可靠恢复的高风险文件，可在写入事务内创建受控备份；普通配置不为每次保存制造永久备份。若原子替换后验证失败，优先从事务基线安全恢复，并把恢复结果明确告知用户。

### 7.4 备份与恢复

备份是独立于单次保存事务的容灾能力：

- 首版使用 Bandi 数据目录内的本地快照，支持手动备份、修改停止后的延迟自动备份、历史枚举和按 Company、Agent 或文件恢复；
- 快照包含 Company/组织配置、AgentPackage、显式共享资产、WorkspaceBinding、SOP 和正式 MemorySpace；不包含 Workspace 项目源码、可重建缓存、Claude Code 会话与执行过程；
- API Key、Token、Cookie、SSH 私钥、系统钥匙串内容和其他凭据永不写入快照或 Git；只保存必要的非秘密引用；
- 恢复前必须先创建当前状态快照，再复核目标范围、路径授权和快照完整性；恢复仍使用原子写入与写后验证，不能绕过外部变化检测；
- 正式 MemorySpace 默认进入本地快照；是否进入远程备份由用户单独开启并确认。

远程 Git 备份是渐进能力：

- Bandi 通过服务 API 自动创建的仓库固定为私有仓库，不提供公开可见性选项；
- 连接已有 GitHub 仓库时必须验证私有状态，确认公开时拒绝上传；自定义 Git 无法可靠验证可见性时必须显示强风险提示并取得明确确认；
- GitHub/OAuth/PAT 等凭据只存入系统钥匙串，不进入 Git remote URL、提交内容、日志或普通配置；
- 首阶段只保证本地到远端的版本化备份，不承诺多设备自动双向同步和自动冲突合并；
- 断开当前设备只移除本机连接与凭据，不删除远端数据；删除远程仓库必须独立确认仓库身份并作为高风险操作审计。

备份实现必须保存快照清单、内容哈希、创建时间、设备标识、范围和来源版本。恢复成功、恢复失败、恢复前安全快照和远端上传分别记录，不把“已提交”或“已推送”与本地配置已安全写入混为同一状态。

### 7.5 文件监听

文件监听用于使资产索引和编辑页面失效重载，不用于建立执行状态：

- 外部变化使相关缓存和有效配置失效；
- 正在编辑的目标变化时标记 `BaselineChanged`；
- 未在编辑的资产可自动重新发现和解析；
- 监听事件必须去抖，并以重新读取结果为准；
- 监听丢失时通过聚焦刷新、手动刷新或周期性轻量校验恢复一致性。

## 8. 领域事实与存储

### 8.1 SQLite

SQLite 管理：

- Workspace、可空且唯一的 `company_id`、Company、Department（含 `parent_department_id`）、Role、主管/成员关系，以及 Workspace 唯一主责部门、默认项目负责人和同公司协作部门关系；
- Agent 稳定身份、active/inactive/archived 状态、可空且唯一的主属部门，以及包含目标部门、允许能力、Workspace 范围、有效状态和禁止事项的跨部门服务授权；
- AgentPackage 元数据、WorkspaceBinding、SourceAsset 索引和引用关系；
- 配置资产身份、规范路径、作用域、格式、解析器版本、哈希和诊断摘要；
- 全局默认与强制边界、共享资产显式引用、Agent × Workspace 专属绑定；
- ConfigRevision 的父版本、恢复来源、内容哈希、保存时间、摘要、来源基线、确认引用和写入回执；
- 作为配置资产的 SOP/WorkflowDefinition、WorkflowVersion 及其适用范围；
- OrchestrationPolicy、允许的委派关系；
- 正式 Memory ReviewDecision，以及长期权限扩大、恢复、删除等高风险长期配置操作的用户确认；
- PluginInstallation；
- MemorySpace 元数据、逻辑定位、owner、steward、审核与可见策略；
- MemoryCandidate、ReviewDecision、MemoryRevision、哈希和写入审计；
- MemoryProjection、RuntimeProjection 和 LaunchContext 的索引或快照元数据；
- 本地 BackupSnapshot 清单、范围、内容哈希、设备、创建原因、恢复记录和远程备份连接元数据；
- 设置、长期权限配置和配置操作审计事件。

SQLite 不保存可替代真实配置文件的整份日常配置副本；备份内容存放在独立快照目录或私有 Git 仓库中，SQLite 只保存索引与状态。SQLite 不保存终端执行过程镜像，也不为 Claude Code 中的临时任务创建 WorkflowRun、Assignment、Handoff、聊天、汇报或验收记录。只有用户明确同意持久化的 SOP/WorkflowDefinition 或其他正式配置提议，才进入对应配置保存流程。

### 8.2 本地文件

```text
真实配置资产
├── Company / 全局配置              底层公共配置、普通默认与强制安全边界
├── 共享资产                        Company 内共享；跨 Company 需单独注册和授权
├── agents/
│   └── <stable-agent-id>/          不随显示名、岗位或部门移动
│       ├── agent.yaml              稳定身份、显示信息、生命周期状态与岗位引用
│       ├── soul.md                 长期行为原则
│       ├── instructions.md         跨 Workspace 主指令
│       ├── memory/long-term.md     Agent 长期正式记忆载体
│       ├── config/                 Skill / Rule / MCP / 权限 / 编排配置与引用
│       ├── workflows/              Agent 自有 SOP；共享 SOP 通过显式引用使用
│       └── workspaces/
│           └── <workspace-id>/     该 Agent 面向目标 Workspace 的专属配置
│               ├── config.yaml
│               ├── instructions.md
│               └── memory.md       Agent × Workspace 项目记忆载体
├── Claude 用户/项目配置            外部 SourceAsset
├── Plugin 配置                     安装基线与受支持设置
├── 其他 MemorySpace 逻辑文件       Workspace 公共和 Department × Workspace
└── BackupSnapshot                  独立本地快照；可选推送至私有 Git 远端
```

上述目录是逻辑文件契约：首版不冻结全部 YAML 字段，也不为没有内容的可选项创建空文件。Bandi 自管 AgentPackage 默认根为 `~/.bandi/agents/`；外部 AgentPackage 保持用户授权的规范路径并以 SourceAsset 引用，只有显式导入才复制到自管根。AgentPackage 的稳定身份来自 `agent-id`，不从路径中的显示名、Company、部门或岗位推断；组织移动只更新关系数据，不移动目录。Bandi 表单与原始文件编辑映射到同一真实资产；用户在外部编辑后，Local Service 重新发现并比较基线，编辑中的变化触发 `BaselineChanged`，不得静默覆盖。

外部 Claude Code 配置保持 SourceAsset 身份，除非用户明确导入。数据库中的哈希、解析摘要和版本用于发现变化、解释来源和审计，不取代原文件。

### 8.3 RuntimeProjection

RuntimeProjection 是 CLI / Plugin 按需生成的不可变、可重建快照：

```text
Bandi Plugin 安装基线
+ Company / 全局底层配置、普通默认与强制安全边界
+ Plugin Agent
+ 目标 AgentPackage / Agent 自有 WorkspaceBinding
+ Agent 显式引用的共享资产
+ 权限过滤、版本化的 MemoryProjection
+ 允许的 Skill / MCP / settings
+ Workflow / Policy / 初始上下文
+ 来源、版本与哈希
= RuntimeProjection
```

约束：

- 只在 CLI / Plugin 明确需要运行上下文时编译；
- 输入版本未变时可复用同一快照；
- 输入变化后重新编译，不反向把快照发布到源配置；
- 快照缺失或被删除时可从真实资产重建；
- 不作为配置编辑器的基线，不承担日常保存或同步职责；
- 终端是否实际加载快照不由 Bandi 首版持续跟踪。

### 8.4 凭据

Token、API Key 和账号密钥只保存于系统钥匙串、Claude Code 受管位置或用户授权 Secret Manager。SQLite 只保存安全引用、授权状态和验证时间。

## 9. 记忆治理

### 9.1 四类 MemorySpace

每个 MemorySpace 使用独立逻辑文件载体，由版本化 `MemoryStorageResolver` 解析物理位置：

```text
agent_long_term(agent_id)
agent_workspace(agent_id, workspace_id)
workspace_shared(workspace_id)
department_workspace(department_id, workspace_id)
```

- `agent_long_term`：单个 Agent 跨 Workspace 的长期记忆；董事长助理用它维护与董事长和主管交互形成的长期总记忆；
- `agent_workspace`：单个 Agent 在单个 Workspace 的项目记忆；董事长助理只在其中维护项目级协调、汇报和待董事长决策摘要；
- `workspace_shared`：Workspace 内按策略共享的公共记忆，由唯一主责部门主管归口；
- `department_workspace`：主责部门或协作部门在单个 Workspace 的项目记忆，由对应部门主管维护本部门的目标、计划、进展、风险、依赖、分工、决策和交付等项目管理事实。

Workspace 的 `company_id` 可空，但非空时必须唯一指向一个 Company；主责部门、默认项目负责人和协作部门都必须属于该 Company。解析有效配置、委派关系和 RuntimeProjection 时只能使用这一 Company 的上下文，禁止把多个 Company 的普通默认、共享引用或强制安全边界合并进同一 Workspace。

每个已关联组织的 Workspace 必须且只能有一个主责部门，可有零到多个协作部门；主责部门主管是默认项目负责人，负责总体结果、公共记忆归口、跨部门进展汇总和向董事长助理汇报。协作主管只负责本部门交付与 `department_workspace`，不能接管公共记忆或其他部门台账。董事长助理负责跨部门协调、冲突升级和董事长决策摘要，不维护完整项目台账。

更换主责部门或项目负责人必须作为显式关系变更处理：先校验新主责部门及主管有效，再转移后续归口与相应权限；`workspace_shared`、所有 `department_workspace`、MemoryRevision 和审计历史保持不变，不自动修改或删除 AgentPackage、WorkspaceBinding 或既有记忆。原主责部门按用户选择转为协作部门或解除项目关系。

更换或清除 `company_id` 是高影响关系事务：在写入前计算旧公司共享资产引用、委派关系、权限和记忆可见性失效范围；关联新公司时要求重新选择主责部门、默认项目负责人和协作部门。事务不得删除 Workspace 目录、`workspace_shared`、MemoryRevision 或审计历史；旧公司的 `department_workspace` 转为只读历史边界，除非用户另行执行迁移或归档。不得按名称自动映射跨公司部门，也不得保留未经新公司授权的访问能力。

不再建立独立的 `assistant_workspace_management` 空间。Workspace 公共记忆不能存入助理 AgentPackage，部门项目记忆不能存入主管 AgentPackage，不同 Workspace 的 Agent 项目记忆不能解析到同一逻辑文件。

### 9.2 Memory Service 与权限

```text
resolveReadableSpaces
buildMemoryProjection
proposeCandidate
reviewCandidate
writeApprovedCandidate
```

以上是职责名称，不是冻结的公开 API。Workflow 权限不能隐式替代记忆权限；读取、提议、审核和正式写入分别裁决。

| 身份 | 默认可读记忆 |
| --- | --- |
| 董事长助理 | 自身长期总记忆、Agent × Workspace 协调/汇报摘要、Workspace 公共；部门项目记忆仅按协调授权读取必要部分 |
| 部门主管 | 自身长期、Agent × Workspace 项目、Workspace 公共、本部门当前 Workspace 项目管理记忆 |
| 专业/执行 Agent | 自身长期、Agent × Workspace 项目、Workspace 公共、所属部门当前 Workspace 项目记忆 |

跨部门参与不自动授予全部部门记忆。提议者不能批准自己的候选；需要自审时按组织关系向上升级。候选改投其他 MemorySpace 后必须重新检查可见性、提议权限和审核策略。

### 9.3 MemoryCandidate 独立状态机

```text
Proposed → Validated → PendingReview
→ Approved | Rejected | ChangesRequested
→ WritePrepared → AtomicallyWritten → RevisionRecorded
```

- 所有正式记忆变化都必须先形成 MemoryCandidate；
- 每个候选只有一个主要目标 MemorySpace；
- `Approved` 只表示审核通过，不表示文件写入成功；
- `AtomicallyWritten` 只表示批准内容已写入目标文件；
- `RevisionRecorded` 记录不可变版本、来源、审核、基线和哈希；
- 投影是否重新编译与终端是否加载均不是候选状态机的下一状态。

记忆写回前必须重新校验目标 revision、content hash、权限、路径和符号链接边界，展示候选 Diff，并使用受控备份和原子替换。普通配置的简化保存流程不得绕过这套审核。

### 9.4 MemoryProjection

CLI / Plugin 按当前 Agent、Workspace、Department、SOP 和权限解析 MemoryProjection：

```text
Agent 长期记忆
→ Workspace 公共记忆
→ 当前 Department × Workspace 部门项目记忆（按职责和权限）
→ Agent × Workspace 项目记忆
→ 当前任务临时上下文（仅在 Claude Code 内，不持久化）
```

每层保存 `scope`、`owner`、`revision`、`content_hash`、来源、纳入原因和权限裁决。组合顺序表示上下文逐步收窄，不是后层静默覆盖前层；内容冲突必须保留来源并阻止或显式降级投影。董事长助理的长期总记忆与 Workspace 协调摘要来自其与董事长、部门主管的正式交互提炼，不复制负责部门的完整项目管理台账。

## 10. Bandi Plugin 与 Claude Code 衔接

### 10.1 Plugin 定位

Bandi Plugin 是 Claude Code 侧稳定安装基线，也是当前会话读取 Bandi 配置事实、校验委派边界和提交持久化提议的适配层。`attachCurrent` 等当前会话行为只属于 Plugin，不成为 Desktop API 或持久化接入记录。

Plugin / MCP 可以读取授权配置、校验委派边界、提交经用户同意的 SOP/普通配置变更或 MemoryCandidate，但不把任务、一次性权限授权、执行状态或 Session 生命周期写入 Local Service。

### 10.2 Desktop 衔接契约

```ts
interface ClaudeCodeGuideService {
  inspectConfig(input: GuideInspectionInput): Promise<GuideInspection>
  buildGuide(input: BuildGuideInput): Promise<ClaudeCodeGuide>
  requestOpenTerminal(input: OpenTerminalInput): Promise<TerminalRequestResult>
}
```

Desktop 只展示 Workspace、cwd、标准命令和 Bandi Plugin 入口。终端请求成功只表示操作系统接受请求；Local Service 不继续发布 Session 或执行进度事件。

CLI / Plugin 可在自身边界内按需编译 RuntimeProjection。临时工具授权不得自动写回长期权限；只有用户明确选择永久化时，才提交普通配置保存，并在 Desktop 或等价可信界面完成长期权限变更确认与 ConfigRevision 记录。

## 11. SOP、委派与策略服务

SOP/WorkflowDefinition 是描述适用场景、分工边界、必要检查和交付要求的配置资产，不是由 Local Service 驱动的运行实例。它由 Claude Code 中的董事长助理结合当前任务解释执行，并可继续委派主管；主管再选择员工。具体任务、步骤、交接、汇报和验收始终留在用户自己的 Claude Code CLI。

```ts
interface WorkflowDefinitionService {
  create(input: WorkflowDefinitionInput): Promise<WorkflowDefinition>
  validateDefinition(id: string): Promise<WorkflowValidation>
  saveVersion(id: string, input: WorkflowDefinitionInput): Promise<WorkflowVersion>
  compose(parentId: string, childId: string, nodeId: string): Promise<void>
}

interface DelegationConstraintService {
  evaluateCandidate(input: DelegationCandidate): Promise<DelegationDecision>
  explainGap(input: DelegationGapInput): Promise<DelegationGap>
  validateDefinitionScope(input: WorkflowScopeInput): Promise<WorkflowValidation>
  detectCycle(input: DelegationGraph): Promise<CycleDetection>
}
```

每次委派必须同时校验：

1. **部门职责**：任务属于候选部门的明确职责范围；
2. **岗位与 Skills**：候选 Agent 的岗位职责和已配置 Skills 覆盖任务需要；
3. **WorkspaceBinding**：候选 Agent、部门及配置资产允许用于当前 Workspace；
4. **MCP 与权限**：所需 MCP、工具、目录、网络和数据权限已配置且未超出边界；
5. **委派关系**：董事长只委托董事长助理，助理只向允许的主管委派，主管默认只向本部门员工委派；跨部门候选必须存在有效服务授权，且任务能力、Workspace 和禁止事项均匹配；
6. **Agent 状态**：只有 `active` Agent 可以接受新委派，`inactive` 和 `archived` 只保留档案与历史；
7. **SOP 适用范围**：使用的 SOP/WorkflowDefinition 适用于当前 Company、Department、Role、Workspace 和任务类型。

组织身份、主管标签、岗位或服务关系本身不授予文件、命令、网络、MCP、记忆和继续委派权限；这些能力必须由权限配置显式授予。Agent 可以在有效边界内收紧权限，但任何扩大都必须向上报告并由有权主体确认后写入，不能在执行中自行放宽。

Local Service 只返回配置事实、校验结论和缺口诊断；MCP 只是 Claude Code 中的适配层，不定义 SOP、不决定组织关系、不创建任务或调度人员。若没有候选 Agent 同时满足约束，必须报告缺失项并请求补充配置、调整目标或由用户明确决策，不得静默越权。

终端中的临时计划、分工、交接、工具进度、汇报和验收不创建 WorkflowRun 或 WorkflowStepRun，也不进入 Local Service。只有用户明确同意把可复用做法沉淀为正式 SOP 时，Plugin/MCP 才提交配置变更，经校验与受限写回形成不可变版本。`saveVersion` 只表达保存版本，不具有发布审批语义。

## 16. 技术验收标准

1. Desktop、CLI 和 Plugin 读取同一 Local Service 事实、配置解析和策略；
2. Rust 是 SQLite 业务事实唯一写入者，也是配置文件受限写回的唯一入口；
3. React UI 无通用 Shell、任意文件系统和凭据读取权限；
4. 已授权根中的真实配置资产可发现，稳定身份、作用域、格式、路径和引用可解释；
5. 外部配置保持 SourceAsset 身份，未经明确导入不复制为 Bandi 主源；
6. 有效配置能逐字段解释 Agent 自有设置、全局普通默认、显式共享引用、全局强制边界、显式清空和 Agent × Workspace 专属设置；
7. Company、Department、Role 和 Workspace 不向 AgentPackage 隐式注入普通配置；WorkspaceBinding 是 Agent 面向特定 Workspace 的独立真实配置；
8. Department 通过 `parent_department_id` 构成无环组织树；创建、移动和删除均校验循环、主管归属与成员迁移，组织调整不改写 AgentPackage 配置；
9. Agent 最多一个主属部门，可有多个带目标部门、能力、Workspace 与禁止事项边界的服务授权；停用和归档保留档案且不接受新委派，永久删除使用独立高风险事务；
10. 共享资产默认 Company 内共享，跨 Company 必须单独注册和授权，局部定制不修改共享本体，删除前处理全部有效引用；
11. 组织身份不授予执行或委派权限；Agent 可收紧但不能自行扩大，缺少权限时返回缺口并由有权主体确认；
12. Bandi 自管 AgentPackage 使用 `~/.bandi/agents/<stable-agent-id>/`，不随显示名或部门移动；根级长期配置与 `workspaces/<workspace-id>/` 专属配置映射到同一组可外部编辑的真实资产；
13. Workspace 的 `company_id` 可空但不可多值；关联后主责部门、项目负责人和协作部门必须来自同一 Company，有效配置与安全边界不得跨公司合并；
14. 每个已关联组织的 Workspace 只能存在一个主责部门和默认项目负责人，可存在多个协作部门；变更主责关系保留公共记忆、部门记忆和历史，不自动改写 AgentPackage 或 WorkspaceBinding；
15. 普通保存严格执行 `ResolveTarget → LoadBaseline → ValidateEdit → CheckCurrentBaseline → AtomicallyWrite → Re-read/Verify → Saved`；
16. UI 普通流程只显示“修改 → 保存 → 已保存”，且写后验证前不得显示成功；
17. Diff 只在用户主动查看或 `BaselineChanged` 时出现；
18. 共享影响只针对存在多个有效引用的同一真实资产；
19. 冲突只用于真实并发、互斥规则和无法一致解析，不把普通覆盖或权限变化称为冲突；
20. 权限扩大在写入前显示边界变化、影响主体和可逆方式，并要求额外确认；
21. 写回防止路径穿越、符号链接逃逸、跨 Workspace 越权和静默覆盖；
22. 原子替换后必须重新读取和解析，内容与有效语义均验证成功才返回 `Saved`；
23. 文件监听以重新读取为准，能使缓存失效并触发编辑中的 `BaselineChanged`；
24. 每次普通配置成功保存生成不可变 ConfigRevision；失败不生成；
25. 可列出和比较 ConfigRevision；恢复复用安全写入链并生成新 revision，记录恢复来源；
26. ConfigRevision 与 BackupSnapshot 分工清晰，均不替代基线检查；
27. RuntimeProjection 可由 CLI / Plugin 按需重建，不是 Desktop 日常配置主源或 Session 状态；
28. Desktop 只展示 cwd / 命令并可请求打开终端，结果不等于 Session 已创建、已连接或已加载配置；
29. 所有任务交互、分层委派、执行推进、汇报和验收只发生在用户自己的 Claude Code CLI；
30. 董事长只与董事长助理交互，助理按配置选择部门和主管，主管按配置选择员工；
31. 每次委派同时校验部门职责、岗位/Skills、WorkspaceBinding、MCP/权限、委派关系和 SOP 适用范围；
32. 无合适 Agent 时返回明确配置缺口，不静默跨部门、突破委派关系、扩大权限或使用未配置替代能力；
33. Desktop 和 Local API 不提供任务创建、人员调度、执行推进、聊天、汇报、验收或运行控制 UI/API；
34. Plugin/MCP 只读取配置事实、校验委派边界和提交必要持久化提议，不成为任务执行器；
35. SOP/WorkflowDefinition 作为配置资产由 Claude Code 中的助理解释执行，临时协作只有经用户同意才保存为正式 SOP；
36. Local Service 不持久化任务审批、一次性工具授权、任务冲突、WorkflowRun 或执行状态，也不向 Desktop 发布 Session/执行进度事件；
37. Bandi 不采集或镜像终端计划、委派、提示词、工具调用、中间结果、进度、汇报、验收、用量和会话生命周期；
38. 前端不提供 WorkflowRun、人员调度台或基于推断的执行中、完成、停止、恢复状态；
39. 四类 MemorySpace 的 owner、steward、reviewer 和 Local Service 写入执行者严格分离；
40. 每个 Agent × Workspace 使用独立项目记忆载体，共享与部门记忆不存入个人 AgentPackage；
41. SOP/Workflow 权限不自动授予记忆读取、提议、审核或写入权限；
42. 所有正式记忆变化先形成 MemoryCandidate，提议者不能自审；
43. MemoryCandidate 批准、原子写入、Revision 记录和投影重编译分别建模；
44. MemoryProjection 保留来源、版本、哈希、纳入原因和权限裁决，冲突不静默覆盖；
