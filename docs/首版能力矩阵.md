## 1. 用途与判定规则

本矩阵把页面承诺拆成可验证的竖切片，统一记录当前事实、首版目标、后端责任、证据、测试和缺口。它不是路线图状态看板，不记录任务、Session 或执行进度。

状态采用正交双轴：数据来源证据固定为 `real / memory-only / demo-fixture / read-only`；系统能力状态固定为：

| 状态 | 含义 | UI 约束 |
| --- | --- | --- |
| `supported` | 已有真实实现与可复现证据，完整满足本切片目标 | 可以提供正常主操作，但不得扩大证据含义 |
| `degraded` | 已有真实实现证据，但只覆盖部分路径；仍有明确、安全的手动或只读降级 | 必须说明已验证范围、限制和补救，不得显示完整成功；纯演示不能使用此状态 |
| `unavailable` | 已确认当前实现不能完成 | 禁用操作并解释原因与补救 |
| `not_checked` | 尚未执行探测、验证或合同测试 | 不得当作可用；可展示检查入口或保持演示/只读 |

每项能力事实必须同时提供：

- `reason`：为什么是该状态；
- `evidence`：支持结论的可验证代码、测试、文件事实或后端回执；
- `remediation`：进入更高状态所需的用户动作或施工缺口。

`real` 表示真实读取、持久化回执或写后验证；`memory-only` 表示本次页面内存操作；`demo-fixture` 表示预置演示资料；`read-only` 表示有真实来源但当前不可写。`demo-fixture`、`memory-only`、页面文案、按钮可点击和类型声明都不能单独作为真实系统能力证据，也不能据此把能力标为 `degraded`；没有真实实现证据时使用 `not_checked` 或经验证后的 `unavailable`。

## 4. 首切片合同测试最低集合

首个竖切片合并前至少具备以下自动化证据：

1. Rust 与 TypeScript 对冻结 DTO 使用同一组 JSON fixture，并双向通过序列化/反序列化；
2. Discovery 覆盖授权根、官方 scope、多 fragment、未知格式、解析失败、符号链接逃逸和脱敏；
3. LoadEditor 覆盖 current/legacy/future/unverified、可写性、双哈希和外部变化；
4. Instructions SaveConfig 覆盖全部结果分支、原子写后重读、unknown kind 拒绝和 revision 一致性；
5. LocalServiceEvent 覆盖失效通知、去抖、重复事件和普通保存无进度事件；
6. RequestClientHandoff 验证请求恰好五个字段、非法 client/adapter 组合拒绝、Workspace 路径由后端重取、仅固定 `/usr/bin/open` 打开 cwd、响应不含命令，以及四种能力状态均包含非空 `reason`、`evidence`、`remediation`；
7. 9 个内置工具 ID 与 Adapter ID 唯一且完整，仅 Claude Code/Codex 的已验证组合可进入目录打开路径，其余状态和错配组合不得触发外部动作；
8. 全部失败路径不产生 Session、任务、日志、运行状态或伪造成功证据。

## 5. 变更规则

- 页面新增真实主操作前，先在本矩阵增加能力行并按联调契约第 14 节冻结 DTO；
- 状态提升必须补充可复现 evidence 和测试，不能只修改文案；
- `degraded` 提升为 `supported` 时必须删除已不成立的限制，保留仍有效的人工回退测试；
- 新增客户端不自动获得交接能力；内置身份、探测、配置和 Adapter 分别判定；
- 本矩阵只描述当前首版，不修改或引用 `docs/archive/*`。
